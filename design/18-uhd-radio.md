## 1. Purpose

Vision §59 asks whether experiments written against MockRadio run on a USRP by changing only the BindingProfile. This Module is the other side of that comparison: it implements spec 07 on an X310 as MockRadio implements it in simulation, reports what the device does through the same events, flags and records, and declares what it cannot promise. It is written so that everything except the device itself runs without hardware: the Provider's logic talks to a `Device` trait, and the tests drive it with `FakeDevice`, a wall-clock double of a USRP, through the real coordinator.

## 2. Evidence

- **UHD's C API is a narrow bridge already** (VERIFIED, UHD 4.10 headers on this Mac, `/opt/homebrew/include`): every C entry point wraps its body in `UHD_SAFE_C`, which catches `uhd::exception`, `boost::exception`, `std::exception` and `...`, stores the text for `uhd_get_last_error` and returns a `uhd_error` code (`uhd/error.h:89-104`). Handles are opaque pointers, structs are POD (`uhd/types/metadata.h`, `tune_request.h`, `usrp/usrp.h`). This is what Vision §35 asks the bridge to be.
- **Receive metadata codes** (VERIFIED, `uhd/types/metadata.h:80-92`): `NONE 0x0`, `TIMEOUT 0x1`, `LATE_COMMAND 0x2`, `BROKEN_CHAIN 0x4`, `OVERFLOW 0x8` (with `out_of_sequence` distinguishing a sequence error), `ALIGNMENT 0xC`, `BAD_PACKET 0xF`. **Asynchronous transmit codes** (`:232-244`): `BURST_ACK 0x1`, `UNDERFLOW 0x2`, `SEQ_ERROR 0x4`, `TIME_ERROR 0x8`, `UNDERFLOW_IN_PACKET 0x10`, `SEQ_ERROR_IN_BURST 0x20`, `USER_PAYLOAD 0x40`.
- **Timed commands** (VERIFIED, `uhd/usrp/multi_usrp.hpp`, `set_command_time`): "A timed command will back-pressure all subsequent timed commands … If the time spec is late, the command will be activated upon arrival." The device neither refuses a full queue nor reports a late command: the Provider must count and judge both itself (UR-24).
- **Setting device time** (VERIFIED, `set_time_unknown_pps`): "a 2-step process, and will take at most 2 seconds", and "when changing clock sources, a previously set time will most likely be lost … set the time after changing the clock source". v3 sets the clock source, then the time source, in that order (`v3/cpp/uhd_usrp/multiusrp.cpp:332-347`, cited by the spike).
- **Sensors** (VERIFIED, `uhd/usrp/usrp.h:448`, `uhd/types/sensors.h:55-121`): `uhd_usrp_get_mboard_sensor` and `uhd_sensor_value_to_bool` read `ref_locked`.
- **Alignment** (VERIFIED by Phase 4 Review D in UHD master `0d7ed3b`, `rx_streamer_impl.hpp`, `get_aligned_buffs.hpp`): an alignment failure yields no samples, or only aligned ones, and discards packets whose timestamps disagree; never a partial channel set.
- **Overflow**: UHD restarts a continuous stream `OVERRUN_RESTART_DELAY` = 0.05 s after an overflow (VERIFIED, audit Finding 3; MR-3).
- **The X310 values** of MockRadio's `x310-like` 1.2.0, with the sources MR-3 marks (spec 09 §2).
- **The spike** (`spike/uhd`, VERIFIED on its fake device and against libuhd with no device): the C API slice of ~40 functions, the anchor-and-extrapolate Authority, the thread structure, and findings K1–K13.
- **INFERRED** (checked on the bench, `bench.md`): the device lead, the delivery allowance, the restart and start leads, the in-flight window and the release window of §3; how many timed UBX commands the device's queue holds before it back-pressures (UR-24); which UHD errors mean a lost device (UR-29); the drift bounds of UR-8; and every INFERRED value of UR-9. **Measured on the bench and applied** (design-notes §11, the owner's decision of 2026-09-30): the X3x0 ignores the time of a continuous receive stream's stop and stops at once (VERIFIED: UHD 4.10's `radio_rx_core.v` and `hw_b8_raw_rx_timed_stop`), so UR-25 hands the device no timed stop; the X300 drops a timed start-of-burst at the tick its previous burst ended (`hw_b8_raw_burst_gap`), so UR-23 continues the device burst there.

## 3. Model

```text
                         runtime (server catalogue / test assembler)
                               │ open(args) ──► Arc<dyn Device> ◄── FakeDevice::new(..) (tests only)
               ┌───────────────┴────────────────┐
         DeviceAuthority (Authority)        UhdRadio (Provider, not stepped)
         root = device master clock           │ prepare: apply, verify, declare clocks
         now = anchor + host elapsed          │ arm: streamers, transmit clock on the lattice
         uhd-clock: re-anchor every 100 ms    │ start(T0): receive clock at T0, timed start
         next_wakeup: nap ≤ 20 ms             │
                                              │
            threads:  uhd-control ── ActionReceiver (MA-14b loop, 1 ms): books Actions, releases
                                     held timed commands, checks reference and device time
                      uhd-rx ─────── owns the receive streamer: recv → blocks → Links;
                                     RX_OVERFLOW on the hot path; performs receive switches
                      uhd-tx ─────── owns the transmit streamer: bursts in target order → send,
                                     BurstTracker; async reports; performs transmit switches

 Kernel side (spec 19): data thread steps the capture Sink (KC-46); KC-21a waits for uhd-control to
 finish a Session's Actions; a DEVICE_LOST from uhd-rx stops the radios at once (MA-9a, KC-46b).
```

A tick of the Run's primary root is one master-clock tick of the device (200 MHz). Every SampleClock is `root_ticks_per_tick = N` for the device's integer decimation `N` (UR-12).

The Module's own constants, all INFERRED and measured at bench step B8, are: the **device lead** 2 ms (the lead it needs from receipt, UR-21, UR-24); the **delivery allowance** 3 ms (UR-14; the declared lead is their sum, 5 ms); the **start lead**, 50 ms, the profiles' `start_lead_ns` (UR-9, UR-25): the bench's raw restarts began on the requested tick at leads down to 1 ms in 19 of 21 rows (`hw_b8_raw_restart_lead`), so 50 ms is a margin whose value Phase 8 measures; the **in-flight window** 10 ms (UR-23); the **release window** 3 ms (UR-24). **Ceiling:** the lead is 50 ms on every profile, the value of the constant it replaces, so no test tells the Module reading its profile from reading a constant until a profile gives it another value, such as Phase 8's measured one.

## 4. Rules

### Identity and the device boundary

- **UR-1** The Module is `ModuleDescriptor { id: ezsdr.radio.uhd, version: 0.4.0, kernel_api: 4.0.0, roles: [Provider, Authority], vocabularies: [{ radio, ^2.0.0 }], deployment: InProcess, impl_hash: Some(ContentHash::of_bytes(b"ezsdr.radio.uhd 0.4.0")) }` (spec 20, VF-6: 0.2.0 and `radio ^1.4.0`, for the profiles' restart and start leads; issue #41; spec 21, VG-1: 0.3.0, for a receive stream's end that moves only earlier (UR-26), its requirement and profiles unchanged; issue #46), returned by `ezsdr_radio_uhd::descriptor()`; `module_ref()` returns its `{ id, version }`. A runtime registers it with `Factories { provider: true, authority: true }`. *Checked by `ur_01_the_descriptor_registers`.*
- **UR-2** Everything the Provider and the Authority do to a device goes through the object-safe trait `ezsdr_radio_uhd::Device: Send + Sync`, whose methods are exactly:

  ```rust
  fn describe(&self) -> serde_json::Value;           // identity for the Manifest (UR-30)
  fn fidelity(&self) -> Fidelity;                    // UR-31
  fn master_clock_rate(&self) -> u64;                // integer Hz
  fn channels(&self, dir: Dir) -> usize;             // Dir::{Rx, Tx}
  fn front_end(&self, dir: Dir, chan: usize) -> Result<String, DeviceError>;  // UHD's name, e.g. "UBX RX" (UR-5)
  fn set_sources(&self, clock: &str, time: &str) -> Result<(), DeviceError>;
  fn set_time_zero(&self, at_next_pps: bool) -> Result<(), DeviceError>;
  fn time_now(&self) -> Result<i64, DeviceError>;    // master-clock ticks since the time was set
  fn ref_locked(&self) -> Result<Option<bool>, DeviceError>;  // None: the device has no such sensor
  fn apply(&self, dir: Dir, chan: usize, s: &Settings, at: Option<i64>) -> Result<Applied, DeviceError>;
  fn rx_open(&self, channels: usize) -> Result<(), DeviceError>;
  fn rx_start(&self, at: i64) -> Result<(), DeviceError>;
  fn rx_packet_samples(&self) -> usize;              // UHD's max_num_samps; 0 when not open (UR-25; Review O)
  fn rx_stop(&self, at: Option<i64>) -> Result<(), DeviceError>;
  fn rx_recv(&self, n: usize, timeout: std::time::Duration) -> RxRecv;
  fn tx_open(&self, channels: usize) -> Result<(), DeviceError>;
  fn tx_send(&self, samples: &[&[Iq]], at: Option<i64>, sob: bool, eob: bool,
             timeout: std::time::Duration) -> Result<usize, DeviceError>;
  fn tx_async(&self, timeout: std::time::Duration) -> Result<Option<TxReport>, DeviceError>;
  fn close_streams(&self);
  fn mark_lost(&self);
  ```

  with `Iq = [f32; 2]` (UHD's `fc32`); `Settings { rate, freq, gain: Option<f64>, antenna: Option<String> }`, `None` leaving a setting alone; `Applied { rate, freq, gain: f64 }`, read back after an untimed change; `DeviceError { lost: bool, message: String }`, `lost` meaning the device is gone (UR-29); `RxRecv` one of `Samples { first_tick: i64, samples: Vec<Vec<Iq>> }` (one vector per channel, all the same length ≥ 1), `Overflow { out_of_sequence: bool }`, `LateCommand`, `Alignment`, `BadPacket`, `Timeout` and `Failed(DeviceError)`; `TxReport { code: TxCode, tick: Option<i64>, channel: usize }` with `TxCode` one of `BurstAck`, `Underflow`, `UnderflowInPacket`, `SeqError`, `SeqErrorInBurst`, `TimeError`, `Other(i32)`. Ticks are master-clock ticks; no floating-point time crosses the trait. *Checked at compile time (`ur_02_device_is_object_safe_and_shared`).*
- **UR-3** `UhdDevice` (module `src/uhd.rs`, feature `uhd`) implements `Device` on UHD's C API. The module is the crate's only `unsafe` code (GZ-3). It declares by hand exactly the functions it calls — `uhd_get_last_error`, `uhd_usrp_last_error`; `uhd_string_vector_{make,free,size,at}`; `uhd_usrp_{find,make,free,get_pp_string,get_master_clock_rate,get_time_now,set_time_now,set_time_unknown_pps,set_command_time,clear_command_time,set_clock_source,set_time_source,get_mboard_sensor,get_mboard_sensor_names}`; `uhd_sensor_value_{make,free,to_bool}`; `uhd_usrp_{get,set}_{rx,tx}_{rate,gain}`, `uhd_usrp_set_{rx,tx}_freq`, `uhd_usrp_get_{rx,tx}_freq`, `uhd_usrp_set_{rx,tx}_antenna`, `uhd_usrp_get_{rx,tx}_num_channels`, `uhd_usrp_get_{rx,tx}_subdev_name`; `uhd_{rx,tx}_streamer_{make,free,max_num_samps,last_error}`, `uhd_usrp_get_{rx,tx}_stream`, `uhd_rx_streamer_recv`, `uhd_rx_streamer_issue_stream_cmd`, `uhd_tx_streamer_send`, `uhd_tx_streamer_recv_async_msg`; `uhd_rx_metadata_{make,free,has_time_spec,time_spec,error_code,out_of_sequence,strerror}`; `uhd_tx_metadata_{make,free}`; `uhd_async_metadata_{make,free,channel,has_time_spec,time_spec,event_code}` (all present in UHD 4.10.0's headers, Review J; the two `subdev_name` calls, added for UR-5 on 2026-09-30, in `usrp.h` of v4.10.0.0) — with the structs `uhd_stream_args_t`, `uhd_stream_cmd_t`, `uhd_tune_request_t`, `uhd_tune_result_t` laid out as the UHD 4.x headers lay them out. Every call's `uhd_error` other than `UHD_ERROR_NONE` becomes `DeviceError { lost, message: "<call>: UHD error <code>: <text>" }`, the text read from the handle the call was made on — `uhd_usrp_last_error` under the control-call mutex, `uhd_{rx,tx}_streamer_last_error` under the streamer's call mutex — and from `uhd_get_last_error` only for a call on no handle, because UHD's global string is overwritten by every other thread's successful call ("None") (Review L, P1-2). A streamer value owns its handles from their creation and is moved into its `Arc` (Review L, P0-1: a copy freed them twice), and an open releases the old streamer before it makes the new one (Review L, P1-3). Streams are `fc32` on the host and `sc16` on the wire (`radio.perf.wire_bytes_per_sample` 4). **Time conversion** (TM-20): a tick `t` is sent as `full = t.div_euclid(mcr)`, `frac = t.rem_euclid(mcr) as f64 / mcr as f64`; a time spec `(full, frac)` is read as `full · mcr + round(frac · mcr)`, rounding to nearest, ties away from zero, with `checked` arithmetic (an overflow is a `DeviceError`); a tick converted to a time spec and back is the same tick for every tick in `0 ..= 2^53` (`rem < mcr < 2^28`, so the round trip is exact). `open` refuses a device whose master clock rate is not a positive whole number of hertz. **Threads.** The handles are shared by the Module's threads under two rules: every **control call** (`apply` with its `set_command_time`…`clear_command_time` bracket, which is per-motherboard state; `set_sources`, `set_time_zero`, `time_now`, `ref_locked`; and the timed stream commands of UR-15, UR-17 and UR-25) is made under one `UhdDevice` mutex, and a time read used for an anchor or a relation takes its host brackets around `Device::time_now`, which takes the mutex inside, so that a read that waited for the mutex is widened and UR-7's 1 ms rule discards it (the `Device` trait has no bracketed read; Review L, deviation 6); and each **streamer** has one owning thread at a time — uhd-rx owns the receive streamer (`recv`, the stream commands, and its reopen, UR-25), uhd-tx the transmit streamer (`send`, `recv_async_msg`, and its reopen) —, each streamer's handle being kept alive by an `Arc` its owner holds, so that `close_streams` frees only a streamer no thread holds (UR-16). The public safe `Device` methods enforce exclusive native access with a separate mutex on each streamer, held through the call and all metadata/error-text reads; receive stream commands share that receive mutex, and transmit sends and asynchronous reports share the transmit mutex. Construction and final destruction have exclusive handle ownership. `UhdDevice` is `Send + Sync` on that enforced basis, stated at its `unsafe impl` (INFERRED from UHD's documented thread safety of `multi_usrp` control calls; the bench runs every step with these threads). *Checked by `ur_03_time_specs_round_trip` (default build: the conversion functions live outside `uhd.rs`), and with the feature by `uhd_api_find_returns`, `uhd_api_open_of_an_absent_device_is_an_error_with_uhd_s_text` and `uhd_api_struct_sizes_match_the_headers`.*
- **UR-4** `ezsdr_radio_uhd::open(args: &str) -> Result<Arc<dyn Device>, String>` opens the device UHD's device string `args` names (`uhd_usrp_make`). Built without the feature `uhd` it returns `Err("ezsdr.radio.uhd: built without UHD (feature `uhd`)")`. It never returns a `FakeDevice`, whatever `args` says (GZ-9). A runtime calls it once per binding, and the Provider and the Authority built from that binding share the returned object (UR-6). *Checked by `ur_04_open_without_the_feature_refuses` and `ur_33_no_document_selects_the_fake_device`.*

### Construction and the Authority

- **UR-5** `UhdRadio::from_binding(binding: &Binding, device: Arc<dyn Device>) -> Result<UhdRadio, ModuleError>` refuses with `Rejected`: a `module` other than UR-1's; a `profile` other than `x310-ubx`, `x310-obx` or `x310-cbx` 0.3.0 (absent is refused); a `feed`; a selector key other than these, or one of the wrong kind or out of range; a device whose master clock rate is not the profile's 200 000 000 Hz (reason `"UR-5: profile <p> needs a 200 MHz master clock; the device runs at <n> Hz"`); and a device that has fewer channels in a direction than the profile's (reason `"UR-5: profile <p> needs <k> <rx|tx> channels; the device has <m>"`) or whose front end on one of those channels `Device::front_end` names otherwise than the profile's (`UBX…` for `x310-ubx`, `OBX…` for `x310-obx`, `CBX…` for `x310-cbx`, as UHD names them: `UBX RX`, `OBX TX`, `CBX-120 TX`; reason `"UR-5: profile <p> needs <UBX|CBX> front ends; <rx|tx> channel <c> is `<name>`"`). The last two exist because UHD clips a tune to the front end's range widened by the DSP's reach (min(DSP range, bandwidth / 2), `multi_usrp_utils.hpp`) without a warning — it is in `tune_result.clipped_rf_freq` and the read-back, which UR-12 records but does not refuse — after the RF envelope (RM-19) passed the claimed frequency: `x310-ubx` on a CBX would transmit at about 1.18 GHz (1.14 GHz on a CBX-120) a Run the envelope allowed at 1 GHz (VERIFIED, UHD 4.10.0.0; Review of 09f11b4, P2-1). A real X310 with one CBX in slot A and slot B empty reports 2 + 2 channels, channel 0 the CBX and channel 1 UHD's unknown board (`db_unknown.cpp`), so only the profile's own channels are checked:

  | `id` | str, one `ResourceId` segment matching `^[a-z][a-z0-9_]*$` | `"usrp"` | the device node's path and the `<id>` of UR-30's section names |

  *Checked by `ur_05_from_binding_refusals`.*
- **UR-6** The Authority role is taken by the radio's own binding: the BindingProfile's `authority` names the binding of `ezsdr.radio.uhd`, and the runtime builds `DeviceAuthority::new(device, clocks, clock_source, time_source, args)` from it, with the same device object as the Provider (SB-22c; spike K4). The Provider refuses in `prepare` a primary root that is not its own device's: the root's `EpochRef::Arbitrary { set_by }` must be `"ezsdr.radio.uhd.set_time_now:<args>"` or `"ezsdr.radio.uhd.set_time_unknown_pps:<args>"` with the Provider's own `args` (reason `"UR-6: the primary root is not this device's; bind the Authority to the radio's own binding"`). *Checked by `ur_06_the_provider_refuses_another_root`.*
- **UR-7** `DeviceAuthority` implements `Authority` with pacing `Device`. `new` sets the reference sources (`set_sources(clock_source, time_source)`, the clock source first), then sets the device's time to zero — at the next PPS edge (`set_time_zero(true)`, up to 2 s) when `time_source` is not `internal`, at once otherwise — and registers the device's master clock as a new Root with rate `master_clock_rate / 1` and UR-6's epoch. Its `TimeAuthority`:
  - `now(root)` extrapolates from an **anchor** (a host `Instant` and a device tick read together) by the host time elapsed since, and is monotonic (a value never below one it returned before). The anchor is re-read from the device by a thread of the Authority's own, `uhd-clock`, every 100 ms for as long as the Authority lives, and at every nap of `next_wakeup` and `wait_until` — a read whose host bracket is wider than 1 ms is discarded and the previous anchor kept (Review K, N-P2-5) —, so the extrapolation never runs on the host clock alone for more than 100 ms, whether or not a client call is running (Review J, P1-4); `now(host.monotonic)` is the nanoseconds since the Authority was built; `now` of a domain derived from the root is the floor conversion (TM-16c);
  - `schedule(t, f)` requires `t` on a governed domain and a tick of the root (TM-16c's `Inexact` otherwise), and at or after the last instant `next_wakeup` fired (`InPast` otherwise; TM-16c as KG-9 amends it for a paced Authority): an accepted `t` at or before `now` fires at the next `next_wakeup`, which returns `t`. It keeps callbacks in `(tick, sequence)` order and wakes a waiting `next_wakeup`; `cancel` removes a pending callback, reports whether it was pending, and wakes a waiting `next_wakeup` (MA-29 as KG-3 amends it);
  - `next_wakeup()` returns `None` at once when nothing is scheduled; otherwise it waits — in naps of at most 20 ms, each followed by a re-anchor, and woken early by `schedule` and `cancel`, after which it re-evaluates (returning `None` if a cancel emptied the schedule) — until `now(root)` reaches the earliest scheduled instant, fires every callback due at that instant in order, including ones they schedule at it, up to 1 000 (TM-17b), and returns the instant; callbacks observe `now()` at or after their instant (TM-16c as KG-9 amends it);
  - `wait_until(t)` sleeps the same way until `now` reaches `t`;
  - it governs its root, the root's derived domains and `host.monotonic` (TM-16a, TM-16a1), and its descriptor is `{ module: module_ref(), governs: [root, host.monotonic], pacing: Device }`.

  A device time read that fails, or that is bracketed more widely than 1 ms, leaves the anchor as it was, so `now` goes on advancing with the host clock from the last good read; both are counted, by `DeviceAuthority::failed_reads()` and `discarded_reads()`, not in the Manifest — an Authority has no section of its own (MA-29) — and the bench prints them (B2); a lost device is found and reported by the Provider (UR-29), not by the Authority. A `set_clock_source` that fails because the X300's reference PLL did not lock within UHD's 30 s (`x300_mb_controller.cpp:243–255`; about 4 % of opens on the bench, parts 6–9; a new open locked every time) refuses the Authority with `UR-7: the reference clock did not lock to its <clock_source> source within UHD's 30 s; connecting again usually succeeds (<UHD's text>)`, which the server returns as the Connect's refusal; the error begins with `REFERENCE_DID_NOT_LOCK`, which the crate exports. **The server opens the device again once on it** — dropping the first device and its radio, building both anew — unless the binding's `reopen_on_unlock` is `false`; a second refusal stands, and a Run built on the reopen records `timing { reopened_on_unlock, first_error }` (design-notes §18; INFERRED that an open within the same process locks as a new process did). ### The Provider's lifecycle

- **UR-10** `instance()` returns `ProviderInstance { id: <id>, module: module_ref(), profile: the binding's, tree: the description's tree for <id> (RM-2), fidelity: device.fidelity() (UR-31), driving: { stepped: false }, arm_after: [], min_command_lead: Some(Duration(host.monotonic, 5 000 000)), sections: UR-30's }`. *Checked by `ur_10_instance`.*
- **UR-11** `coerce(request)` is the description's `coerce` for `<id>` (RM-26): pure, no device call (MA-11). *Checked by `ur_11_coerce_is_the_descriptions` (19.5 Msps → 20 Msps; 7 GHz rejected; four channels refused).*
- **UR-12** `prepare(fragment, ctx)` refuses with `Unsupported` a class other than HardwareInLoop or Hardware (reason `"UR-12: ezsdr.radio.uhd runs HardwareInLoop or Hardware, not <class>"`), and with `Rejected`: a second call (one fragment per instance, as MR-7); a fragment whose instance or role is not this Module's Provider; a fragment content with no `Requested`; any `rejected` entry of its own `coerce`; a primary root that is not its device's (UR-6); a channel count above `device.channels(dir)`; an attached link that is not a `StreamOut` on the fragment's `rx` port, or one whose policy is `Block` (a device cannot wait for a consumer; it overflows); several links on `rx` are allowed, each receiving every block (UR-17). Then, for each direction whose channel count is > 0, it **configures the direction** (below). It declares the SampleClock of each stream whose count is > 0, `<id>/rx` and `<id>/tx`, on the primary root with `root_ticks_per_tick = N`. It keeps `ctx`'s handles and returns `PrepareReport { fragment, effective: RM-5's ten keys with the applied values, coercions: its coerce's, warnings: [] }` (MA-12). **Configuring a direction** — here, when a stream is enabled or its channel count raised (UR-25), and nowhere else — applies the direction's full current configuration (rate, frequency, gain, antenna) to every channel of its count, untimed, and reads it back: the read-back rate must be exactly the claimed one, with `N = round(200 000 000 / rate)` in 1…512 and `200 000 000 / N` computed in `f64` equal to `rate` — MockRadio's rule (MR-3's `Profile::decimation`), so that every one of UR-9's 512 rates is accepted (Review L, P0-2: an exact-arithmetic reading refused 487 of them, `200e6/3` among them); the SampleClock's ratio is `N / 1`, exact whatever the `f64` rate's last bit (K13's hazard was computing `N` by float division) —, else the configuration is refused (`"UR-12: the device applied <rate> S/s for the claimed <claim>"`, or `"UR-12: <rate> S/s is no decimation 1…512 of 200000000 Hz"`); read-back frequencies and gains are recorded beside the claims in the `applied` section, with their difference, and do not refuse. *Checked by `ur_12_prepare_refusals`, `ur_12_the_applied_values_are_recorded`, `ur_12_a_rate_the_device_does_not_apply_is_refused` and `ur_12_every_advertised_rate_is_accepted`.*
- **UR-13** `arm()` records the arm instant `A = now(root)` and `S = A + startup_latency_ns`; when `clock_source` is not `internal`, refuses with `Rejected` a reference that `ref_locked` reports unlocked (`"UR-13: the <clock_source> reference is not locked"`); opens the receive streamer for the receive channels when their count is > 0 and a link is attached, and the transmit streamer when the transmit count is > 0; and registers the transmit SampleClock, when declared, at the first instant at or after `A` on its lattice (RM-25, TM-13e as KG-14 amends it). It radiates nothing (MA-13). *Checked by `ur_13_arm_cases` and `ur_15_every_clock_starts_on_its_lattice`.*
- **UR-14** The **control thread** `uhd-control`, started by `start`, runs until `stop` a loop that every millisecond drains the `ActionReceiver` with MA-14b's loop, **booking** each Action as UR-21, UR-24, UR-25 and UR-26 say before taking the next: it validates, decides and records what the Action asks and hands device work to its owner — a burst to uhd-tx, a stream switch to uhd-rx or uhd-tx, a timed command to its own release list — and never waits for a device instant (Review J, P1-7). In the same loop it releases held timed commands (UR-24) — a command already inside the release window when it is booked is released before uhd-control takes the next Action (Review K, N-P2-8) —, and every 500 ms it runs UR-27's reference check and reads the device's time (UR-29). The Module's **delivery allowance** (MA-10, KG-8) is 3 ms: the poll period plus the time to book the Actions ahead in the queue; its **device lead**, the lead it needs from receipt, is 2 ms (§3). *Checked by `ur_14_actions_are_finished_before_the_next_recv` (with KC-21a: a `SetParameter` returns after the device call, the fake's `apply` taking 20 ms) and `ur_14_the_control_thread_never_waits_for_a_device_instant`.*
- **UR-15** `start(at)` takes `T0 = at` converted to the root and rounded up (the coordinator always passes `Some`). A `T0` before `S` emits `radio.LATE_COMMAND { key: null, requested: T0, applied: S }` and returns `Rejected` (`"UR-15: the start at <T0> precedes the device's start-up at <S>; the profile needs ezsdr.time.start_lead_ns ≥ 2000000000"`), and no stream starts (MR-11's form). Otherwise, when the receive streamer is open, the receive stream's first segment begins at T0 — on the lattice, KC-15 —: it issues a timed continuous start at T0 (`rx_start(T0)`), so that the first sample is tick 0 at T0, and uhd-rx registers the SampleClock with origin T0 at its first block (RM-25, UR-17); then it starts uhd-rx, uhd-tx and uhd-control — uhd-rx and uhd-tx whether or not their direction has a stream (an owner without a streamer idles), so that every stream a later `cold` change enables has a running owner (Review K, N-P0-1). `start` returns without waiting for T0. *Checked by `ur_15_start_cases` and `ur_15_every_clock_starts_on_its_lattice`.*
- **UR-16** Every thread body runs under `catch_unwind`; a panic is recorded in the `rejected` section and, in uhd-rx or uhd-tx, reported as `DEVICE_LOST` with the message `"a Provider thread panicked"` (MA-9a), because the stream it served is gone. Every join the Provider makes is bounded: 1 s per thread, so that its `stop` and `cleanup` together stay within RS-8a's 5 s step deadline on a healthy device; a thread that does not join in time is recorded in `rejected` and left detached, and then `cleanup` does **not** call `close_streams` for the streamer that thread owns — it records the leak instead — because the thread may still be inside a UHD call on that streamer (UR-3; Review J, P1-8). *Checked by `ur_16_a_panicking_thread_is_a_lost_device`, `ur_16_a_wedged_thread_does_not_wedge_stop` and `ur_16_cleanup_keeps_the_streamer_of_a_detached_thread`.*

### Receive

- **UR-17** uhd-rx carries out its plan (UR-25). It calls `rx_recv(block_len, 100 ms)` in a loop, asking for no more than up to a pending cut; it takes as the cut the later of the cut it was given and the first sample it has not delivered, discards samples at or after that cut, and stops the stream untimed once its samples reach it or it has been silent past it for one block plus 3 ms — the X3x0 ignores a continuous stream's stop time —, recording the stop in `applied` with the cut and the instant it was issued, and ends the clock at the cut. For the next segment it reopens the streamer if the channel count changed, configures the direction with the configuration in effect at the origin (UC-2's projection, held timed commands included), issues a timed start there once configured, and registers the clock at its first block, at or after the origin; when a cut cancels a segment whose timed start is already issued, it stops the stream untimed only after that origin has passed, discarding what arrives; a configuration UR-12 refuses halts the direction (RM-25), with `COMMAND_REJECTED` and UR-12's reason, and uhd-rx begins nothing until uhd-control's plan made without that segment arrives. Under `Provider::stop(abort)` it ends the stream at once at the first sample not yet delivered; under `orderly` at the cut uhd-control books.
  A result's first tick `f` gives the index `k = (f − origin) / N`, rounded to the nearest sample off the lattice (`stats.rx_off_lattice`). A block after the expected index carries `GAP_BEFORE` and `lost` its jump, with the flags UR-18 and UR-19 left pending; one overlapping what was delivered is trimmed (`stats.rx_overlapping`) and dropped if empty; one before its segment's origin or the previous stream's untimed stop is dropped (`stats.rx_before_origin`). Its bytes are SC-4's planar `cf32` from a `HostPool` (HD-2), published as `SampleBlock::new_host` with `direction: rx` and `valid` full to every link (SC-11); a publish not `Accepted` is counted (`stats.link_drops_seen`). A `LateCommand` at a segment's start is a missed origin: `radio.LATE_COMMAND { key: null, requested: origin, applied: T1 }`, a timed start at `T1`, the first lattice instant at or after now plus the start lead, and a first block with `GAP_BEFORE` and `lost` its index, the origin unchanged (SC-18, TM-13b); while a cut is pending it is no missed start, and the stream is stopped untimed.

- **UR-18** An `Overflow { out_of_sequence: false }` is RM-17's overrun: the next block carries `GAP_BEFORE | RESTARTED` with `lost` its whole time jump, and when it arrives `radio.RX_OVERFLOW { cause: overrun, lost, restart_gap_ns: lost · N · 10⁹ / 200 000 000 }` (the jump in nanoseconds) is emitted with time `TimePoint(<receive clock>, e)` (RM-11, UR-20). ### Transmit

- **UR-21** On a `TxBurst` uhd-control refuses with `radio.COMMAND_REJECTED` (RM-13, MR-16's list): a target other than `<id>/tx`; a transmit count of 0; an `at` not in the current transmit SampleClock; a `size_bytes` that is not a positive multiple of `8 · channels`; waveform bytes not in the input store or with a non-finite component; a repeated waveform longer than `repeat_max_samples`; non-empty `metadata`; a start before `S`; a start equal to a held burst's. (A start at or before the open burst's next sample is not refused here: uhd-tx's preemption, below, decides it — Review L, deviation 9.) Otherwise it decides with `LatePolicy::decide(clocks, at, now', 2 ms)`, where 2 ms is the device lead (RM-14 as VE-2 amends it) and `now'` is the first transmit sample at or after the later of its current instant and the transmit clock's origin less the device lead — so that a burst admitted right after a `cold` transmit change, whose clock starts only at its origin (UR-25), is late and not `OnTime` (RM-15 as VE-2 amends it; Review K, N-P0-1). `OnTime` holds the burst at `at`; `SendAsap` moves it to the first transmit sample at or after `now' + 2 ms`, emits `radio.TIME_ERROR { cause: late, outcome: send_asap, late_by_ns, target }` and holds it, with `BurstOpen.late` and `requested_target` as MR-17 sets them; `Drop` and `PlanViolation` do not transmit it and emit `TIME_ERROR` with that outcome. A held burst is handed to uhd-tx. Before its first timed start-of-burst hand-over, uhd-tx repeats the device-lead decision against its current instant: queueing or a host scheduling delay can expire the booking verdict. The same late outcomes, moved-start collision checks and requested-target records apply; an adjacent continuation of an already open device burst has no timed start and follows the preemption rule instead. **Preemption.** A held burst that would start while another burst is open is decided again by uhd-tx when it takes it, between two buffers of the open burst, against the first sample of the open burst uhd-tx has not yet handed to the device — which only uhd-tx advances, so the decision cannot race the hand-over (Review K, N-P1-2): a start before it is late, and the burst's `LatePolicy` applies as above, the event emitted from uhd-tx; a move that would land on another held burst's start refuses the moved burst with `TIME_ERROR { refused }` and `COMMAND_REJECTED` (RM-14's form) (RM-15 as VE-2 amends it; Review J, P0-2). *Checked by `ur_21_txburst_refusals`, `ur_21_late_policies_on_the_device_lead`, `ur_21_an_untimed_send_is_on_time_after_its_delivery` (a Session `radio.send` with no `at`, admitted at `now + 5 ms` by RS-19, received at most 3 ms later with no burst open, is `OnTime` and emits nothing) `ur_21_a_burst_inside_the_in_flight_window_is_late` and `ur_21_a_burst_before_its_clock_s_origin_is_late`.*
- **UR-22** uhd-tx transmits a burst by sending its waveform with start-of-burst and the time spec of its start; a burst without `repeat` ends with end-of-burst on its last samples. A repeated burst is sent again and again from host memory, each repetition without start-of-burst and without a time spec, never with end-of-burst until the burst ends (UR-23); the device receives one contiguous burst, so the wrap has no gap (v3 behaviour 1). Every sent buffer is fed to the Kernel's `BurstTracker` as a transmit block (SC-29), the first with `START_OF_BURST` and `BurstOpen`, so the Manifest's `bursts` section holds SC-28's records; a send that does not complete within 1 s ends the burst (`BurstTracker::stop`), is recorded in `rejected`, and the burst is not resumed; its device burst, if begun, is ended by an empty buffer straight after the samples the device took, and the burst's held last sample (UR-23) is not sent (Review P, NB-1). A send that fails is handled the same way, its device burst taken as begun even on its first buffer, since whether UHD sent packets before the error is unknown (an end-of-burst outside a burst costs one zero sample), and its start counted for the device's report (Review Q, NB-Q1); so is the send of a held sample ahead of the burst that continues its device burst, which abandons that burst rather than play it a sample early (Review Q, NB-Q2). An underflow or sequence-loss report also abandons the currently open device burst, conservatively including a pending continuation: the nominal sample timeline no longer bounds actual playback. Its held tail is discarded, an empty end-of-burst closes the device burst, a still-open Kernel burst ends with `BurstTracker::stop`, and `rejected` records the recovery reason; independent future held bursts keep their reservations and undergo UR-21 at dispatch. Before sending another untimed buffer or a continuation, uhd-tx also abandons a timeline whose next sample is already before its current instant, even if the asynchronous report has not arrived. It never resumes payload on that expired timeline. Between buffers, and while idle, uhd-tx reads the device's asynchronous reports (`tx_async` with a zero timeout; UR-28). *Checked by `ur_22_repeat_is_continuous_across_the_wrap` (on `FakeDevice`, which records a restart for a start-of-burst inside a burst: the received loopback holds the waveform back to back for three wraps, no restart is recorded, and the burst record counts the wraps), `ur_22_a_single_burst_ends_with_end_of_burst`, `ur_22_a_send_cut_short_ends_the_device_burst_after_what_it_took` and `ur_22_a_first_send_cut_short_keeps_the_reports_paired`.*

A Kernel burst's end is not at once the device burst's: while a burst could still be booked at its next sample, its last sample is held back from its last buffer, so that a burst booked there after that buffer went out still continues it (Review N, B3: the last buffer goes out up to the in-flight window before the end, and admission needs only the 5 ms lead); when no burst is booked there by the time that sample is a device lead (2 ms) away, or another burst is next, the held sample is sent with end-of-burst, before the device runs dry (the X300 underflows otherwise); when a burst is booked there, it is sent without end-of-burst ahead of that burst's first buffer. INFERRED: that one sample of gap suffices at every rate — the bench measured it at 1 Msps; the FPGA checks a timed start only after a cycle in `ST_IDLE` (`radio_tx_core.v`), so at 200, 100 or 66.7 Msps a gap of 1–3 samples may be late too (Review N, N1; Phase 8 measures). uhd-tx keeps at most the in-flight window, 10 ms, of samples handed to the device ahead of its time, pacing itself with `now(root)`, so that a burst stopped at instant `s` ends no later than `s + 10 ms`; its record's end is the last sample actually handed over (RM-16 as VE-2 amends it). *Checked by `ur_23_a_burst_ends_at_the_next_bursts_start` (the next burst 20 ms ahead, outside the window; one device burst: one start-of-burst, one end-of-burst), `ur_23_a_burst_booked_at_a_sent_burst_s_end_continues_it`, `ur_23_a_stop_while_the_device_burst_waits_for_a_continuation_ends_it`, `ur_23_a_burst_alone_is_ended_before_it_runs_dry`, `ur_23_a_burst_one_sample_after_a_burst_is_played`, `ur_23_a_one_sample_burst_booked_ahead_starts_at_its_time`, `ur_23_two_bursts_back_to_back_loop_back_whole`, `ur_23_a_continuation_whose_held_sample_is_not_taken_is_abandoned`, `ur_23_a_continuation_s_first_send_that_takes_nothing_ends_the_device_burst`, `ur_23_bursts_go_out_in_target_order` and `ur_23_a_stop_ends_the_burst_within_the_in_flight_window` (a margin of 20 ms, so that the fake's 50 ms acceptance cannot pass it); `FakeDevice` counts a timed start-of-burst sent inside an un-ended burst, and the first and `ur_21_a_burst_inside_the_in_flight_window_is_late` assert none.*

### Parameter updates

- **UR-24** A `hardware_timed` update — `radio.{rx,tx}.frequency_hz`, `radio.{rx,tx}.gain_db` — to `<id>` takes effect at `e`: `at` converted to the root and rounded up when present, otherwise the current instant plus the 2 ms device lead (UC-6 as KG-8 amends it). An explicit deadline that cannot be converted or rounded within the root range is refused with `COMMAND_REJECTED`; it is never treated as an omitted deadline. An `at` closer than 2 ms ahead is late: `radio.LATE_COMMAND { key, requested: at, applied: now + 2 ms }` and `e = now + 2 ms`. **Holding and release.** uhd-control does not hand a timed command to the device at receipt: UHD's command queue is in order and back-pressures ("A timed command will back-pressure all subsequent timed commands", §2), so a command far ahead would hold every later one behind it and could block uhd-control inside UHD (Review J, P1-6). A command whose `e` precedes a command already released is applied late: at the released command's instant, with `LATE_COMMAND`, so that the device queue's order is the effective order (UC-2). The timed stream commands of UR-17 (a segment's start at its origin, and a restart) are issued by uhd-rx, which owns them, when it performs them, about a start lead (50 ms, the profile's `start_lead_ns`) ahead; uhd-rx hands the device no timed stop (UR-25). ## 5. Decisions

| # | Decision | Choice | Rejected (one line each) | Ceiling / upgrade path |
|---|---|---|---|---|
| U1 | The device boundary | One trait, `Device`, with ticks only; two implementations (UR-2, UR-3, UR-33) | Calling the C API from the Provider directly (no test without hardware); a trait per direction (the Authority and both directions share one device) | A second backend (SoapySDR, a C++ shim) implements the same trait |
| U2 | Threads | Three per Provider — control (books Actions, never waits for a device instant), rx and tx (each owns its streamer and performs its own switches; tx also reads the asynchronous reports) — and one in the Authority, `uhd-clock` (UR-3, UR-7, UR-14…UR-28) | One thread doing everything (a blocking `send` would stall the receive path and the Actions); a separate async thread (the first draft: it shares the transmit streamer, whose reopen it would race — Review J, P1-7); switches on the control thread (it would block later Actions beyond the delivery allowance, P1-7) | none |
| U3 | `tx.repeat` | Streamed from host memory (UR-22) | RFNoC Replay (§35: device memory, alignment, a graph; no Phase 7 need) | Replay as a capability in a later version |
| U4 | `now()` | Extrapolated from an anchor re-read every 100 ms by `uhd-clock` and at every wakeup nap (UR-7) | Reading the device at every `now()` (a control-port round trip per call, and the coordinator calls `now` often); re-anchoring only in wakeups (the first draft: between client calls the extrapolation runs on the host clock alone, and at UR-8's own 1e-4 bound twenty idle seconds use up the 2 ms device lead — Review J, P1-4) | none |
| U5 | When the device's time is set | When the Authority is built, before the Run (UR-7) | At `arm` (the Run's T0 would depend on a PPS wait inside `arm`, and the root would not exist during `validate`) | Multi-device sets time on every device at one PPS |
| U6 | `cold` changes | The clock bookkeeping while the Action is carried out; the device switch at the cut and the new origin, a start lead later (UR-25) | Everything at the Action's receipt (the change could not be timed); the bookkeeping at the switch (the next admission would race it, spike K5) | Phase 8 measures the start lead |
| U7 | A transmit in-flight window | 10 ms, with the preemption bound it implies stated (UR-21, UR-23; RM-15, RM-16 as VE-2 amends them) | Unbounded (a `Stop` would leave seconds on air); none (underflows); 10 ms with the preemption unstated (the first draft: a burst preempting a repeat within 10 ms would be dropped by the device as late while its record claimed it on time — Review J, P0-2) | Phase 8 measures the least window without underflow |
| U13 | Timed commands | Held host-side in effective-instant order and released 3 ms ahead (UR-24) | Issued at receipt (the first draft: UHD's in-order, back-pressuring queue lets a far-future command delay every later one and block the control thread — Review J, P1-6) | B8 measures the device queue's capacity for UBX tunes |
| U14 | Enabling a stream at runtime | Configures the direction in full, as `prepare` does, before its clock starts (UR-12, UR-25) | Opening the streamer only (the first draft: the X310 would transmit with whatever frequency and gain it was left at while RM-19 judged the configured ones — Review J, P0-3) | none |
| U8 | Alignment failures | A whole-stream gap and `ALIGNMENT_ERROR` (UR-19) | Per-channel `ALIGNMENT` (UHD never delivers part of a channel set) | none |
| U9 | Which errors mean a lost device | IO, USB, OS and RUNTIME errors on a streaming call, and 1 s of silence while streaming (UR-29) | Every error (a transient `recv` error would abort the Run); none (the Run would go on without its device) | B9 checks; a later version refines the list |
| U10 | Values and versions | `x310-ubx` 0.2.0 = `x310-like` 1.2.0's X310 values except the lead and the repeat constraints; Module 0.3.0 (UR-9) | New guesses of our own (two unmeasured profiles that disagree); 1.0.0 (claims a verified envelope) | Phase 8 measures, and the profile becomes 1.0.0 |
| U11 | Sample formats | `fc32` on the host, `sc16` on the wire (UR-3) | `sc16` on the host (the Radio Model's receive contract is `ezsdr.stream.cf32`, RM-2; a conversion Processor would be needed); `sc8` (halves the transport and the precision; §34 makes it a PerformanceEnvelope choice for later) | A wire-format selector key later |
| U12 | Instances and devices | One fragment per instance, one device per Run (UR-12; overview T13) | Two resources on one USRP (MR-7's refusal applies for the same reason: one stream per direction) | Multi-device after Phase 8 |
