## 1. The three parts

- **EA-1** The Easy API has three parts. The **server** `ezsdr-server` (crate `crates/ezsdr-server`) is the Runtime: it compiles the Modules in (Vision §62), builds each Run's `Assembly`, and drives one Session through the Kernel's `RunHandle`. The **protocol** `ezsdr.protocol` 2 carries the Kernel's own documents — `SessionAction`, `LogEntry`, `Event`, `Manifest`, `TimePoint`, `Duration`, `Lease`, BindingProfile and ExperimentSpec documents — between a client and the server. The **Python package** `ezsdr` (directory `python/`) is a client: it spawns the server, names Radio Model keys in Python terms and composes a capture from protocol requests. The Python package holds no Run semantics: every change it asks for is a `SessionAction` the Kernel admits and logs, and every advance of time is the server's (Vision §3: "nothing bypasses the log"). *Checked by the Python carriers of [`plan/phase6/00-overview.md`](../plan/phase6/00-overview.md) §8; the ones that read logged entries back are `test_v3_parameters_through_attributes`, `test_v54_a_sweep_of_child_runs`, `test_v57_repeat_then_capture_in_software`, `test_v58_13_the_session_manifest_is_written_and_complete` and `test_v58_16_a_rejected_call_raises_and_is_logged`; the rest pin the client's behaviour.*

## 2. The protocol

- **EA-2** **Transport and framing.** The protocol runs over one reliable, ordered byte stream in each direction; in Phase 6 that is the server's standard input (client to server) and standard output (server to client), and the server writes nothing else to its standard output. A **frame** is a header line — one JSON object in UTF-8, with no line feed inside it, terminated by one line feed (`0x0A`) — followed by exactly `body_bytes` raw bytes (none when it is 0). A client's header is `{ "request": <Request>, "body_bytes": <u64> }`, the server's `{ "reply": <Reply>, "body_bytes": <u64> }`; `body_bytes` may be omitted when 0, and an unknown field anywhere is refused (Vision §9). A header longer than 16 MiB is refused. The client sends one request and reads its reply before it sends the next. *Checked by `ea_02_framing`.*
- **EA-3** **Handshake and version.** The first request must be `hello { protocol }`. A server supports protocol 2 only: to `hello { protocol: 2 }` it replies `hello { protocol: 2, server: "ezsdr-server <version>", kernel_api: "<the Kernel API version, MA-2>" }`; to another version it replies the error `unsupported_protocol` with `supported: [2]` and exits; to any other first request, including a first frame that does not decode, it replies the error `protocol` and exits (Review I, P1-B). A later protocol version is a new integer, and a server that speaks several lists them (Vision §9: refused, never reinterpreted). *Checked by `ea_03_handshake`.*
- **EA-4** **Requests and replies.** After `hello`, the requests and their replies are:

  | Request | Body | Reply | Rule |
  |---|---|---|---|
  | `connect { profile?, lease?, initial? }` | — | `connected { run, now, start_instant, dir, profile, effective, root_rate, root_epoch, streams, channels }` | EA-10 |
  | `submit { action }` | the waveform, if the action carries one | `submitted { entry, refused, now, events }` | EA-11 |
  | `advance { to? , by? }` (exactly one) | — | `advanced { now, events }` | EA-12 |
  | `wait_for { kinds, from, within? , until? }` (exactly one) | — | `waited { index?, event?, now, horizon, events }` | EA-12 |
  | `events { from }` | — | `events { events, next }` | EA-12 |
  | `status {}` | — | `status { run, state, now, root_rate, effective, events, sample_clocks }`, where `root_rate` is the primary root's nominal rate in ticks per second as `{ num, den }` (`ClockRegistry::nominal_rate`) (Phase 7, VE-6) and `sample_clocks` the SampleClocks registered so far, in registration order (`ClockRegistry::sample_clock_records`, TM-13a) | EA-12 |
  | `read { uri }` | — | `read { size }` | EA-13; the reply's body is the bytes |
  | `run_child { spec, profile?, inputs, duration_ns? }` | the inputs' bytes, concatenated in the order of `inputs` | `ran { entry, manifest?, path? }` | EA-14 |
  | `finish {}` | — | `finished { manifest, path }` | EA-15 |

  `events` in a reply is the number of events the Run has delivered so far, the index the next one will take. `connect` is valid once, after `hello`, until a `connect` succeeds; every other request needs a connected Session. *Checked by `ea_04_requests`.*
- **EA-5** **Errors.** A request that cannot be carried out gets `{ "reply": { "error": { "kind", "message", … } } }` and changes nothing, except as noted. The kinds are: `protocol` (a header that is not a valid frame, an unknown request, a body of the wrong length, a request out of order, a negative `Duration` (EA-12)); `unsupported_protocol` (EA-3); `refused` (a `connect` or `run_child` whose documents the Kernel or the server refuses before a Run exists, with the Kernel's reason; a `connect` may be retried); `malformed` (`RunHandleError::Malformed`); `ended` (`RunHandleError::Ended`, with the `termination`); `not_on_primary_root`; `not_found` (EA-13); `io` (the server could not read or write a file). The server frames first and decodes second: a header line that is a JSON object with a readable `body_bytes` (absent means 0) frames the stream, its body is read, and only then is the frame decoded. After a `protocol` error in the framing itself — a header that is not a JSON object, a `body_bytes` that is not a count, a header over 16 MiB, a stream that ends inside a header or a body — the server cannot find the next frame and exits; a frame that does not decode (an unknown request or field, a malformed Kernel document) costs only that request, and after it and any other error the Session is as it was (Review H, P1-1). *Checked by `ea_05_errors`; none named for the `io` kind (a Session directory or a reported artifact that cannot be read or written).*
- **EA-6** **Schemas.** The frame types are Rust types in `ezsdr-server` with generated JSON Schemas committed at `schemas/server/request_frame.v1.json` and `schemas/server/reply_frame.v1.json`, frozen byte for byte by `ea_06_schema_freeze` (regenerated with `EZSDR_UPDATE_SCHEMAS=1`), which says whether a difference is one of shape (OV-12). A Kernel document embedded in a frame has the Kernel's schema; a BindingProfile or ExperimentSpec travels as the JSON document itself, because the Kernel parses the document as sent and hashes it as parsed (KC-1, RS-45). A frame schema's file carries its document major under OV-10 and OV-12, not the protocol's integer: protocol 2's frames are `request_frame.v1.json` and `reply_frame.v1.json` until the v4.0 freeze, after which a breaking frame change makes both a new file major and a new protocol (spec 20, VF-2; issue #40). *Checked by `ea_06_schema_freeze`.*

## 3. The server

- **EA-7** **The catalogue.** The server compiles in and registers exactly: the Vocabularies `radio`, `sim`, `sink`; the Modules `ezsdr.sim-engine`, `ezsdr.radio.mock`, `ezsdr.link.host`, `ezsdr.sink.capture` and `ezsdr.exec.native`; and hands the native Executor the component implementations its embedding supplies (the binary supplies none; a test embedding may supply the Phase 5 responder). `ezsdr_server::assemble(profile, inputs, implementations)` builds a Run's `Assembly` from a BindingProfile document; a binding that names another Module, or a Module the catalogue cannot build from its binding, is refused with its reason. The acceptance rig uses the same function. The catalogue also registers `ezsdr.radio.uhd` 0.4.0 with the Provider and Authority roles (spec 18; spec 20, VF-6; issue #41; spec 21, VG-1; issue #46). For each binding of it the server opens the device named by the selector's `args` with `Config.open_device` — `ezsdr_radio_uhd::open` in the binary, which without the server's cargo feature `uhd` refuses with `"EA-7: ezsdr.radio.uhd: this server was built without UHD; rebuild ezsdr-server with --features uhd"` — and builds the Provider from the binding and that device. A profile with more than one binding of `ezsdr.radio.uhd` is refused (`"EA-7: one USRP per Run in this server (Phase 7)"`). The Authority is the Simulation Engine, or, when `authority` names a binding of `ezsdr.radio.uhd`, that device's Authority (spec 18 UR-6) (Phase 7, VE-5). `Config.open_device: Option<OpenDevice>` (`Arc<dyn Fn(&str) -> Result<Arc<dyn ezsdr_radio_uhd::Device>, String> + Send + Sync>`), `None` meaning `ezsdr_radio_uhd::open`; a test embedding passes a closure that returns a `FakeDevice`; no document can (GZ-9). `assemble` takes it as a fourth argument, and `Config::new(runs_dir)` builds a `Config` with nothing else configured. *Checked by `ea_07_a_profile_naming_an_unknown_module_is_refused`, `ea_07_a_uhd_profile_without_the_feature_is_refused`, `ea_07_a_session_on_the_fake_device`, `ea_07_two_uhd_bindings_are_refused` and every carrier that assembles a Run; none named for the catalogue's exact membership, for a known Module bound in a role it cannot fill, or for the refusal of an Authority that is neither `ezsdr.sim-engine` nor `ezsdr.radio.uhd`.*
- **EA-8** **The Session directory.** The server takes `--runs-dir <path>` (default `ezsdr-runs`, relative to its working directory) and creates in it a fresh directory `session-<pid>-<n>` for its Session, `n` the smallest number from 0 that names no existing entry. The Session's Manifest is written there as `manifest.json` and each child's as `child-<seq>.manifest.json`, `seq` the parent's log entry. *Checked by `ea_08_the_manifests_are_written_to_the_session_directory`; none named for the default `ezsdr-runs` relative to the server's working directory.*
- **EA-9** **The default profile.** `connect` without a profile uses this BindingProfile, with `<dir>` the Session directory:

                 "profile": { "name": "x3xx", "version": { "major": 0, "minor": 1, "patch": 0 } } },

  It is data in the server, not in any client (§58 #10). `Config.default_profile: Option<PathBuf>` names a BindingProfile document that `connect` without a profile uses instead of the built-in default; a file that cannot be read or is not JSON is the error `refused` naming the path, and the document is used as written (its capture Sink's `dir` included). The binary sets it from the environment variable `EZSDR_PROFILE` when that is set and not empty; the library reads no environment variable (Phase 7, VE-5; Review J, P2-2). *Checked by `ea_09_the_default_profile_loops_back`, `ea_09_the_configured_default_profile_is_used` and `ea_09_the_binary_reads_ezsdr_profile`; none named for the configured profile's capture Sink `dir` being used as written.*
- **EA-10** **`connect`.** The server builds the Assembly (EA-7), which refuses a channel name two of the profile's radios give (RM-28), expands `initial` (below) and calls `coordinator::connect(profile, requests, assembly, lease)` (`lease` defaults to `Lease::attached()`; `requests` is RS-12's `InitialRequests`). A `SpecError` is the error `refused`. `initial` (EA-10a) is expanded into `requests` first. If the Run is `Running`, the server advances it to `start_instant()` — T0, the instant its devices start — and replies `connected` with the Run's id, `now`, T0, the Session directory, the profile document it used, `effective()` the primary root's nominal rate, `root_rate`, from which a client counts a `Duration`'s ticks (EA-12; spec 20, VF-2; issue #40), and its epoch, `root_epoch`, the Kernel's `EpochRef` (TM-3), from which a client finds a PPS edge (EA-16). If the Run ended during its pipeline (a stage failed) or on its way to T0 (a fault at instant 0), the server finishes it, writes `manifest.json`, replies the error `ended` with its termination and exits. *Checked by `ea_10_connect_stands_at_t0` (an `arbitrary` epoch in simulation), `ea_07_the_uhd_authority_takes_the_binding_s_sources` (`pps` on the FakeDevice with both sources external, `arbitrary` naming `set_time_unknown_pps` with an internal clock) and `ea_10_a_failed_connect_writes_its_manifest`.*
  `lease`, when given, must be Attached: a Detached Lease is refused with `refused` before the Session directory or any Run exists, because this server ends its Session when its input ends (EA-15) and nothing could adopt it (RS-24). *Checked by `ea_10_a_detached_lease_is_refused` (no directory, and a plain `connect` then connects).*
- **EA-10a** **Initial streams.** `initial` maps a resource name to its streams, `{ "rx": [StreamInit…], "tx": […] }`. A `StreamInit` is `{ number | name, channels, sample_rate?, frequency?, gain?, antenna? }`: one of `number` and `name`, `channels` the logical channels (each an integer, the channel's number, or a string, the name its radio's selector gives it, RM-28), `sample_rate` the stream's, and `frequency`, `gain` and `antenna` objects keyed by a channel of the stream. A key or channel is a number only when it is spelled as a canonical ASCII decimal (digits 0-9 only, no sign, no leading zero, a `u32`); any other legal spelling is a name, and a spelling that is neither (digits only and not canonical, or against the name rule of RM-28) is refused. A direction absent or empty puts all its channels in no stream (RM-30), as does `initial` absent.

  Before the Kernel is entered the server first puts each stream under the radio it belongs to: the radio that owns the channel names the stream mentions, in `channels` and in value keys, whatever resource it was written under, so a stream of names needs no resource of the profile. A stream that mentions no name stays where it was written. It refuses names no radio gives, a name of the other direction, names of two radios, and a channel number or number-valued key beside names of a radio other than the resource it was written under. A stream's own `number` or `name` is a position in the owner's stream list.

  Then, after the Assembly is built and so that no Run exists, it refuses with `refused`: a name that is no radio of the profile, a channel or stream number the layout lacks (`RM-4: no such channel c<n>`, `RM-4: no such stream s<k>`), a channel in two streams or twice in one (a number and a name of one channel included), a stream number given twice for one radio, a stream name given twice (a name is unique across `rx` and `tx` and across radios) or not a name (RM-28's rule), two value keys for one channel, a value for a channel its stream lacks, an entry with both or neither of `number` and `name`, and a value that is not finite. It numbers each stream name with the smallest number its direction does not claim, in request order, writes RM-27's keys into the requests, and returns the numbers in `connected.streams`. `connected.channels` returns each Provider radio's names as `{ "rx": { name: number }, "tx": { name: number } }`, empty for a radio that names nothing. The Kernel judges the rest: EA-10's `ended`.
  *Test:* `ea_09_the_default_profile_connects_with_no_stream`, `ea_10_a_direction_list_is_the_whole_channel_set`, `ea_10_two_streams_and_an_empty_direction`, `ea_10_a_named_stream_gets_a_number_from_the_server`, `ea_10_a_stream_name_is_used_once_across_both_directions`, `ea_10_a_request_the_layout_cannot_meet_is_refused_before_any_run`, `ea_10_a_wrong_typed_initial_is_a_protocol_error`, `ea_10_initial_requests_name_their_resource`, `ea_09_initial_requests_mean_the_same_under_every_profile_source`, `ea_06_connect_initial_is_in_the_schema`, `ea_10_a_named_selector_connects_as_the_unnamed_one_and_the_record_holds_numbers`, `ea_09_a_bad_selector_name_is_refused_before_any_run`, `ea_09_a_name_is_unique_in_the_whole_profile`, `ea_10_a_channel_name_is_resolved_to_its_number`, `ea_10_a_key_is_a_number_only_when_it_is_a_canonical_ascii_decimal`, `ea_10_a_name_that_cannot_be_resolved_is_refused`, `ea_10_a_stream_of_names_goes_to_the_radio_that_owns_them`, `ea_10_a_stream_of_two_radios_is_refused`, `ea_10_connected_carries_the_channel_name_table`.
- **EA-11** **`submit`.** `RunHandle::submit(action, body)` with the body as the waveform when `body_bytes` > 0 and `None` otherwise; the reply carries the `LogEntry`, admitted or rejected (a rejection is a result, not an error: the Kernel logged it). The reply also carries `refused`, the `radio.COMMAND_REJECTED` events that name one of the entry's dispatched Actions by id and exist when the submit returns: a Provider's booking decision is made before it does (a device-paced Run waits for the Provider to book the Action, KC-21a; a stepped Run steps it), so a Provider that refused an admitted Action has its event there. A submit that dispatched an Action and finds the Run no longer Running answers the `ended` error instead (with the termination when the Run is cleaned up): its wait may have returned early, and no refusal is not success then; the entry stays in the log.
  *Checked by `ea_11_submit_returns_the_logged_entry`, `ea_11_a_provider_refusal_is_in_the_submit_reply_on_a_stepped_run`, `ea_11_a_provider_refusal_is_in_the_submit_reply_on_a_device_paced_run`, `ea_11_a_kernel_rejection_and_a_capture_have_an_empty_refused_list`, `ea_11_a_start_of_a_streaming_stream_is_refused_in_the_submit_reply_on_both_kinds_of_run`, `ea_11_a_start_the_line_cannot_represent_is_refused_in_the_submit_reply_with_its_id`, `ea_11_the_refused_list_holds_only_this_actions_refusals`, `ea_11_a_submit_that_dispatched_to_a_run_that_is_no_longer_running_is_ended_not_submitted`, `kg_21a_submit_cannot_complete_before_the_booking_gate_opens` and `kg_21a_a_run_that_ends_while_submit_waits_is_no_longer_running_when_it_returns`.*
- **EA-12** **Time and events.** Durations on the wire are the Kernel's own `Duration` (TM-7; `schemas/duration.v1.json`). `advance { by }` and `wait_for { within }` take a `Duration` whose `domain` is the Session's primary root and whose `ticks` are not negative, added to `now` without rounding; a `Duration` on another domain is refused with `not_on_primary_root` ("EA-12: the duration counts ticks of <domain>, not of the primary root <root>"), as `to` and `until` are, a negative one with `protocol`, and a sum that is no instant with `not_on_primary_root` ("EA-12: the duration does not fit the Run's clock"). `connected` and `status` report the primary root's nominal rate (`root_rate`), from which a client computes the ticks (EA-16). `run_child`'s `duration_ns` counts nanoseconds, converted onto the child's primary root with its nominal rate and rounded up (EA-14). `advance { to }` is `advance_to(to)`; `advance { by }` is `advance_to(now + by)`; `wait_for { kinds, from, within }` is `RunHandle::wait_for(kinds, from, now + within)` (KF-2) (spec 20, VF-2; issue #40). `wait_for { kinds, from, until }` is `RunHandle::wait_for(kinds, from, until)`; the reply carries the index and the event when one matched, and the `horizon` it waited for, which a client that waits again passes as `until` to keep its deadline. `events { from }` is `RunHandle::events(from)` (KF-1). `status` reports the Run's id, state, `now`, the primary root's nominal rate (`root_rate`, Phase 7, VE-6), `effective()` and the event count. *Checked by `ea_12_time_and_events` and `ea_12_status_carries_the_root_rate`, and by `ea_12_a_duration_counts_the_primary_root` and `ea_12_a_duration_is_whole_root_ticks` (spec 20, VF-2; issue #40), and by `ea_12_durations_round_up` (the `ticks` helper rounds a nanosecond count up to whole root ticks, on a 3 Hz root); none named for `run_child`'s horizon `T0 + ticks(duration_ns)` on the child's primary root, or for `until` on another domain (`to` is checked by `ea_05_errors`).*
- **EA-13** **`read`.** The server serves the bytes of an artifact only if its Runs reported it: a `file://` URI that appeared as the `artifact.uri` of a delivered `sink.CAPTURE_WRITTEN` event (VD-1) or among the `artifacts` of a child's Manifest. Any other URI is `not_found`, whatever file it names: a client reads what its Session produced and nothing else. *Checked by `ea_13_read_serves_only_reported_artifacts`.*
- **EA-14** **`run_child`.** The server splits the body into the inputs' bytes by the sizes `inputs` lists and keys each by its `ContentHash`; sizes whose sum overflows or differs from the body are `protocol`, and nothing changes (Review H, P0-3). The child's profile is `profile` when given; otherwise it is the parent's profile document with the `feed` member removed from every binding (decision S6 of the overview). It needs `duration_ns` or a schedule entry `Stop {}` — with no target: a `Stop` for a resource ends no Run (KC-33) — in the Spec, and without either the request is refused before the Kernel sees it (a child with neither would never end: a MockRadio always has a next wakeup); a `duration_ns` that does not fit the child's clock is refused likewise: more than half the tick range, so that T0 — the start lead, on a root that counts from 0 — plus the duration is still an instant. It builds the child's Assembly (EA-7) and calls `RunHandle::run_child(spec, profile, assembly, drive)` (KF-3), where `drive` runs the child with `run_until_end(T0 + duration_ns)` or, with no duration, until it ends. An admitted child's Manifest is written as `child-<seq>.manifest.json` and its artifacts become readable (EA-13); the reply carries the parent's log entry, the child's Manifest and the file's path. A child Manifest that cannot be written is still returned, with no `path`, as EA-15's is: the child has run and the parent's log holds it (issue #38). A rejected child has no Manifest. In a device-paced Session (the server built a UHD Authority for it) the server hands `run_child` an Assembly that holds no Provider, Sink, Executor or Link and opens no device (`catalogue::empty_assembly`; its Authority is a Simulation Engine only because an `Assembly` must hold one), and the Kernel refuses the child before it reads the Assembly (KC-37a, KG-12); the reply is `ran` with the rejected entry (Phase 7, VE-5). *Checked by `ea_14_run_child`, `ea_14_a_child_manifest_that_cannot_be_written_is_still_returned`, `ea_14_a_child_of_a_device_paced_session_opens_no_device` and the Python sweep, and by `v58_09_a_reactor_runs_in_a_child_run_of_a_session` (two inputs split from the body by their sizes and keyed by ContentHash, used by the child's radios and responder) and `ea_14_refusals_before_a_child_runs` (sizes that overflow or differ from the body are `protocol` and change nothing).*
- **EA-15** **The end.** `finish` calls `RunHandle::finish()`, writes `manifest.json`, replies `finished` and exits with status 0; a Manifest that cannot be written is still returned, with no `path` (Review I, P2-7). When its input ends before `finish`, the server calls `disconnect()` (an Attached Lease ends the Run `Stopped { client_disconnect }`, RS-23), finishes, writes `manifest.json` and exits. After the Run has ended by itself (a Policy abort, a failed stage), every request that needs a live Run gets `ended`, and `finish` still returns the Manifest. Every other way the server stops with a live Session — a reply it cannot write, a panic unwinding — finishes it as a disconnect does and writes `manifest.json` (`Drop for Server`; Review H, P0-4). *Checked by `ea_15_finish_and_disconnect` and `ea_15_a_manifest_that_cannot_be_written_is_still_returned`.*
  The binary reads its input on a thread of its own (`serve_watched`), so it sees, while it serves a request too, that its input ends or a read fails with any error but `Interrupted` (which it retries; EBADF and EIO fail); either is the client's departure: it then calls the disconnect signal (KC-36) of the Session's Run and of a child Run it is running, the request in progress returns as for an ended Run (`ended` with `Stopped { client_disconnect }`, a submit as EA-11 says, `run_child` with the child's Manifest), and the server finishes as above. Once its input has ended it serves no further request, one it has already read included, so a request reaches the Run only if the server took it before the end; an input that ends during `connect` before its advance to T0 has returned ends the Run on its way to T0 (EA-10's `ended`), one that ends later gets `connected`, and the Session ends at the next request or at the end of the input. When `finish` and the end of the input overlap, the first end requested stands (KC-32): `Stopped { client }` or `Stopped { client_disconnect }`. A reply write that fails with `BrokenPipe` is the client's departure: the server finishes as above and exits with status 0 and no message, as it does after a read that fails between frames; any other write error still exits with status 1 and its message. `serve` reads on the calling thread, for an input that holds every request (a test's), and sees the end only after the requests before it.
  A read that fails inside a frame (after part of its header or body) is a stream that ended inside it: the Session still ends as a departure and its Manifest is written, and the server answers it as a frame the input cut short (EA-2, EA-5).
  The binary also starts a timer when its input ends or fails: a process still alive `EZSDR_SERVER_FAILSTOP_SECS` seconds later (a whole number, default 60; a value that is not one is a usage error, exit 2) exits at once with status 3, with no cleanup, no Manifest and no message; so does a server that cannot create the timer's thread, at once. The delay is a cutoff, not a bound on cleanup: RS-8a bounds each cleanup step, not the whole cleanup, so a cleanup still running when the delay ends is cut, with no Manifest. The library's `serve_watched` has no timer.
  *Checked by `ea_15_an_input_that_ends_during_an_advance_ends_the_session`, `ea_15_an_input_that_ends_during_a_simulated_advance_ends_the_session_and_nothing_after_it_is_served`, `ea_15_an_input_that_ends_during_a_child_run_ends_the_child`, `ea_15_a_read_error_during_an_advance_ends_the_session`, `ea_15_the_binary_exits_0_when_its_client_closes_both_pipes_during_a_request`, `ea_15_the_binary_exits_with_status_3_after_the_failstop_delay_when_it_cannot_finish` (a server blocked in a reply write nobody reads, the delay set to 2 s), `ea_15_the_watch_calls_every_signal_it_holds_once_and_each_added_after_it_fired`, `ea_15_a_removal_waits_for_a_fire_in_progress_so_the_owner_drops_last`, `ea_15_a_signal_is_removed_when_its_holder_is_dropped`, `ea_15_every_end_of_a_run_removes_its_signal_from_the_watch`, `ea_15_a_connect_after_the_input_ended_ends_on_its_way_to_t0_and_leaves_no_signal`, `ea_15_finish_removes_the_session_s_signal_before_it_finishes_the_run` and `ea_binary_speaks_the_protocol` (a `finish` answered while the input is still open: the reply, then the exit); none named for a write error other than `BrokenPipe`, nor for a read that fails inside a frame.*

  **Channel names.** `sdr.rx_channels` and `sdr.tx_channels` of a radio accept a name, `sdr.rx_channels["loop-rx"]` being the channel its selector names so, from the table `connected.channels` returns; an unknown name raises `KeyError` naming the names that direction has. A stream written with names only may be sent under any resource key (`radio=`): the server moves it to the radio that owns the names (EA-10a).

  **Streams at connect.** `rx` and `tx` set the radio `radio` (default `"radio"`) up: each is a dict from a stream, a number (`int`) or a name (`str`), to an `ezsdr.Stream` or a plain list of channels, and is that direction's whole channel set — a channel it leaves out, and every channel of a direction left out or `{}`, is in no stream (RM-30). `Stream(channels, sample_rate=None, frequency=None, gain=None, antenna=None)` holds a stream's logical channels, each an `int`, its number, or a `str`, the name its radio's selector gives it (RM-28), and its starting values: `frequency`, `gain` and `antenna` are dicts keyed by a channel of the stream, a number or a name, and `sample_rate` is the stream's.

  Before it starts the server the package refuses, with `Error`: a direction that is not a dict, a stream key that is a bool or negative, a name that is empty, only the digits 0-9, or holds `:`, `#`, white space or a control character, a name used twice across `rx` and `tx`, a `radio` that is not a non-empty string or is given with neither `rx` nor `tx`, a stream that is neither a `Stream` nor a list, a channel that is a bool, negative or neither an integer nor a `str`, a channel name that breaks RM-28's rule, a channel in two places (by number or by name), a value for a channel no channel of its stream can be (a number beside names only, or a name beside numbers only, is left to the server, which alone knows whether the two are one channel), a value that is not a finite number (an `antenna` that is not a `str`); the layout's own bounds are the server's (EA-10a).

  **An interrupted call.** A call is interrupted when an exception — `KeyboardInterrupt`, `SystemExit`, a dead server's end of output, a header line that is not JSON or lacks `reply` — ends it while its reply is awaited: during the write of the request, or the read of the reply's header line or body. The package then closes the server's input and output at once and re-raises. That is the client's departure (EA-15): the Session ends, whether the server was inside a request or between two, and every later call raises `ProtocolError`. An error reply (EA-5) is read whole and abandons nothing, and neither does a `reply` that carries neither `result` nor `error`, which raises after the read. The server runs in a session of its own, so a signal to the client's process group, a terminal's Ctrl-C, reaches the client and not the server, which finishes the Session and writes the Manifest. One thing stays outside this: a process that inherited the client's pipes keeps the server's input open, as KL-43 says. A server that is hung after its input ended, or that is behind `ssh` (which the client does not kill), exits by itself through EA-15's timer.

  After such a call `close()` sends no `finish`: it waits for the server to exit (`kill` after 30 s), then reads `<dir>/manifest.json` and keeps it in `manifest` when it can. Otherwise `manifest` stays `None` and nothing is raised: the file is on the server's host, is partial, or was never written because the server was killed or its write failed: once a Session exists, every exit of the server but the timer's (EA-15) writes the Manifest. `close() may be called again. When `close()`'s own `finish` fails, because the server has gone, it waits the same way and reads the Manifest, and raises `ProtocolError` only when none is readable. An interrupted `connect()` ends the server and returns after the server has finished and exited (up to 30 s), with no `Session`; when the server had not yet read the request, there is no Session directory and no Manifest.

  **Seconds.** `after`'s and `sleep`'s `seconds`, the `timeout` of `wait_for`, `capture` and `result`, and `run`'s `duration` are seconds of Run time, `run`'s counted from the child's T0 (EA-14); `None` keeps the meaning a signature gives it (`capture`'s and `result`'s default timeout, `run` without a duration). Before it sends any request — `capture` included, which reads its `timeout` before its own request although it hands it to `result` — the package reads each value as an exact rational `s`, a binary float as the shortest decimal that rounds to it in its own format: a numpy floating scalar as `numpy.format_float_positional(value, unique=True, trim="-")` writes it, so `np.float32(0.001)` is a thousandth; a `float` as `Fraction(repr(float(value)))` — the literal the caller wrote when that has at most 15 significant digits, so `0.0041` is 41 ten-thousandths and not the binary float nearest it; an `int` that is not a `bool`, a numpy integer scalar other than `timedelta64`, a `Decimal` or a `Fraction` as its exact value. A value of any other type — a `str`, a `bool`, a numpy `bool_` or `timedelta64`, a numpy array, `None` where the signature gives it no meaning — raises `TypeError`, and a NaN or an infinity raises `ValueError`. A duration on the Session's clock — `sleep`'s `seconds` and the `timeout` of `wait_for`, `capture` and `result` — goes on the wire as a `Duration` on the primary root, its `domain` that of `connected`'s `now` and its `ticks` `ceil(s · R)`, `R` the `root_rate` `connected` reported; `run`'s `duration` as `ceil(s · 10⁹)` nanoseconds (EA-14). A negative duration raises `ValueError`, and so does one whose count exceeds the most its field carries — 2⁶³ − 1 ticks, 2⁶⁴ − 1 nanoseconds; `after` sends no duration and takes any sign. So `sleep(d)` reaches the instant `after(d)` names from the same `now`, and a timeout ends at the first tick at or after its `s`, on every root; a child's horizon lies at least `s` and less than `s` plus one nanosecond plus one tick of the child's root after its T0, exactly `s` rounded up on the Simulation Engine's 1 GHz root and the X310's 200 MHz root (spec 20, VF-2; issue #40).

- **EA-17** **Samples.** A waveform `x` is a 1-D array (one channel) or a 2-D array of shape `(channels, n)`; it is sent as little-endian `cf32`, channel-interleaved (sample `k` of channel `c` at byte `(k · channels + c) · 8`), which is RM-13's layout and the capture Sink's. `capture(n, at, timeout)` on receive stream `k` finds the recorder whose `feed` starts at this radio's receive port `rx<k>` — the one binding of the Session's profile whose `feed.port` is `{ component: <radio>, port: "rx<k>" }` —, submits `sink.capture` with target `{ output: <recorder> }` and `sink.capture_samples = n` (and `at` when given) and raises `Rejected` on a rejected entry; then waits (`wait_for`) for the `sink.CAPTURE_WRITTEN` or `sink.REQUEST_REJECTED` whose `action` is among its entry's `dispatched` ids (HD-16; spec 27 §3), so the client counts nothing and a request another caller made — a Reactor's, a schedule's, one submitted raw — shifts nothing — within `timeout` seconds of Run time (default `n / rate + 1`, `rate` this stream's effective rate), keeping that deadline across waits; raises `CaptureTimeout` when none arrives and `Rejected` on `REQUEST_REJECTED`; reads the artifact's bytes (`read`); and returns them as `complex64`, of shape `(n,)` for one channel and `(channels, n)` otherwise, the channel count taken from the artifact's `continuity`. When the profile has no such binding, or more than one, `request` — and so `capture` — raises `Error` naming the radio and the bindings it found, before it sends any request, so nothing is logged: the helper never chooses among recorders. A client reads one of several by submitting `sink.capture` naming `{ output: <recorder> }` with `Session.submit` (RS-14) and waiting for the `sink.CAPTURE_WRITTEN` whose `action` is among that entry's `dispatched` ids (HD-16) (spec 20, VF-1; issue #42). An artifact whose continuity spans more than one SampleClock (a restart during the capture, §23) or channel count, or holds a gap, a channel gap or more than one valid stretch on a channel (§23: a gap is a flag and a time jump; Review I, P1-C), is refused with `Error` rather than returned as one array. A request that timed out, or one submitted raw with `Session.submit`, is still served first, so the id, not the order, identifies the capture (Review H, P0-2). A capture starts at `at` when the recorder has not yet received the samples at `at` when the request reaches it, and otherwise at the first sample it receives after the request; the artifact's ContinuityMap says where it started. In the Simulation class the two are the same (the client's calls move the Run's time). On a device-paced Session, whose recorder the data thread steps between calls (KC-46), a capture meant to start at an instant names one ahead of the Run's time — `sdr.rx.capture(n, at=sdr.after(0.05))` —, and `t = sdr.sleep(d)` followed by `capture(n, at=t)` starts at `t` only when the request outruns the device's receive latency (INFERRED for a server on the device's host; bench B7 records it) (Phase 7, VE-6; after Review J, P1-5). *Ceiling:* `samples()` reads `cf32`, the only contract a Phase 6 radio streams. *Checked by `test_v57_repeat_then_capture_in_software`, `test_ea_17_two_channels_round_trip`, `test_ea_17_each_capture_gets_its_own_samples`, `test_ea_17_requests_made_ahead_capture_contiguous_samples`, `test_ea_17_a_capture_keeps_its_first_deadline`, `test_ea_17_a_capture_the_recorder_refuses_raises`, `test_ea_17_capture_at_an_instant`, `test_ea_17_a_capture_across_a_restart_is_refused`, `test_ea_17_a_capture_across_a_gap_is_refused`, `test_after_names_an_instant_ahead`, `test_ea_17_capture_needs_exactly_one_recorder` and `test_ea_17_stream_one_capture_uses_its_recorder` (spec 20, VF-1; issue #42), on the fake device `ea_17_a_capture_ahead_starts_at_its_instant` (the first sample is not before `at`, 1 000 samples in the map; the exact start on a Spec is `uhd_59_receive_capture_starts_at_the_requested_index`'s) and `ea_17_a_capture_at_a_passed_instant_says_where_it_started`, and by `test_ea_17_a_channel_with_no_valid_stretch_is_refused`, `test_ea_17_two_valid_stretches_on_a_channel_are_refused` and `test_ea_17_a_channel_count_change_is_refused` (a hand-built artifact `samples()` refuses: a channel with no valid stretch, one with more than one, and a continuity whose channel count changes); none named for `samples()`'s refusal of a non-empty `channel_gaps`, or of a `valid` list holding fewer entries than the map's channels, or for the default timeout `n / rate + 1`.*

## 6. Decisions

| # | Decision | Choice | Rejected (one line each) |
|---|---|---|---|
| A1 | Frame format | A JSON header line plus a raw binary body | Samples base64-encoded inside JSON (a third larger, and a parse of megabytes of text); a length-prefixed binary header (unreadable in a trace, and one more format); MessagePack or protobuf (an external package on both sides for what JSON and a length do) |
| A2 | Envelope | `{ "request": … }` / `{ "reply": … }` with `body_bytes` beside it, every level `deny_unknown_fields` | The request's fields flattened beside `body_bytes` (serde cannot refuse unknown fields through `flatten`, and Vision §9 wants them refused) |
| A3 | A rejected Session Action on the wire | A normal `submitted` reply carrying the `Rejected` entry; Python turns it into `Rejected` | A protocol error (the Kernel logged it: it is the result the user asked for, and an MCP client may want the entry, not an exception) |
| A4 | What `read` may serve | Only URIs the server's Runs reported (EA-13) | Any file under the Session directory (a user profile may name another capture directory, and the Session directory holds Manifests, not artifacts); any path (a client could read any file the server's user can) |
| A5 | Where Manifests go | The Session directory, `manifest.json` and `child-<seq>.manifest.json` | Only in the replies (a Session's provenance would live only as long as the client's variable); the capture directory (a user profile may place it elsewhere, and the Manifest is the Session's, not the Sink's) |
| A6 | The shape of a capture in Python | `(n,)` for one channel, `(channels, n)` otherwise | Always 2-D (§3's `y = sdr.rx_streams[0].capture(N)` reads as a vector); `(n, channels)` (numpy code indexes a channel as `y[c]`) |
| A7 | Python version floor | 3.9: the oldest the machines at hand run (macOS's `/usr/bin/python3`), with `from __future__ import annotations` | 3.10 or later for `match` and `X | Y` (nothing in the package needs them) |
| A8 | How Python finds the server | `server=`, else `EZSDR_SERVER`, else `ezsdr-server` on `PATH`; a clear error naming `cargo build -p ezsdr-server` otherwise | Building it from Python (a toolchain dependency); a wheel bundling it (packaging is later work) |
