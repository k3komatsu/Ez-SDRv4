## 1. Purpose

Vision §8 and §10 make one separation load-bearing: an ExperimentSpec says what an experiment requires, a BindingProfile says how that requirement is met and what surrounds it, and the same Spec runs in simulation and on hardware because only the profile changes. This document turns that into two envelopes, a generic matcher that knows no radio words, and a pipeline whose stages each have a defined input, output and failure.

Three properties have to survive the encoding. The Kernel must not learn a single Radio Model key, or Finding 7's escape hatch reopens. Placement and environment must be impossible to write in a Spec, or R21's regression returns and a Spec stops being promotable. And a document must be migrated or refused, never reinterpreted, or v3's three configuration formats grow a fourth.

## 2. Evidence

- **v3 grew three configuration formats and a chain of converters.** `v3/source/app.d:103-108` dispatches on a missing `version` key to a v1-to-v2 conversion (`:222-268`), normalises v2 (`:309-330`), and the v2-to-v3 call site is commented out, so a v2 document is normalised and then handed to code that indexes keys the v1 and v2 shapes do not have. Vision §10 states the policy before the first schema exists, and this document implements it.
- **v3's configuration became a small language.** `v3/source/settingfile.d:12-87` detects `CONSTANTS` references and `!COMPUTE(expr)` and re-walks the document until nothing expands; the four-operator evaluator it calls is at `:147-226`. `v3/changelog/v3.0.21.md:5-13` documents the feature. The motivation usually given for it, that users wanted parameter sweeps without duplicating files, is Vision §9's account and is **not** stated in the changelog, which has no background section: treat it as the Vision's reading rather than as evidence from the repository. Vision §9 rejects expressions in the Spec and puts parametrisation in a client-side builder; SB-14 makes the rejection mechanical.
- **v3's protocol version had to match exactly.** `v3/source/tcp_iface.d:22` and `:255-261` drop a connection whose version string is not `"3.0.11"`. Exact-match is one of the two honest options; this document takes the other, migrate-or-refuse, and keeps the refusal explicit.
- **Start-up order was a real failure mode.** `v3/changelog/v3.0.20.md:56-59` records, under a heading that reads "background of the change", that with a shared PPS the devices must be started beginning with the one that sources it or start-up fails, and that v3 answered by letting the user specify the order. Audit Finding 6 attributes this to `v3.0.17.md`, which is about the RFNoC device and does not mention PPS; the confusion is explicable, because `v3.0.20.md`'s own first line reads `# EzSDR v3.0.17`. SB-39 keeps v3's answer and moves it: the order is a property of the plan, derived from explicit edges and Provider declarations, rather than of the operator's memory. (Audit Finding 6 attributes the note to `v3.0.17.md`, which introduces the RFNoC device instead; the correct citation is `v3.0.20.md`.)
- **UHD coerces silently unless you read back.** A request for 19.5 Msps on an X310 is applied as 20 Msps, and UHD documents reading `get_rx_rate()` afterwards. `v3/cpp/uhd_usrp/multiusrp.cpp` prints the actual rate to standard output and nothing reaches the client. SB-44 and SB-46 make the coercion a document.

## 3. Model

```text
ExperimentSpec            intent, portable                BindingProfile        this site, this run
├── requirements          vocabulary majors               ├── bindings          resource -> Provider instance
├── resources             per-direction requirements      ├── authority         which binding keeps time
├── graph                 components and links            ├── placements        islands (with their components), links
├── schedule              actions at relative times       └── environment       namespaced sections
├── outputs               artifacts to produce                 ezsdr.time, ezsdr.rf_path,
├── policies              failure table, coercion policy       radio.rf_envelope, sim.channel, ...
└── extensions            namespaced
        │                                                              │
        └──────────────────────────┬───────────────────────────────────┘
                                   ▼
   validate → plan → prepare → arm         each stage defined in §6
   AdmissionResult   ExecutionPlan   PrepareReport
```

The Kernel reads the envelope and the shapes. Everything inside `requires`, `selector`, `environment` and `extensions` is namespaced content whose meaning belongs to a Vocabulary or to a Module.

## 5. Normative rules

### Identifiers, keys and values

- **SB-1** A name the Kernel reads from a document has one of the grammars of table SB-T0, and the grammar is enforced where the name enters: a document's deserialiser refuses a name that does not match, at any depth and map keys included. A Rust caller cannot build an unparsed name either: a `ResourceId`'s fields are private, and `parse`, `child`, `parent` and its deserialiser are its only constructors. Names are compared as bytes; there is no case folding and no Unicode normalisation. A schema states a type's grammar in its description and carries no `pattern`.

  Table SB-T0 — name grammars:

  | Type | Grammar | Names |
  |---|---|---|
  | `Ident` | `^[a-z][a-z0-9_]*$` | everything named inside one document: resources, components, outputs, ports, bindings, Island executors, `authority`, schedule clocks, fragments |
  | `Namespace` | `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$` | Vocabulary prefixes and ids, `environment` and `extensions` sections, resource, artifact and Executor kinds (`any` included, MA-36) |
  | `Key` | a Vocabulary key `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`, or an Extension key `^ext(\.[A-Za-z0-9_-]+){2,}$`; a key beginning `ext.` is read as an Extension key only | SB-2 |
  | `ModuleId` | `^[A-Za-z0-9_-]+(\.[A-Za-z0-9_-]+)*$`, at most 256 bytes | MA-31, and an Extension key's Module segments (SB-2) |
  | `EventKind` | `^[A-Za-z][A-Za-z0-9_]*(\.[A-Za-z][A-Za-z0-9_]*)+$`: every kind is namespaced, the Kernel's under `ezsdr.` | RS-27 |
  | `DataContractId` | `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$` | SC-2 |
  | `ContentHash` | `^sha256:[0-9a-f]{64}$` | OV-14 |
  | `ResourceId.path` | `^[A-Za-z0-9_.-]+(/[A-Za-z0-9_.-]+){0,15}$`, at most 256 bytes | SB-3 |

  A `Value` map's keys are not names: they are Vocabulary content, ASCII by SB-9a and otherwise unconstrained (SB-4).
  *Test:* `sb_01_every_name_grammar_is_enforced_at_the_document_boundary` (SB-T0's eight types, a map key and a nested port reference); the private `ResourceId` fields by the type definition; none named for the comparison as bytes or for the schemas' missing `pattern`.
- **SB-2** A `Key` is a `Namespace` prefix owned by a declared Vocabulary, followed by a path, or `ext.` followed by a Module id and a path. A Spec has exactly five key positions: a resource's `requires`, a `needs[].requires` under it, an output's `params`, a `policies.coercion` key, and a `schedule` entry's `UpdateParameter`. One iterator over them (`ExperimentSpec::keyed_entries`) feeds both the prefix check and the declaration check. At each position a key is checked against its **owner**, and `validate()` refuses it with `UnknownKeyPrefix` when: its prefix belongs to no Vocabulary the Spec declares in `requirements`; it is an `ext.` key whose Module id, with `ext.` stripped exactly once, names no registered Module; or it is any other key and no registered Vocabulary declares a `KeyDecl` for it (SB-2a, for a declaration with a numbered segment). The constraint or value at the position must then be of that declaration's kind (SB-6), a List or Map judged by its outer kind, else `KeyShape`; a `policies.coercion` key has no value to judge. The Kernel checks the prefix and the value's shape against the `KeyDecl` and never interprets the meaning. A `{component}` schedule target is the one exception: its key is owned by that component's own `ParamDecl` (MA-34), so no Vocabulary prefix is required, no `KeyDecl` is consulted — a missing or fixed `ParamDecl` is never a reason to consult one — and no kind check applies, the component's `schema` staying opaque. `Command` params and a `TxBurst`'s `metadata` are not key positions and need no `KeyDecl`; they keep their own rules (SB-4, RS-44a). An `ext.` key has **no** `KeyDecl` by construction, so the shape check and SB-7's coercion path do not apply to one and the constraint goes straight to the capability match; its Module id must name a **registered** Module. Its segments follow SB-T0's `ModuleId` grammar. A `KeyDecl` also carries the optional `update_class` under which the key may be changed during a Run, absent meaning it may not be. This is where a **Provider** parameter's class is declared, and the only place it can be.
  *Test:* the owner at every position by `sb_02_the_ext_owner_is_checked_at_every_key_position`, `sb_02_unknown_key_prefix_refused`, `sb_02_an_ext_key_needs_a_registered_owner` and `sb_02_needs_constraints_are_checked_against_key_decl`; an unregistered Vocabulary by `sb_11_the_declared_vocabulary_major_is_checked`; the kind by `sb_02_values_are_checked_against_their_key_decl`, `sb_02_a_list_value_matches_only_a_list_declaration` and `sb_02_needs_constraints_are_checked_against_key_decl`; the component exception by `sb_02_a_component_value_is_not_checked_against_the_vocabulary_kind` and `sb_02_one_key_declared_differently_by_two_components`; an `ext.` key at the capability match by `sb_02_an_ext_key_reaches_the_capability_match`, and its segments by `sb_02_an_ext_key_parses_for_every_module_id_grammar`; `update_class` by `rs_52_a_scheduled_update_states_no_class`; the checks in `plan` by `sb_39_plan_reruns_the_structural_checks_and_refuses_a_stale_admission`; none named for `Command` params and a `TxBurst`'s `metadata`.
- **SB-2a** A `KeyDecl` may carry `indexed`, the zero-based position of its **numbered segment**: the declaration then declares every key of its own length whose segments equal `key`'s except at that position, where `key`'s segment — a word of `[a-z]+` — is followed by a decimal index, of one to nine ASCII digits and no leading zero (`c0` is a key, `c01` and `c1234567890` are not). The position lies within `key`'s segments and past the Vocabulary `prefix`'s, and a numbered declaration does not cover its own spelling. Registration refuses a numbered declaration whose position is out of range or on a prefix segment, or whose numbered segment is not a word of `[a-z]+`; and any two declarations that cover one concrete key, which is so when they have the same number of segments and at every position exactly one of these holds: neither is numbered and the two segments are equal; exactly one is numbered and the other's segment is the numbered one's word followed by an index; or both are numbered and the two words are equal; the refusal names both declarations. The key a `KeyShape` refusal names is the concrete key, not the declaration's spelling. `policies.coercion` is keyed by the concrete key, so no policy covers a range of indices.
  *Test:* the lookup by `sb_02a_a_numbered_declaration_declares_the_indexed_keys` and `sb_02a_a_numbered_declaration_matches_only_its_own_fixed_segments`, an absent `indexed` by `sb_02a_a_declaration_without_index_is_an_exact_key`, and an exact declaration of a spelling beside its numbered one by `sb_02a_a_numbered_and_an_exact_declaration_of_one_spelling_coexist`; the registration refusals by `sb_02a_registration_refuses_a_numbered_segment_out_of_range_or_outside_the_path` and `sb_02a_registration_refuses_two_declarations_that_cover_one_key`, their admitted side by `sb_02a_registration_accepts_declarations_that_cover_no_common_key`; SB-2's key positions by `sb_02a_a_numbered_key_reaches_every_key_position` and `sb_02a_the_declaration_s_own_spelling_is_no_key`; the concrete key of a refusal by `sb_02a_a_kind_refusal_names_the_concrete_key` and `sb_02a_a_session_update_reads_a_numbered_declaration_s_class`; `policies.coercion` by `sb_02a_a_numbered_key_resolves_its_policy_by_the_concrete_key`.
- **SB-3** A `ResourceId` is `{ node: NodeId, path }`, the path slash-joined segments of SB-T0's grammar. The path addresses a node of the composite resource tree: `radio` is a bound device, `radio/rx/0` one of its channels. A segment is not an `Ident`. In v4.0 `node` is `LOCAL`. A `ResourceId` therefore carries **no instance qualification**, and a node path is the Provider's own declaration, so `validate()` refuses two bound instances that declare one path. An **instance** is identified by its **binding description** — the `(module, selector, profile)` triple the profile carries: two bindings with equal descriptions name one instance (which is how SB-23 reads a multi-device selector) and must report one `instance().id`, and two descriptions name two instances, whose ids differ and whose trees share no node path. Identity rests on the document and not on assembly-time input, as MA-38's Executor does. One instance bound by two Spec resources is SB-34's case and is not this.
  *Test:* `sb_03_two_instances_may_not_declare_one_node_path`; one description reporting two ids by `sb_3_two_bindings_with_one_description_may_be_two_objects`; the path by `sb_03_resource_path_addresses_a_sub_resource`, `sb_34_sub_resource_binding` and `sb_3_no_provider_node_path_is_reserved`, and its grammar by `sb_01_every_name_grammar_is_enforced_at_the_document_boundary`.
- **SB-4** A `Value` is a `Scalar`, or a list or map of `Scalar`s, and a `Scalar` is `Bool`, `Int`, a finite `Num` or `Str`. The shape is the type: a deeper value or a non-finite number cannot be parsed or built. A map's keys are ASCII strings (SB-9a) and no other grammar is imposed on them: a `Value`'s content belongs to the Vocabulary that declares the key, and the Kernel checks its shape and never its spelling (SB-2).
  *Test:* `sb_04_a_nested_value_is_refused_by_every_deserialiser` (a Spec's schedule entry, a selector, an Action, a `ParamDecl`), `sb_04_a_manifest_refuses_a_nested_value`, `sb_04_a_number_is_finite`, `sb_14_compute_expression_refused`.
- **SB-5** A `Constraint` is one of `Eq`, `Range`, `Set`, `Min`, `Max`, `Present`, and a `CapabilityValue` one of `One`, `Range`, `AnyOf`; their values are `Scalar`s. The shape is the type: a constraint or a capability over a list or a map cannot be written.
  *Test:* `sb_05_constraint_values_are_scalars`.

### Matching

- **SB-6** A constraint is satisfied by a declared `CapabilityValue` as follows. Equality and order are defined once, on `Scalar`, the type SC-2's attributes share. Comparison across `int` and `num` is **exact**: an `Int` is compared with a `Num` as the integer it is, in 128-bit arithmetic and never through an `f64` cast, and two scalars are **one value** iff they are numerically equal — the one relation `Eq`, `Set`, `Range`, `Min`, `Max`, `PartialEq` and SC-2's "identical" all decide by. One value has one canonical form and one hash while |v| ≤ 2^53 (OV-15a). Above that bound a float's canonical text is the shortest decimal that **names the `f64`**, not the number's exact decimal, so canonical-form identity is there neither necessary nor sufficient for equality: `Int(2^60)` and `Num(2^60)` are one value with two forms, and `Int(1152921504606847000)` and `Num(2^60)` are two values with one form. `Eq(v)` by `One(v)`, by a `Range` containing `v`, or by an `AnyOf` containing `v`. `Range{min,max}` by a `One` inside it, by an overlapping `Range`, or by an `AnyOf` with a member inside it. `Set(s)` by any capability value whose possible values intersect `s`. `Min` and `Max` by the corresponding bound. `Present` by the key being declared at all. Every comparison is between scalars of the `KeyDecl`'s kind; a mismatch is `KeyShape`. Whether a value or a constraint's scalars are of a declaration's kind is one rule, `kind_accepts`, shared by `validate()` and admission (spec 06 KC-24 steps 6 and 11): a `Num` declaration accepts an `Int` scalar too, every other pair must be the same kind, and a List or Map is judged by its outer kind. The exact numeric comparison above is a different question and is not this rule.
  A Spec that wants two Runs comparable by hash writes such a value in the key's declared kind.
  *Test:* `sb_06_constraint_match_table`, `sb_06_key_shape_mismatch`, `sb_06_a_capability_of_the_wrong_kind_is_key_shape_in_every_cell`, `sb_06_any_of_checks_later_values_after_a_match`, `sb_6_equality_is_exact_and_the_matcher_agrees`; `kind_accepts` by `sb_02_values_are_checked_against_their_key_decl` and `sb_02_a_list_value_matches_only_a_list_declaration`, and at admission by spec 06's `kc_24_an_admission_refusal_leaves_no_configuration_and_no_action_id`. *Producer obligation:* on the Spec author, the declared kind for hash-comparable Runs.
- **SB-7** When a key's `KeyDecl` says it is coercible, a constraint the declared capability does not satisfy directly is offered to the Provider's `coerce` (spec 05, MA-11). The matcher asks only whether a value can be coerced and what it becomes; it never decides the grid. A key that is not coercible fails immediately, before `coerce` is called at all. `coerce` is called **exactly once** per bound node, with the resource's whole `requires` map, unless a non-coercible key has already failed — **including** when every constraint is satisfied directly. A key the declared capability did not satisfy directly is judged from `applied`. Every entry of `CoerceReport.rejected` whose key the request names becomes a `RejectedConstraint` carrying the Provider's reason (one per key; an entry for a key already rejected replaces that reason); an entry whose key the request does not name is a malformed report and a violation, as SB-44 treats a stray coercion. A coercion the Provider reports for a key the capability satisfied directly is previewed like any other.
  *Test:* `sb_07_coercible_key_consults_provider`, `sb_07_non_coercible_key_fails_directly`, `sb_07_coerce_is_called_once_with_the_whole_request`, `sb_07_coerce_refuses_a_combination` (a call when every constraint is satisfied directly, and the Provider's reason), `sb_07_a_stray_rejection_is_a_violation`; none named for an entry that replaces an earlier rejection's reason, or for a coercion of a key satisfied directly.
- **SB-8** The matcher is generic. It reads no Vocabulary key by name: it compares a constraint with a capability through the key's declared shape (SB-6). The rule is about the matcher, not every Kernel item: the Stream Contract's per-channel validity (SC-14) and a SampleClock's rate (TM-13a) are Kernel concepts.
  *Test:* `sb_08_the_test_vocabulary_names_no_radio_word`: the test Vocabulary declares only `test.` keys, none of them a radio word (`00-overview.md` OV-21).

### ExperimentSpec

- **SB-9** The top level of an ExperimentSpec is the closed set `version, requirements, resources, inputs, graph, schedule, outputs, policies, extensions`. An unknown **top-level** field is `UnknownField { path }`, not a warning. The rule applies at **every object** of every Kernel document, not only its top level: every document type refuses an unknown key (its schema says `additionalProperties: false`). Extension content lives only in the namespaced maps the Kernel names (`extensions`, `selector`, `environment`, `sections`, `Fragment.content`, `ModuleError.detail`); it never adds a key beside a Kernel field. Below the top level the rule is enforced at parse and surfaces as `Structural` whose `reason` is prefixed `SB-9:` (`SB-21:` for a profile) and names the key, e.g. ``SB-9: unknown field `memory_domain` ``; a dotted path is not promised for a nested key in v4.0.
  *Test:* `sb_09_unknown_top_level_field_refused`, `sb_09_an_unknown_nested_field_is_refused`, `sb_14_compute_expression_refused`, `sb_25_an_island_states_each_component_and_its_memory_domain`.
- **SB-10** `version` is a positive integer and is mandatory. Exactly `{1}` is supported.
  *Test:* `sb_10_version_one_validates`, `sb_47_version_two_refused_by_name`; `version`'s presence by `ov_22_schema_freeze` (`required` in `experiment_spec.v1.json`; the schema's `minimum: 0` does not carry the rule's "positive"); none named for `version: 0` or an absent `version`'s envelope refusal.
- **SB-11** `requirements.vocabularies` lists the Vocabulary majors this Spec's keys belong to. It is the only content of `requirements`; the per-resource requirements live in `resources[].requires`.
  *Test:* `sb_11_the_declared_vocabulary_major_is_checked`.
- **SB-12** A `ResourceReq` states `kind` and `requires` and nothing about how the requirement is met. Direction-asymmetric requests are expressed as distinct keys under the Vocabulary's prefix — `radio.rx.channels`, `radio.tx.channels`, `radio.rx.coherent` — not as a single count. ### BindingProfile

- **SB-21** The top level of a BindingProfile is the closed set `version, bindings, authority, placements, environment`, with the same unknown-field rule — including SB-9's split by depth — and the same mandatory integer `version` as a Spec.

- **SB-22** *Bindings and roles.* A Run's roles are read from its two documents, the registry and the Run kind (a Spec Run or a Session), and from nothing else. The documents name every role **slot** the Run has and the binding that fills it; the registry says which roles a bound Module may play; the runtime supplies, under the slots' names, the instances and descriptors the documents named, and what it supplies under any other name is never read. One `bindings` map binds every role. Tables SB-T1 to SB-T4 are normative, and each row names the rule that governs it. SB-T4 says where each rule is checked: parse enforces the grammars and the presence of `authority`; a Session's derivation (SB-22c) refuses a binding it cannot derive; `validate()` checks every other rule of SB-22a…SB-22g and SB-24, and `plan()` runs those checks again through the same functions (SB-39).

- **SB-22a** *One namespace.* The Spec's resource names, graph component names and output ids, and the profile's Island executor names, Island fragment ids and `authority` name, are pairwise distinct, with two exceptions: one executor name may serve several Islands, and `authority` may be a resource name (SB-24). A collision is `DuplicateBindingName`. No name is reserved: a target and an event source carry their role in their type (spec 06, KC-8, KC-23), so `sink` is a name like any other and an output id derives no address. An Island's fragment id is `island_<local>`, with `<local>` its `IslandId.local` in decimal.

  *Test:* `sb_22b_spec_run_slots`.
- **SB-22c** *Slots of a Session.* A Session has no Spec to name its resources, so RS-12's implicit Spec is derived from the profile, binding by binding, by the first row of SB-T2 that applies, and SB-22b…SB-22g then apply to it unchanged. The derivation reads three things — a binding's registered roles, a bound Sink's `artifact_kinds` and a bound Provider's root kind — and refuses a binding only when the row it reaches lacks one of them, in that order, with the error SB-22e or SB-22f would give — or, for a Sink that declares no artifact kind, RS-12's; every other refusal is `validate()`'s. Row 3 is the one place a Module's declared roles **select** a slot rather than only permit it. A Module holding both Provider and Authority that `authority` names is a resource in a Session, and an Authority slot of its own in a Spec Run whose Spec does not name it. A Module that is an Authority and also part of a simulated Provider is therefore bound as the resource and named by `authority`, and the Authority rides on it under both Run kinds.
  *Test:* `sb_22c_session_derivation_table`, `rs_12_a_multi_role_module_is_bound_once_per_role` (the first row that applies).
- **SB-22d** *Exactly the slots are bound.* `bindings` holds one entry per slot name and no other. A slot with no binding is `UnboundResource`, `UnboundOutput` or `UnboundExecutor`, or, for the Authority slot, a refusal naming `authority`. A binding that fills no slot is refused. The profile handed to the Kernel is the one this Run uses: choosing a Run's bindings from a larger shared set is outside the Kernel, and a child Run names its own profile (RS-14, RS-25a).

### The admission-check hook

- **SB-29** A Vocabulary registers an `AdmissionCheck` against an `environment` section: the section's namespace, the stages at which it runs, and a function from the section's content and the effective configuration to a list of violations. The Kernel guarantees that the check runs; the Vocabulary owns what it means. No radio word enters the Kernel, and no Vocabulary can be bypassed.
  *Test:* the registration by `ma_35_vocabulary_carries_its_own_content` (`module_api.rs`); the runs by `sb_30_admission_check_runs_at_three_points` and `sb_30_the_check_sees_each_fragment_s_own_value`.
- **SB-30** The Kernel runs every registered check whose section is present, at three points: `validate()` against the requested configuration, `prepare()` against the applied configuration returned by each Provider, and the admission of every Action before dispatch, whatever its origin (spec 06 KC-24 step 12). At each point the configuration is given **per fragment**, keyed by fragment id (SB-T1), never merged: at `validate`, one entry per Spec resource holding the values of its own `Eq` constraints only (possibly empty) — a need's `Eq` values do not join it (SB-36) — and one per output holding its `params`; at `prepare`, one entry per fragment that returned a `PrepareReport`, holding that report's `effective`; at the runtime point, the coordinator's current per-fragment configuration (KC-27), with `proposed` holding only the target fragment's proposed key and value — for every `UpdateParameter`, whether its target is a Provider, a Sink's output or a component, the value after the coercion when one ran. At the third point the check receives the Action's key and value as `proposed` and evaluates the effective configuration overlaid with it. A non-empty violation list fails the stage, and nothing transmits until every check at every applicable stage has passed. `validate()` **reports**, and `plan()` refuses a non-admitted `AdmissionResult` before it builds anything; `prepare` runs its own point inside `collect_prepare` (SB-41); the runtime point is `Admitter::admit`, called at KC-24 step 12 (Vision invariant 42).
  Rejections and violations are recorded in the Manifest (spec 04 §6).

### Resources and binding

- **SB-33** A Provider instance exposes a composite resource tree (Vision §8, spec 05 MA-10): a device with channels, streams, a timekeeper, GPIO banks, replay memory and sensors beneath it, each a node with its own `ResourceId` and its own declared capabilities. The tree's shape is spec 05's `ProviderInstance`; this rule binds the matcher.
  *Test:* the matcher's walk by `sb_34_sub_resource_binding` and `sb_34_binds_the_sub_resource_that_can_satisfy_the_request`.
- **SB-34** A Spec resource binds to exactly one Provider instance. Its `kind` must match the kind of the instance's root or of one sub-resource, and its constraints are matched against that node's capabilities. Two Spec resources may bind to different sub-resources of one instance. A node is bound by at most **one** Spec resource or `needs` entry (SB-36) unless the bound instance declares it `shareable` (MA-10); a second binding of an exclusive node is refused with `NodeAlreadyBound { node, first, second }`, naming both resources, and is never resolved by sharing. Whether a channel, a timekeeper or a sensor is shareable is the Provider's declaration and not the Kernel's knowledge (OV-21). A free node is preferred over a shareable one that is already bound.
  *Ceiling:* the matcher is greedy and does not backtrack; a bipartite matching is the upgrade if a profile ever needs one.
  *Test:* `sb_34_sub_resource_binding`, `sb_34_two_resources_one_instance`, `sb_34_two_resources_take_different_sub_resources`, `sb_34_binds_the_sub_resource_that_can_satisfy_the_request`, `sb_34_exclusive_node_bound_twice_is_refused`, `sb_34_shareable_node_may_be_bound_twice` (a free node first).
- **SB-35** A requirement that one instance cannot satisfy fails with `NoSingleInstance`, naming the constraint. The Core never assembles a capability across instances: coherence in particular is declared by the Provider that owns the channels and is never inferred (Vision §8, §25). The Kernel holds only the single-instance rule; that a given key means coherence is the Radio Model's business.
  *Test:* `sb_35_no_single_instance`.
- **SB-36** A resource may declare `needs`: named capability requirements it does not own. The matcher resolves each to a sub-resource of an instance bound to one of the Spec's resources — nothing supplied under another name is read (SB-22) — which may be a different instance from the one the resource itself is bound to, and records the resolved `ResourceId` in `AdmissionResult.needs[<resource>][<need>]`; `matched` holds the resources alone. The two maps are recorded in the Manifest, and `matched` is read by SB-15's port resolution. A smart antenna needing a timed GPIO line declares `needs: { gpio: { kind: gpio.bank, requires: { gpio.timing_class: Eq("hardware_timed") } } }` and the Kernel resolves it to a bank of the radio's device. This is not a cross-module dependency: the peripheral knows only the capability, and the Kernel does the resolution (Vision §39).
  *Test:* `sb_36_needs_resolves_across_instances` (and an unresolvable need refused), `sb_36_two_needs_of_the_same_name_do_not_collapse`, `sb_36_a_need_and_a_resource_of_one_joined_name_do_not_collide`, `sb_36_needs_whose_joined_names_are_equal_do_not_collide`, `sb_39_the_guard_covers_every_matched_entry`.

### The pipeline

- **SB-37** Capability matching uses the **bound** instances and follows binding resolution. The checks and refusals at each stage are table SB-T4's.
  *Test:* `sb_37_matching_follows_binding`; the checks and refusals by the rules named in SB-T4.
- **SB-38** `validate(spec, binding, registry) -> AdmissionResult` returns the matched resources, the rejected constraints, the envelope violations, a preview of the coercions and the warnings. It touches no hardware.
  *Test:* the fields by `sb_10_version_one_validates` (`matched`), `sb_07_non_coercible_key_fails_directly` (`rejected`), `sb_30_a_validate_violation_refuses_the_plan` (`violations`), `sb_07_coercible_key_consults_provider` (`coercions_preview`) and `sb_46_validate_applies_the_coercion_policy` (`warnings`); none named for touching no hardware.
- **SB-39** `plan(spec, binding, admission) -> ExecutionPlan` adds the fragments, the DataLink declarations, the dependency edges, the Authority and the derived ExecutionClass. `plan()` does not presume that `validate()` ran: it runs `validate()`'s structural checks, SB-30's first point and its endpoint checks again through the same functions (SB-T4), and it takes from the `AdmissionResult` only what matching produced. It refuses a result that is not admitted (SB-30) or not this Run's — one with no matched node for a Spec resource or for one of its needs, with a resource's matched node its bound instance does not declare, with a need's matched node no instance bound to the Spec's resources declares (SB-36), with a `matched` key that is not a resource of the Spec, or with a `needs` entry that is not a need of its resource. `collect_prepare` applies the same guard. The guard reads all of `matched` and all of `needs`. A Provider fragment's `content` is `{ selector, requested }`, where `requested.resource` is the node the matcher bound (SB-34) and `requested.constraints` is what the Spec asked of that resource; a Sink fragment's `content` is its `OutputReq`, a Session's implicit one included (SB-22c); an Island fragment's `content` is its `IslandDecl`. Dependency edges come from the explicit `ezsdr.arm_order` section and from each Provider instance's declared `arm_after`. A cycle is `ArmCycle`. The `ezsdr.arm_order` section, when present, is an **array** of `{ before: Ident, after: Ident }`, each naming a fragment of this plan. A section that is not an array, an entry lacking either field or carrying a non-string, and an edge naming a fragment the plan does not have are each **refused rather than skipped**. A Provider's `arm_after` entry naming an instance this profile does not bind contributes no edge. A fragment's id is its slot's name, or `island_<local>` for an Island (SB-T1). Fragments with no edge between them are ordered by their `Ident`.
  *Test:* the checks run again and a stale admission by `sb_39_plan_reruns_the_structural_checks_and_refuses_a_stale_admission`; a result not admitted by `sb_30_a_validate_violation_refuses_the_plan`, and one that is not this Run's (an empty `AdmissionResult`) by `sb_39_plan_refuses_an_admission_result_from_another_spec`; the guard by `sb_39_the_guard_covers_every_matched_entry` and, in `collect_prepare`, `sb_30_prepare_refuses_an_admission_result_from_another_spec`; the contents by `sb_39_a_provider_fragment_carries_the_matched_request` and `sb_39_a_sink_and_an_island_fragment_carry_their_declarations`; the links by `sb_39_the_plan_records_the_contract_the_link_actually_carries`; the edges by `sb_39_arm_order_follows_edges`, `sb_39_arm_after_from_the_provider_declaration`, `sb_39_arm_cycle_refused`, `sb_39_a_malformed_arm_order_entry_is_refused` and `sb_39_two_islands_on_one_executor_is_not_a_cycle`; an `arm_after` naming an unbound instance by `sb_22_the_runtime_is_read_only_under_slot_names`; the fragment ids by `sb_22b_spec_run_slots`; the needs' resolutions planned by `sb_36_needs_whose_joined_names_are_equal_do_not_collide`.
- **SB-40** The Core neither measures nor uses transfer costs: the placement is the BindingProfile's (SB-25), and the Core never chooses one (Vision §20, §31, §63). The plan has no transfer-cost field; a declared cost returns only with a rule that reads it.
  *Test:* `sb_40_the_plan_carries_no_transfer_costs`.
- **SB-41** `prepare(plan, ctx)` calls each fragment in plan order (KC-12), which is dependency order, and collects one `PrepareReport` per fragment, each filed under the fragment it was called for: `collect_prepare` takes `(fragment, result)` pairs, so a report carries no fragment of its own and an error names the fragment that returned it (`PrepareError::Fragment`). Plan order is the plan's `fragments`. The reports are `prepare`'s one result, and no merged configuration is built from them. The **per-fragment configuration** `{ fragment: report.effective }` is what the Kernel judges and serves: SB-30's second point gives it to every check, KC-27's configuration, which `RunHandle::effective()` returns, starts as it, and the Manifest's `prepare` section records the reports (KC-45). A report carries the effective configuration, the coercions and any warnings. A lifecycle fragment with no report fails `prepare` (SB-42); an Authority fragment has no lifecycle (MA-2) and supplies no report. `prepare` also runs SB-30's second point — every registered check, over the per-fragment configuration — before it returns; a violation fails `prepare` (SB-42). It also runs MA-12's two obligations there: each `effective` value is checked against the bound node's declared capability for narrowing, and the Spec's own constraints are re-matched against it.
  *Test:* the order by spec 06's `kc_12_a_prepare_failure_stops_the_loop_and_cleans_up_what_was_prepared`; the filing by `sb_41_the_reports_follow_plan_order` and `sb_41_a_report_is_filed_under_the_fragment_invoked` (`coordinator.rs`); `collect_prepare` by `sb_41_prepare_reports_one_per_fragment`, `sb_41_a_resource_with_no_report_is_refused` and `sb_41_sink_reports_are_required`; the checks' per-fragment input by `sb_30_the_check_sees_each_fragment_s_own_value` and `sb_30_prepare_runs_the_checks_against_the_applied_configuration`; MA-12's two obligations by `ma_12_a_widening_effective_is_refused_at_prepare` and `ma_12_two_resources_naming_one_key_do_not_refuse_each_other`.
- **SB-42** Any fragment's failure fails the whole transaction, and the Run moves to cleanup (spec 04, RS-3), which releases in reverse dependency order (RS-8).
  *Test:* `sb_42_fragment_failure_fails_the_transaction`; the Run's cleanup order by spec 06's `kc_13_arm_and_start_follow_instance_order_cleanup_reverses_it` and, in `run_session.rs`, `rs_08_cleanup_runs_in_reverse_dependency_order`; with spec 04, `rs_03_failure_at_each_stage_reaches_cleanup` (`run_session.rs`).
- **SB-43** `arm` is the coordinator's (KC-14…KC-19): it fixes T0, resolves every entry, refuses an ambiguous or unresolvable one, and dispatches each resolved Action at start or at its instant. `arm` fixes what could not be fixed earlier: each transmit stream's SampleClock origin (TM-13e) and each `SpecTime`'s resolution to an `AbsoluteDeadline` (SB-16). A burst target's conversion onto the transmit sample grid (SC-23a) therefore happens at the first admission point after `arm`; the plan-time check of a statically known lead compares durations only, which TM-21 does from the nominal rates fixed at `prepare` and which needs no origin.
  *Test:* spec 06's `kc_15_t0_is_arm_end_plus_the_lead` (KC-15), `kc_16_a_spec_time_resolves_on_the_target_stream` (KC-16) and `kc_18_a_start_failure_is_failed_arm` (KC-18); an ambiguous or unresolvable entry by `kc_16_an_ambiguous_spec_time_is_refused` and `kc_16_off_root_negative_and_overflowing_times_are_refused`; the template with no time field by `sb_16_spec_time_resolves_at_arm`.

### Coercion and versioning

- **SB-44** A `Coercion` records the key, the requested value, the applied value and the Provider's reason. A Provider's `prepare` must report the same coercions its `coerce` reported for the same request (spec 05, MA-12), and "the same request" is literal: SB-7 calls `coerce` with the same whole map a fragment carries. A `Coercion` whose key is **not** in that request is a malformed report and fails the fragment (SB-42); a Provider choosing its own default belongs in `effective`, where MA-12's narrowing rule judges it.
  *Producer obligation:* on the Provider, tested from the Module side in spec 05. *Test:* from the Kernel side by `ma_12_prepare_matches_coerce` and `ma_12_prepare_that_disagrees_with_coerce_is_visible` (`module_api.rs`), which call `prepare`, and by `sb_44_a_coercion_is_charged_only_to_the_resource_it_was_computed_for`, `sb_44_a_provider_may_not_exempt_a_key_by_declaring_a_coercion`, `sb_44_a_coercion_of_an_unrequested_key_is_refused_at_validate`, `sb_44_a_coercion_of_an_unrequested_key_is_refused_at_prepare` (the `prepare`-stage refusal, on a report whose coercion names a key the request does not) and `sb_39_a_provider_fragment_carries_the_matched_request`.
- **SB-45** The coercion policy for a key resolves in this order: the Spec's `policies.coercion` entry; then, for a Session, `warn`; then the key's `coercion_default` from its `KeyDecl`; then `warn`.
  *Test:* `sb_45_coercion_policy_chain`, `sb_44_a_coercion_of_an_unrequested_key_is_refused_at_validate`.
- **SB-46** Under `reject` a coercion fails the stage with `CoercionRejected`. Under `warn` it is applied, recorded and warned. Under `accept` it is applied and recorded. In all three cases it appears in the PrepareReport and in the Manifest, and under `warn` the warning goes on that fragment's `PrepareReport.warnings` at `prepare` as it goes on `AdmissionResult.warnings` at `validate`. A key the **Kernel's own preview** recorded a coercion for is not re-matched against the requested constraint by MA-12, and what is checked for it instead is SB-44's obligation — that the value applied is the one `coerce` returned. The exclusion may not be keyed on the report's own `coercions`. The division is: a **declared** change is this rule's, an **undeclared** one is MA-12's, and a Vocabulary that wants a key refused sets `coercion_default: reject` (SB-45).
  *Test:* `sb_46_an_accepted_coercion_survives_prepare` (`accept`, and the exclusion keyed on the Kernel's preview); `reject` and `warn` at `validate` by `sb_46_validate_applies_the_coercion_policy` and at `prepare` by `sb_30_prepare_runs_the_checks_against_the_applied_configuration`; `sb_45_coercion_policy_chain`, `sb_44_a_coercion_is_charged_only_to_the_resource_it_was_computed_for`, `sb_44_a_provider_may_not_exempt_a_key_by_declaring_a_coercion`; none named for the `CoercionRejected` error itself.
- **SB-47** A document whose `version` is not supported is refused with `UnsupportedVersion`, naming the version found and the versions supported. It is never interpreted under a newer version's defaults.
  *Test:* `sb_47_version_two_refused_by_name`.
- **SB-48** *Withdrawn.* A later major refuses an older document under SB-47; the Kernel has no migration registry.
- **SB-49** *Withdrawn.* With no migration, the Manifest records no original version or hash.

## 6. Decisions

| # | Decision | Choice | Rejected (one line each) | Ceiling / upgrade path |
|---|---|---|---|---|
| B1 | Constraint vocabulary | The six of audit Finding 7, over scalars only | A general predicate language (Vision §9's ban on expressions applies to the BindingProfile too); constraints over lists (the matcher would need Vocabulary semantics to compare them) | A Vocabulary needing set-of-sets logic registers an `AdmissionCheck` instead |
| B2 | Direction asymmetry | Distinct flattened keys under the Vocabulary prefix (SB-12) | A Kernel-level `rx`/`tx` split (a radio word in the Kernel, Finding 7); a single `channels` count (re-review R1's regression) | The Kernel cannot check that `rx` and `tx` are consistent; that is the Radio Model's `AdmissionCheck` |
| B3 | Forbidding placement in a Spec | A field-name scan at any depth outside `extensions` (SB-13; corrected 2026-10-13: and any `schema`, D19, D30) | Trusting the schema (a Spec could carry placement inside a Vocabulary section and still validate); allowing it with a warning | A Vocabulary could still smuggle placement into `extensions` (corrected 2026-10-13: or into any `schema`, D30); that is visible in the Manifest and is the Vocabulary's defect |
| B4 | Schedule times | A resource-relative offset resolved at `arm` (SB-16, SB-43) | A `ClockDomainId` in the Spec (domains are allocated at `prepare`, so the Spec would not be portable); wall-clock times (TM-1) | An offset is from the Run's start only. An absolute device time in a Spec is deliberately not expressible, which means v3's `onTime` — one of Vision §61's four behaviours worth a regression test — is testable on the Session path, where a `Vocabulary` action carries an `at` beside its params (spec 04, RS-19), and not on the Spec path. |
| B5 | RF envelope enforcement | A Vocabulary-registered `AdmissionCheck` the Kernel is obliged to run at three points (SB-29, SB-30) | The envelope's fields in the Kernel (Vision §52 read literally, but Finding 17 puts the schema in the Radio Model); enforcement left to the Provider (Vision §52 makes it a Kernel policy, and a Provider could skip it) | A check is pure and cannot consult hardware; a site limit that needs a measurement is a Provider constraint instead |
| B6 | Arm ordering | Explicit edges plus Provider-declared `arm_after`, cycle refused, ties by name (SB-39) | Inferring order from the resource tree (the PPS relationship is not in the tree); operator documentation, which is what v3 had | No automatic ordering; a missing edge is a start-up failure the plan cannot predict |
| B7 | Versioning | A mandatory integer major, supported set `{1}`, refusal implemented (SB-47) | A semver string for *documents* (a document has one dimension of compatibility, so a minor and a patch would be decoration). Module and Vocabulary versions are a different matter and do carry minor and patch, as `Binding.profile.version` and the Manifest's `modules[].version` show, and Vision §59 bumps a Mock profile's version on measurement; spec 05 owns that type; v3's exact-match (correct but leaves no upgrade path); silent reinterpretation | One major at a time; a later major refuses an older document |
| B8 | One instance per resource | The Kernel holds only the rule; which key means coherence is Vocabulary (SB-34, SB-35) | The Kernel understanding coherence (Finding 6 forbids it); allowing a resource to span instances (Vision §25) | A genuinely multi-instance requirement must become one Provider instance, which is what `addrs: [a, b]` is |
| B9 | Transfer cost | Not in the plan: the Core neither measures nor uses transfer costs (SB-40) | Declaring a cost the Kernel reports (nothing read it, and a declared number can be wrong); measuring it in Phase 1 (nothing to measure yet); using it to rank placements (Vision §63 rejects an optimiser) | A user who needs a cost measures it outside the Core |

## 9. Vision issues found

1. **§9's tree lists both `requirements` and per-resource `requires`** without saying how they differ. SB-11 divides them: `requirements` declares the Vocabulary majors, which is what SB-2's prefix check needs, and `requires` holds the constraints.
2. **§8's simulation example writes `instances: 2` under one binding**, which contradicts SB-34's one-instance rule if read as two Provider instances. SB-23 reads it as selector content, mirroring the laboratory example's comment that `addrs: [a, b]` is one instance. MockRadio declares a channel layout instead of that key now (design 33 D5), the example staying an illustrative shape.
3. **§8's environment examples use bare keys** (`time:`, `channel:`, `rf_envelope:`) where two Vocabularies would collide. SB-26 makes the normative form namespaced; the examples are illustrative shapes, which the Vision's index already says of every `{ ... }` block.
4. **§52 says the Kernel enforces the RF envelope as a Kernel policy while audit Finding 17 puts its schema in the Radio Model.** Reconciled by SB-29 and SB-30: the obligation to run the check is the Kernel's, the content is the Vocabulary's.
5. **§11 says a PrepareReport per fragment and §52 says "the PrepareReport".** SB-41 produced both until spec 20's KH-1 removed the merged configuration; the reports are now its one result (spec 20, KH-1; issue #43).
6. **§52's list of what validation "may determine" includes "performance risks" and "selected fallback strategies"**, which are not testable as written. Phase 1 implements exactly the `AdmissionResult` fields of SB-38.
7. **§11's PrepareReport sketch lists `constraints_hit` with no semantics**, and audit §13 repeats the name without one. Phase 1 found no reader, no rule that consumes it and no meaning either document supplies, and removed the field; `warnings` carries what a Provider would have said with it. Recorded for §12.
8. **§8's binding example writes `provider:` as the Binding's field name** (`bindings: radio: provider: ezsdr.radio.uhd`). SB-22 binds Providers, Sinks and Executors through that one map, so the field is `module`. The example is an illustrative shape, which the Vision's index already says of every `{ ... }` block, but the word is a visible departure and is recorded here for §12. Beyond the name, the value is an exact `{ id, version }` (D78), where §8's example gives only an id.
9. **Audit Finding 6 cites `v3/changelog/v3.0.17.md` for the PPS start-order failure.** The note is in `v3/changelog/v3.0.20.md:56-59`, whose own first line nevertheless reads `# EzSDR v3.0.17`, which is presumably how the misattribution arose. The finding's substance is unaffected.
10. **§8's two example profiles carry no `authority`**, which SB-24 makes mandatory, and the simulation example binds no Authority at all for its `time: { class: simulation }` — under the earlier inference it would have planned only if the Mock Module were itself an Authority. Like `provider:` (item 8) and the missing `version`, the examples are illustrative shapes; they owe one `authority:` line each, recorded here for §12 (finding D97).
