## 3. Design constraints that shape every type (settled; do not relitigate)

Full list: Vision §65, 42 invariants. The ones that bite first when writing code:

- **Kernel stays small.** Three tiers: Kernel (frozen at v4.0), Vocabulary (versioned, additive), Extensions (namespaced, unstable). A new experiment type adds a Vocabulary crate, never a Kernel concept. Nothing on the §6 list (UHD API, CUDA, wasmtime, RFNoC graph construction, IEEE 802.11 algorithms, placement optimiser, metrics framework, ...) appears in Kernel crates. §5, §6.
- **"Kernel" means only the Core tier.** The discrete-event simulator is the **Simulation Engine** (`sim-engine`), never a kernel. §5, §15.
- **Time is integer ticks at a rational rate; every timestamp names its ClockDomain.** Never floating-point seconds. A sample-rate change starts a new SampleClock. §15, §23, §27.
- **The Stream Contract is normative.** SampleBlocks are immutable-after-publish, refcounted handles tagged with a MemoryDomain; gaps are flags plus time jumps, never filled; validity is per channel; TX is a sequence of bursts with `START_OF_BURST` / `END_OF_BURST`, a time jump inside a burst is `TX_DISCONTINUITY`, never zero padding. §23.
- **Mock enforces the hardware envelope.** A Mock that accepts what an X310 would reject is a bug. TimingEnvelope and PerformanceEnvelope are checked at `validate()` and at runtime, on Mock and hardware alike. §13, §34, §59.
- **Intent and binding are separate.** ExperimentSpec = intent, with per-direction resource requests (`rx` / `tx`). BindingProfile = bindings + placements + environment (channel model, fault schedule, RF safety envelope). Placement and environment never appear in the Spec. §8, §10, §20.
- **Everything is a Run.** `connect()` opens a Session = Run with an implicit Spec and a typed action log; every Action is admitted on the control path before dispatch. §3, §50, §52.
- **Compile before RUN; the real-time path never parses Spec/JSON.** No structural graph mutation during RUN; parameters change only through declared update classes. §10, §27.
- **Modules talk only through Kernel contracts** (Resources, Ports, Events, Actions, Capabilities, DataContracts); no Module depends on another concrete Module. Coherence is declared by the owning Provider, never inferred across Providers. §7, §25.
- **Kernel public types are schema-first, versioned, language-neutral.** Old documents are migrated or refused, never silently reinterpreted. §9, §65 #39.
- **Core validates, it does not optimise.** No automatic placement, graph fusion or transfer planning. §10, §20, §31, §63.

## 6. How the user wants design work done

- **Adversarial, evidence-driven, minimal-core.** Verify claims against the repo and primary sources (UHD docs, source, papers). Mark what you could not verify as inference (the audit uses VERIFIED / INFERRED). "This should NOT be in Core" is a valid and welcome conclusion. Scope creep is a defect equal to a missing feature.
- **Pre-release: long-term benefit over compatibility** (owner, 2026-10-06). v4 is not released, and v4.0 has not frozen (OV-12); it freezes after Phase 10 (§4). A breaking change is allowed when it is genuinely better for the software in the long term. This covers a schema before the freeze, the Python API, a Vocabulary or Module version, and existing fixtures. Do not choose a weaker design to save compatibility cost. Short-term effort is no reason either (owner, 2026-10-07): a long-term simplification is worth a large change, and a plan is staged only to control risk, never shrunk to save work. **No users yet, so no version management** (owner, 2026-10-09): until the v4.0 freeze, do not bump crate, Module, Vocabulary, profile, protocol or package versions and do not write `schemas/SCHEMA_CHANGELOG.md` entries — versions stay as they are and git history is the record. What stays because it is cheap and catches real mistakes: regenerate a changed schema and keep `schema_freeze` green; a document of a version it does not support is refused, never silently reinterpreted (§3; invariant 39). At the freeze, versions are set once and the changelog starts (handoff's checklist). This is about compatibility cost; it does not reopen the settled constraints of §3.
- **Simplify, but stay in control** (owner, 2026-10-09). Keep simplifying so the specs do not grow out of hand, but never at the cost of a flood of bugs or a state nobody can follow: every simplification lands with the tests that pin its rules, an independent review, and the mutation gate at the end of its step (§7); a large change is staged so each step leaves the tree green.
- **Three strikes on one failure mechanism: doubt the design** (owner, 2026-10-07). Count bugs, issues and review findings alike, by the design mechanism that caused them (a review FAIL that is only a missing test or a stale copy of a rule does not count), not by symptom or area: one mechanism can surface in several areas, and one symptom can have unrelated causes. Labels: `area:<name>` sorts an issue when it is filed; `mech:<name>` names its mechanism as soon as the root cause is clear enough, without waiting for a fix, with one line in the issue saying why. When a third bug is given one mechanism, stop patching locally: before fixing any open bug of that mechanism, write a short design note. Can the concept be removed or merged, is a rule implemented twice (in MockRadio and a hardware Module, say), is its spec text too complex? Record the outcome: an amendment spec, or the reason the design stands together with the tests that pin it (such as a differential harness). The rule asks for the question, not a rewrite; complexity the hardware really has stays. The mechanisms, their counts and where each note is: [plan/maintenance/failure-mechanisms.md](plan/maintenance/failure-mechanisms.md).
- Review-only tasks change no design documents unless asked.
- Lead with one recommendation plus the rejected alternatives, not a menu.
- Language: the Vision is English; the audit and re-review are Japanese with English technical terms. Either is fine for new documents; keep `§N` citations either way.

## 7. Git habits

- Stop exactly where asked: `git add` is not a commit, and a commit is not a push. The user usually commits themselves.
- Commit subjects in Conventional Commits style (`chore:`, `docs:`, `feat:`); the body records the decision, not the diff.
- `.DS_Store` is ignored; keep the tree free of OS and editor junk.
- Build output never goes inside the working tree. The main tree builds into `~/.cache/cargo-target/Ez-SDRv4` (untracked `.cargo/config.toml`). A review, mutation or probe build in a copy or worktree — which does not inherit that config — sets `CARGO_TARGET_DIR=~/.cache/cargo-target/Ez-SDRv4-review`, shared by every reviewer; never a per-copy target directory. Cargo judges freshness by mtime and reuses any artifact newer than a copy's files, whichever copy built it — a mutated build included. So make such a copy with fresh timestamps (`rsync -a --no-times --exclude .cargo`, or `shutil.copy` rather than `copy2`), refresh them (`find <copy> -type f -exec touch {} +`) immediately before each build session in it if another copy may have built there since, and never interleave two copies' builds in that directory (Phase 5 Reviews F and G). Each copy's path adds a full set of artifacts there, so copy builds run with `CARGO_INCREMENTAL=0`, and a local, untracked `.git/hooks/post-commit` deletes `Ez-SDRv4-review` after each commit unless a cargo or rustc process is running (2026-10-10: it had reached 93 GB and was filling the disk).
- Mutation runs (owner, 2026-10-08): a fix round runs only the recorded rows whose code or killing test it changed, plus its new rows; the full lists run once, at the end of each implementation step. Every row's `old` and optional `old2` must match exactly once through `anchor.py`: Rust token sequences ignore inter-token whitespace; other files use exact substrings (owner, 2026-10-31).
- Remote mutation runs (owner, 2026-10-08): the lab servers `sim02` and `sim03` (32 cores, 60 GB each; `ssh sim02`, `ssh sim03`; docker without sudo) run mutation rows sharded, about 15–20× faster than one local list. `plan/maintenance/tools/remote/remote_mutate.py <lists> sim02:8,sim03:8 [IDs]` (`<lists>` is one list, a comma-separated set, or `all`) copies the working tree (uncommitted changes included) into a directory of its own on each host (`~/ezsdr-mut/<tag>`, deleted at the end, so two runs never collide), builds the image from that directory's `Dockerfile`, and runs each shard in its own container with its own scratch and Cargo target, so no build directory is shared; a shard runs its rows of every named list in turn, building once. The full gate is `all sim02:8,sim03:8`: about 8 minutes (2026-10-13), against 17 for the six lists one by one. Keep shards × `REMOTE_CPUS` (default 4) within a host's 32 cores: the FakeDevice smoke set no longer fails under load (#60), but other tests still carry wall-clock bounds, and a test that fails under load counts a mutant as killed — a hidden survivor no result shows. Since 2026-10-16 development runs on the Linux PC `usrp-lnx03` (handoff §6), which reaches sim02 and sim03 directly: `REMOTE_SSH="ssh -o BatchMode=yes" python3 plan/maintenance/tools/remote/remote_mutate.py all sim02:8,sim03:8`.
- Python (since Phase 6) follows the same rule: run it with `PYTHONDONTWRITEBYTECODE=1` so no `__pycache__` lands in the tree, keep virtual environments outside it (the one the Phase 6 suite uses is `~/.cache/ezsdr-venv`, Python 3.14 with numpy on usrp-lnx03; Python 3.9 runs in a `python:3.9-slim` container, command in handoff §5), and point `EZSDR_SERVER` at the `ezsdr-server` binary built from the same tree (`plan/phase6/00-overview.md` GY-7). `ezsdr-runs/`, the server's default Session directory, is ignored.

## 8. Subagent usage policy (Claude only)

Applies only when the agent working in this repo is Claude (Claude Code). Not applicable to Codex or other agents reading this file — they have their own subagent mechanics.

The rules below are defaults, not a lookup table (owner, 2026-10-08). Deviate when the task calls for it, and say why in one line when you do. The exceptions are Fable and parallelism, which need the user's word.

**Whether to delegate at all** (owner, 2026-10-07). The tier table says which model a subagent gets, not that work must leave the main session; when the main session already runs the right model, it does judgment work itself. Delegate only: a review whose value is independence (an implementer and a separate reviewer); a large implementation that would flood the main context; and reading-heavy investigations whose answer is a fact. Analysis and decisions made with the owner, and small or medium investigations, stay in the main session, so it can answer follow-up questions from what it read rather than relaying a report. Saving main context is a reason to delegate only when what comes back is a fact: heavy reading that ends in a judgment (classifying issues, say) stays in the main session and relies on auto-compaction.

**Fact or judgment picks the tier**, not the topic or the tool. A fact (where X is defined, every caller of Y, whether §N exists) can go to a cheap tier; a conclusion (is this sound, VERIFIED or INFERRED, what should we do) goes to Opus.

**Evidence.** A delegated investigation returns `path:line` or a URL for every finding. A negative result ("not found") carries the exact search it ran, so the main session can rerun it; a missed hit is the cheap tiers' typical failure.

| Tier | Character | Use it for (examples here) | Launch |
|---|---|---|---|
| Haiku | Cheapest and fastest; misses things more often | Reading-heavy fact-finding: every caller of a Kernel type, where UHD sets a value, the matching lines of a long test or log output, whether each `§N` / `v3/...` citation in a file resolves. Bulk edits whose correctness a machine check settles (rename, fixture or `mutations.json` update, then `cargo test`). | `haiku-scout` (read-only); bulk edits: `general-purpose`, `model: haiku` |
| Sonnet | Solid coding and reading at moderate cost | Implementation bounded by an accepted spec and its tests; reading external docs or UHD C++ source to answer a factual question. Interpreting a Kernel contract or the Stream Contract is judgment and stays with Opus; Opus reviews what Sonnet writes. | `sonnet-researcher` (research); implementation: `general-purpose`, `model: sonnet` |
| Opus | Strongest judgment in normal use | Independent review, design and architecture critique, VERIFIED vs INFERRED calls (§6), drafting or editing design documents, recommendations, adversarial critique. | `general-purpose`, `model: opus`, effort `max` |
| Fable | A different model family; the most expensive | Never by default. Only when the user asks for it in that session: a **second opinion on a judgment Opus has already made**. Never the first pass, never mechanical work; the report names the model that produced it. | `model: fable` |

Relative cost: Haiku ≪ Sonnet < Opus < Fable. The table names tiers, not versions; an alias resolves to the newest model of its tier that the installed Claude Code knows, and an old Claude Code silently maps it to an older one (2026-10-08: 2.1.292 mapped `haiku` to Haiku 4.5; 2.1.293 maps it to Haiku 5.5). After a model release, check with a subagent that only reports the model ID from its system prompt. The built-in `Explore` agent runs on the main session's model (Opus); use `haiku-scout` for searches instead. The agent definitions live in `~/.claude/agents/`.

**Parallelism.** Default to exactly one subagent at a time. Launching more than one in parallel requires the user's explicit permission first — ask before fanning out, every time; do not fan out and explain afterward.

## 9. Multi-model workflow (owner, 2026-10-11)

Since 2026-10-11 the work is split across models, and this section applies to every agent that reads this file. Each agent finds its role here.

| Role | Who | Does |
|---|---|---|
| Orchestrator | Claude Opus (Claude Code) | Makes decisions with the owner, writes each delegated task's brief, reviews, adjudicates the reviews, and closes each step's gate (tests and mutation runs, §7) with a commit and a push. It does not implement large changes itself. |
| Implementer | The OpenCode2 model the owner currently names in handoff §5, which is the only place the implementer and its self-review model are written (owner's choices change with quotas and results; this file names no default so the two cannot disagree) | Implements against the accepted plan and the brief, and fixes the adopted findings. Its self-review reviewer (step 5) runs on the model handoff §5 names, given in the brief. |
| Independent reviewer | Sol 6.1 in OpenCode2 (`openai/gpt-6.1-sol`), read-only (`--agent plan`) | Reviews a risky step's test plan before its code, and every step's code at its end without seeing the orchestrator's findings. It runs in OpenCode2, not the Codex CLI, because Codex works badly with Orca. |

Each implementation step runs in this order (owner, 2026-10-18: for a risky step, the expensive judgment moves before the code; reviewed by Sol the same day):
1. The orchestrator's brief names the step's risk. A step is **risky** when it changes a queue, a deadline or an identity, a lifecycle, ownership across the FFI, or the boundary between a fake and the hardware it stands for; any other step skips steps 2 and 3. For a risky step the brief lists the operation sequences that matter, each with its expected result — short sequences, not a product of every state and operation — and the hardware or UHD behaviour they rely on, marked VERIFIED or INFERRED. Behaviour that several steps rely on is kept once, with its sources, in the plan file the steps share.
2. For a risky step, the implementer writes a **test plan** before any code: for each sequence, the test, what it asserts, how the assertion observes the behaviour, and the wrong behaviour that would fail it. Mutation rows use token anchors for Rust and exact substrings for other files (owner, 2026-10-31), and come with the code.
3. Sol reviews the test plan. It first writes its own failure scenarios from the step's purpose, the existing code and the primary sources, and only then compares them with the brief's sequences and the plan, so that the review is not anchored to the orchestrator's list. The orchestrator adjudicates and the plan is amended.
4. The implementer implements, and extends the plan for every state or failure path the implementation adds.
5. The implementer runs its own self-review loop before it reports (owner, 2026-10-11, from item 3 stage 3c on). Each round starts a **fresh** read-only reviewer from its shell, so the reviewer does not inherit the implementer's reasoning: `opencode2 run --standalone -m <the reviewer model the brief names> --agent plan --auto "<checklist>"`. The implementer fixes what the reviewer finds; one round is the default (owner, 2026-10-26: in stage 3a the second and third rounds took about 35 of the step's 117 minutes and overlapped what Sol found anyway), and a step's brief may allow a second only after a round that found a P1. A gate the brief leaves to the orchestrator is not a finding. Every finding is either fixed or rejected with its reason in the report — none is carried silently into the next round or the report's open items. The orchestrator's brief supplies the checklist:
   - every planned sequence has its test, the test observes what the plan says, and the mutation row breaks it;
   - scope against the plan, missing and extra;
   - a grep over every position for each "every / only / all" claim;
   - every `design/` text the change makes false, listed in the amendments;
   - maintainability introduced or worsened by the step, against the checks below.
6. The orchestrator reviews the brief's fidelity, behaviour that must not change, and design intent.
7. Sol reviews the code independently, including scenarios the test plan missed and the step's maintainability (below).
8. The orchestrator adjudicates both reviews and the implementer fixes the adopted findings. After a fix for a major, Sol re-reviews the fix and the sequences next to it. A fix round runs the tests and the mutation rows it touched or added (§7); new tests are repeated (20 runs) only when their verdict can depend on timing (a manual or wall clock, threads), not when they are pure (owner, 2026-10-26); the full lists, the image build and the Python suites run at the orchestrator's gate, and again for whatever changes after it. The step's review record counts its findings by source, severity and mechanism, matched against `plan/maintenance/failure-mechanisms.md`.

Self-review is a cheap first filter. It never replaces steps 6 and 7: the same model keeps the same blind spots, and a cheaper reviewer misses more, so a self-review that ends satisfied proves nothing about the tests' power. The orchestrator steps in at the brief, the test plan and the report, not between rounds; a background watchdog shell (no model, `plan/maintenance/tools/mutation_watchdog.py`) reports a breach of the mutation rule below. Whether steps 2 and 3 pay is judged after the next two or three risky steps, from their review records (wait for reviews, fix rounds, majors found after the plan).

**Maintainability** (owner, 2026-10-31; the rule reviewed by Sol the same day). Correctness gates do not stop code and tests from growing (in the UHD Module the tests are about five times the production code). Reviews in steps 5–7 therefore also check production code, tests and mutation rows. Read connected code, but require changes only for problems the step introduces or worsens:
1. **Duplication:** search for an existing helper or decision before accepting another copy. Name the copies and what would have to change together; do not merge code merely because it looks alike.
2. **State:** keep each lifecycle fact with its owning state and transitions, not in independently updated flags or caches. Name the competing representations and the sequence that could make them disagree.
3. **Tests:** test pure decisions at that level; retain caller, concurrency and device-path tests for wiring and ordering. Reuse fixtures and repeated setup without hiding the sequence or assertions. Follow the brief's named cases; remove coverage only with evidence that its failure case is unreachable or covered elsewhere.
4. **Leftovers:** remove code, parameters, tests and mutation rows the step makes obsolete, including outside edited hunks. Retarget rows when behaviour remains reachable.
5. **Mutation rows:** mutate the intended behaviour with the smallest uniquely matching source text practical. Avoid unrelated context and production scaffolding added only as an anchor.

Findings need concrete evidence, not style preferences or line-count targets. Maintainability alone is minor or a note by default; duplicated decisions or scattered lifecycle facts may be major when a concrete inconsistency risk is shown. Correctness findings keep their normal severity. Assign mechanism labels only when their definitions fit; §6 still applies. Pre-existing maintainability debt goes to the Phase 8-end review of code and test architecture (handoff §2), not a step-wide refactor. Minor-only fixes do not add a Sol re-review.

**Counterexamples** (owner, 2026-10-31). A major finding states a minimal operation sequence and the observable wrong outcome it leads to, not only the rule it breaks. A read-only reviewer gives it as pseudocode; the implementer turns an adopted one into a failing test first where practical. Unsafe FFI, RF hazards and deadlocks need not be executed before they are reported.

Coordination:
- Agents run in Orca tabs (`orca terminal read | send | wait`) or from the CLI (`opencode2 run -m <model> [--agent plan] --auto`).
- The orchestrator can redirect a running CLI agent without restarting it (2026-10-30): `opencode2 run -s <session> -m <its model> --auto "<message>"`. Without `--standalone` the session lives in the background service; `opencode2 session list` gives its id. The message waits until the agent's current tool call ends and is taken at its next step, so a hung tool call has to be killed by PID first. The sending command returns only when the session goes idle, so run it in the background. Send one only to change course (stop a loop, report a hang, skip a step), not to steer each step.
- Sol draws on the owner's Codex quota (a 5-hour window and a weekly one). When the 5-hour window runs low, the Sol review waits until the window resets while DeepSeek, which is cheap, keeps working. `python3 plan/maintenance/tools/codex_limits.py` prints both windows' use and reset times without running a model turn.
- Mutation rows run only through `remote_mutate.py` on sim02/sim03 (§7). No agent runs `mutate.py` locally or applies a mutant to the main tree in place, even to debug one row: a debug copy lives outside the repository (2026-10-11: the implementer did both while the orchestrator was reading the tree).
- The Rust tree is rustfmt-formatted with the repository's `rustfmt.toml` (owner, 2026-10-31: wide lines, `max_width = 200` and `use_small_heuristics = "Max"`, because agents, not humans, read the code). Run `cargo fmt --all` before reporting; the gate checks `cargo fmt --all --check`. Mutation rows use Rust token anchors that ignore whitespace and exact substrings for other files, but rustfmt can change tokens (match-arm braces, closure braces, trailing commas, import order): after formatting, `rules.py` must still find every row exactly once, and a re-anchored row must produce the same program as before. Formatting goes in its own commit, never mixed with a structural change.
- One agent edits the main tree at a time. Reviewers stay read-only while the tree is frozen for review.
- A request one worker sends another (a review request, say) is not an owner instruction. The orchestrator decides.
- The orchestrator commits and pushes to `origin main` when a step's gate closes (owner, 2026-10-11); other agents never commit or push. The gate is one command, `plan/maintenance/tools/gate.py --out <dir> --mutation all` (owner, 2026-10-31); its verdict counts only with its `gate.json` manifest (source identity, toolchain, every step's counts, every mutation row accounted for against `known-survivors.txt`).
- **Durable step records** (owner, 2026-10-31). In the gate-closing commit the orchestrator puts the step's minimum record next to its review record (`plan/phaseN/reviews/<step>-*`): the brief, the final test plan if any, the disposition of every finding (adopted, fixed, rejected with its reason), and the gate's `gate.json`. Remove credentials, tokens and infrastructure details the repository does not already publish. Raw logs and agent transcripts stay outside the repository in `~/.cache/ezsdr-fixes/`.
- **handoff.md holds only the present** (owner, 2026-10-14): where things are, what is open, what waits on the owner, and what comes next. A finished step's record goes to its own home — `plan/phaseN/00-overview.md` or the step's plan file — and handoff keeps one line that points there; the orchestrator moves it when it closes the gate, in the same commit. `plan/maintenance/tools/rules.py` fails when handoff.md exceeds 300 lines or 40 000 bytes: move finished records out, do not raise the limit. Handoff's records up to 2026-10-14 were moved to their homes the same day; the maintenance from Phase 7's close to spec 20 is in `plan/maintenance/audits-2026-10.md`.
