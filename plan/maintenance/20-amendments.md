## VF-1 — `Radio.rx.capture` needs exactly one recorder on the receive port (#42)

**Problem.** [#42](https://github.com/k3komatsu/Ez-SDRv4/issues/42): EA-17's helper uses "the recorder" of a radio's receive port, and nothing says what it does when the profile has none or several. Each claim, re-checked:

- VERIFIED — EA-17's `capture` "finds the recorder whose `feed` starts at this radio's receive port" (`design/16-easy-api.md:99`); neither `capture` nor `request` takes a recorder (`:86-87`).
- VERIFIED — several are allowed: SC-22 fans a port out to N links (`design/02-stream-contract.md:204`), and on a Session each Sink binding's `feed` is an output (SB-22c, SB-22g: `design/03-spec-and-binding.md:180, 184`). The default profile with its recorder bound twice, both fed from `radio/rx`, connects (probe).
- VERIFIED — RS-14 requires a `sink.capture` to name one recorder when several are bound (`design/04-run-and-session.md:131`; `crates/ezsdr-kernel/src/session.rs:506-533`): with two bound, one targeting `radio/rx` is rejected, "RS-14: sink.capture must name one of the 2 bound recorders", and one naming `rec_b` is admitted and answered from `sink/rec_b` (probe). RS-14 counts the recorders bound, not those reading a given radio.
- VERIFIED, beyond the issue — what the client does today (`python/ezsdr/session.py:414-420`). With none it raises `Error("no recorder is fed from radio's receive port in the Session's profile")` before any request (the Manifest's action log is empty). With several it silently takes the first binding of `profile["bindings"]`; since the server re-serialises the profile with its members sorted — serde_json without `preserve_order`, which `crates/ezsdr-kernel/Cargo.toml:13` excludes for OV-15 — that is the name that sorts first: profiles written `{zeta, alpha}` and `{rec_b, rec_a}` captured from `alpha` and `rec_a` (probe; their action logs). No test covers either case.
- INFERRED (the issue's) — another client may choose another recorder. Agreed; here the choice already rests on a serialisation detail, and binding a recorder whose name sorts first — a monitoring Probe (SC-22), say — moves every later `capture` to it. No claim of the issue is wrong.

**Decision for the owner.** What `Radio.rx.capture` and `Radio.rx.request` do when the Session's profile has no recorder, or more than one, fed from the radio's receive port. *Decided 2026-10-06: accepted as recommended (Owner decisions).*

**Recommendation.** Exactly one, or refuse before anything is sent — as `Session.radio()` already refuses to choose among radios (`python/ezsdr/session.py:393-400`).

*Re-evaluated under the owner's pre-release premise (2026-10-06):* unchanged and still decided. No compatibility cost weighed in it — refusing several recorders was the better rule on its merits — and the `recorder=` argument the owner declined can still be added later without changing this rule.

`design/16-easy-api.md` EA-17: in its second sentence, "finds the recorder whose `feed` starts at this radio's receive port," becomes "finds the recorder whose `feed` starts at this radio's receive port — the one binding of the Session's profile whose `feed.port` is `{ component: <radio>, port: rx }` —,"; and after the sentence that ends "the channel count taken from the artifact's `continuity`." this is added:

> When the profile has no such binding, or more than one, `request` — and so `capture` — raises `Error` naming the radio and the bindings it found, before it sends any request, so nothing is logged: the helper never chooses among recorders. A client reads one of several by submitting `sink.capture` naming it with `Session.submit` (RS-14) and waiting for the `sink.CAPTURE_WRITTEN` whose source is `sink/<recorder>` and whose `request` is that request's number (HD-16, counted as above) (spec 20, VF-1; issue #42).

**Rejected alternatives.**
- *The first matching recorder in a fixed order (today's behaviour, made a rule).* A JSON object's members carry no order (RFC 8259 §4) and the server sorts them, so "first" can only mean "sorts first", and binding one more recorder can silently redirect every capture.
- *A recorder argument, `capture(n, recorder=…)`, or a handle per recorder.* A new API the issue does not need: `Session.submit` already names one (RS-14, Vision §3's descent). *Decided 2026-10-06: not added now; it can be added later without changing this rule.*
- *Submit and let RS-14 decide.* RS-14 counts recorders bound, not recorders reading this radio: a Session with two radios and a recorder each would be refused, and a lone recorder fed from another port would be used.
- *Capture on every matching recorder.* Two requests and two artifacts for one call, and the caller still has to pick one.

**Code.** `python/ezsdr/session.py:414-420`: `_recorder` collects every binding whose `feed.port` is `{ component: radio, port: rx }` and raises `Error` unless there is exactly one: with none, "EA-17: no recorder is fed from radio's receive port in the Session's profile"; with several, naming them sorted, "EA-17: 2 recorders are fed from radio's receive port ['rec_a', 'rec_b']; submit sink.capture naming one". `Rx.request` calls it before its first request (`:185`), so nothing else changes. Today's code conforms for none and not for several (VERIFIED above).

## VF-2 — Seconds in the Easy API: read exactly, rounded once, and sent as the Kernel's `Duration` on the Session's clock (#40)

**Problem.** [#40](https://github.com/k3komatsu/Ez-SDRv4/issues/40): EA-16 defines `after(seconds)` to the tick but leaves to the client how `sleep`, `wait_for`, capture and `run` turn seconds into the protocol's nanoseconds — the number read, the rounding, the range. Each claim, re-checked:

- VERIFIED — EA-16 reads `after`'s argument as the decimal written (`Fraction(repr(seconds))`) and rounds `s · root_rate` up once (`design/16-easy-api.md:88`), while `sleep` is only "`advance { by_ns }`" (`:89`); `wait_for`'s `timeout` and `run`'s `duration` have no unit in EA-16 (`:90`, `:92`), and only EA-17 gives capture's `timeout` one (`:99`). EA-12 puts integer nanoseconds on the wire, which the server rounds up onto the root (`:69`), exactly (`crates/ezsdr-server/src/lib.rs:420-426`). No rule addresses a negative or non-finite value, or which types are seconds. Vision §54 defines `sdr.sleep(d)` as `run.wait_until(now + d)` and says nothing of rounding (`design/vision/09-provenance-validation-and-ownership.md:158`).
- VERIFIED, with a correction — the issue's arithmetic holds: 5.42e-9 s on a 184 320 000 ticks/s root is 1 tick directly and 2 through 6 ns. The gap is bounded: through nanoseconds the instant is never earlier, and on a root of at most 10⁹ ticks/s at most one tick later; where 10⁹ divided by the rate is an integer `k` there is none, because ⌈⌈x⌉/k⌉ = ⌈x/k⌉ (probe: 19 999 durations per rate; worst gap 0 at 1 GHz and 200 MHz, 1 tick at 184.32 and 245.76 MHz). But no Authority of this repository has a root like the issue's: the Simulation Engine's is 1 GHz (SE-7, SE-9: `design/08-simulation.md:27, 32`) and UR-5 refuses a device master clock other than 200 MHz (`design/18-uhd-radio.md:54, 124`), so today the nanosecond step loses nothing. The example stands for a root the time model allows and no Authority has yet; the one-tick disagreement that exists today has another cause (next point).
- VERIFIED, beyond the issue — the two EA-16 rows already disagree on the default profile, where the two-stage rounding is exact. The package computes `max(0, ceil(seconds * 1e9))` in binary floating point (`python/ezsdr/session.py:48-49`), and the product's rounding can add a nanosecond: `after(0.0041)` names `now` + 4 100 000 ticks, `sleep(0.0041)` stands at `now` + 4 100 001 (probe, 1 GHz root); 1 755 of 100 177 decimals enumerated gain a nanosecond this way, 0.0041, 0.067, 7.7e-6 and 6.1e-8 among them. With numpy scalars the result depends on numpy's type promotion: `np.float32(0.1)` is 100 000 002 ns under numpy 1.24 and 100 000 000 under 2.5.
- VERIFIED, beyond the issue — the two paths accept different types. `after`'s `Fraction(repr(seconds))` fails under numpy 2, where `repr(np.float64(0.001))` is `'np.float64(0.001)'` (`sdr.after(np.float64(0.001))` raises `ValueError: Invalid literal for Fraction`, probe), and on `Decimal`, `Fraction`, `bool` and `str` under any numpy; the four durations read a `Fraction`, read `True` as one second, and raise `TypeError` for a `Decimal` or a `str` (Evidence).
- VERIFIED — a negative duration is silently zero (`sleep(-1.0)` does not move the Run; `wait_for(kinds, -5)` returns `None` at once); NaN raises `ValueError` and ±∞ `OverflowError` before any request; more than 2⁶⁴ − 1 ns reaches the server, which refuses the frame as `protocol` ("invalid type: floating point `1e+21`, expected u64") and keeps the Session (probe). Only the characterization tests of `DurationRequests` pin this (`python/tests/test_easy_api.py:400-442`, added by the refactor b8548da; their "RF-001" names no rule).
- INFERRED (the issue's) — independent clients would place deadlines a tick apart. Agreed: today through the float product, on a future root through the nanosecond step. The issue's claims hold; only its example root is one no Authority has.

**Decision for the owner.** How the package turns an argument in seconds into what the protocol carries — the types and numbers read, the rounding, the values refused — and what a duration on the wire is. *Decided 2026-10-06: accepted as recommended (Owner decisions).*

**Recommendation.** One reading for every argument in seconds — an exact rational, from a fixed list of types; a value of another type, a non-finite value and a negative duration refused before any request — and one rounding, done exactly, once. A duration on the Session's clock goes on the wire as the Kernel's own `Duration { domain, ticks }` on the primary root: `advance { by }` and `wait_for { within }`. The client takes the domain from `connected`'s `now` and computes `ticks = ceil(s · R)` with `R` the root rate `connected` reports — the formula `after` already uses — so that `sleep(d)` reaches the instant `after(d)` names on every root. The server refuses a `Duration` on another domain with `not_on_primary_root`, as it refuses `to` and `until`, and a negative one with `protocol`. A child Run's duration stays nanoseconds, `duration_ns`, because the child's clock is not the client's to know until the child exists. `ezsdr.protocol` 2.

*Re-evaluated under the owner's pre-release premise (2026-10-06), twice:* the first recommendation kept the wire's nanoseconds, accepting a one-tick disagreement between `sleep(d)` and `after(d)` on a root whose rate does not divide 10⁹ (the issue's 184.32 MHz example, a master clock rate the X310 also offers and UR-5 refuses today), because changing the protocol had a cost. The second sent bare tick counts, `by_ticks` and `within_ticks`, leaving their domain implicit. The Kernel's `Duration` names it: its domain tag "is what stops 1 000 ticks at 20 Msps being added to a 200 MHz point as a silent factor-of-ten error" (`crates/ezsdr-kernel/src/time/point.rs:28-31`), Vision §15 asks every timestamp to name its ClockDomain, and EA-1 has the protocol carry the Kernel's own documents (the fifth review).

> **Seconds.** `after`'s and `sleep`'s `seconds`, the `timeout` of `wait_for`, `capture` and `result`, and `run`'s `duration` are seconds of Run time, `run`'s counted from the child's T0 (EA-14); `None` keeps the meaning a signature gives it (`capture`'s and `result`'s default timeout, `run` without a duration). Before it sends any request — `capture` included, which reads its `timeout` before its own request although it hands it to `result` — the package reads each value as an exact rational `s`, a binary float as the shortest decimal that rounds to it in its own format: a numpy floating scalar as `numpy.format_float_positional(value, unique=True, trim="-")` writes it, so `np.float32(0.001)` is a thousandth; a `float` as `Fraction(repr(float(value)))` — the literal the caller wrote when that has at most 15 significant digits, so `0.0041` is 41 ten-thousandths and not the binary float nearest it; an `int` that is not a `bool`, a numpy integer scalar other than `timedelta64`, a `Decimal` or a `Fraction` as its exact value. *One principle for every binary float: its shortest decimal in its own format.* A `float32` holds durations finer than a nanosecond below about 8.4 ms — `np.spacing` is 0.12 ns near 1 ms and 0.93 ns near 8 ms — so reading it through `float()` would bring back the nanosecond Review K N-P1-3 took out of `after`: `np.float32(0.001)` would be 1 000 001 ns where `0.001` is 1 000 000 (re-review; this draft's second version did so). `format_float_positional` with `unique=True` takes no print option: under `legacy="1.13"`, `precision`, `floatmode`, `sign` and `suppress` it writes the same decimals on numpy 1.24 and 2.5, while `str` writes `np.float64(0.1) + np.float64(0.2)` as `0.3` under `legacy="1.13"`. **Rejected alternatives.**
- *Bare tick counts, `by_ticks` and `within_ticks` (this draft's second version).* The ticks' domain would be implicit: a client that counted ticks of the wrong clock would be scaled silently, where a `Duration` on another domain is refused; and the protocol, which otherwise carries the Kernel's own documents (EA-1), would carry a unit with no type.
- *Keep nanoseconds on the wire, with the client's reading (this draft's first version).* Two roundings: on a root whose rate does not divide 10⁹, `sleep(d)` can stand a tick after `after(d)` (the issue's 184.32 MHz example), and the Session's own time travels in a unit the Kernel never uses.
- *An exact rational number of seconds on the wire, `{ num, den }`.* The one rounding would be the server's, but an ordinary computed float has a shortest decimal that 64-bit integers cannot hold — `1000 / 2.7e6` is `0.00037037037037037035`, a denominator of 10²⁰ — so the client would refuse such values, or the server would need arbitrary-precision arithmetic for a product the client already computes exactly for `after`.
- *A `Duration` converted from any related domain.* Exactness again needs one named root: a duration on a sample clock or another root would be rounded onto the primary root by the server, a second rounding the client cannot see.
- *Absolute instants computed in the client, `advance { to }` and `wait_for { until }`.* `sleep` would need a `status` first, and on a device-paced Session the Run moves on between the two, so `sleep(d)` would fall short of `d` by a round trip.
- *A `Duration` for a child Run as well.* The child's root is known only once its Authority is assembled from its profile (EA-14); nanoseconds leave that conversion to the server, exact on the roots children run on here.
- *Keep protocol 1 beside protocol 2.* Pre-release, a server that speaks one protocol is the simpler contract; EA-3 already refuses a version it does not speak.
- *Name the frame files `.v2.json` after the protocol.* Every other committed schema keeps its major 1 until the v4.0 freeze (OV-12); a file major that followed the protocol would be the one schema whose version means something else.
- *The float's binary value, `Fraction(seconds)`.* `0.001` would be 1 000 001 ns — the reading EA-16 already rejected for `after` (Review K, N-P1-3).
- *Today's `ceil(seconds * 1e9)` in floating point.* Not a rule: it adds a nanosecond to 0.0041, and its result for a numpy scalar depends on the numpy version.
- *`Fraction(repr(value))` for every type, EA-16's spelling for `after`.* It refuses numpy 2 scalars, `Decimal` and `Fraction`.
- *`Fraction(str(value))` for every type (this draft's first version; the review).* A `str` argument is then read by Python's literal grammar, which has changed (`"1_000"` reads on 3.13 and not on 3.9); a `bool` is refused only by accident; and a numpy scalar's `str` follows print options.
- *`numbers.Real` and `Decimal`, less `bool`, as the accepted types.* It admits third-party types registered as `Real` whose reading the rule would then have to define; the list covers the Python and numpy numbers a caller has.
- *A numpy floating scalar read through `float()` (this draft's second version).* Every `float32` below about 8.4 ms would gain the nanosecond Review K removed (`np.float32(0.001)` → 1 000 001 ns); the re-review showed the earlier claim that a `float32` is never exact to the nanosecond false.
- *Rounding down or to nearest.* A `sleep` could fall short of `d` and a timeout end before its boundary, against EA-12's ceiling.
- *Clamping a negative duration to 0 (today).* It hides the caller's arithmetic error; `time.sleep`, which `sleep` replaces (Vision §54), raises `ValueError` for it.
- *`ezsdr.Error` instead of `TypeError` and `ValueError`.* An `except ezsdr.Error` around a sweep would swallow a caller's bug; `time.sleep` raises these two (`time.sleep("1")`, `time.sleep(-1)`).

## VF-4 — A receive fault's loss is settled by the stream it hit (#45)

**Problem.** [#45](https://github.com/k3komatsu/Ez-SDRv4/issues/45): a receive fault at the tail of a stream that a cold change ends reports a loss no delivered block carries. Re-checked:

- VERIFIED — the issue's table reproduces at `7d3bb1d` with its own harness: each row records `applied: true, lost: 2000` and emits `RX_OVERFLOW` with `lost` 2 000, and no delivered block carries a gap (probe).
- VERIFIED — the cause is as the issue says. The fault fixes its `lost` and emits at once (`crates/ezsdr-mock-radio/src/lib.rs:557-573`) while the gap rides on the next block (MR-21, MR-22), and a cold change replaces `Rx` with its pending `flags` and `lost` (`lib.rs:1121-1143`). MR-18 checks the change only when it applies (`design/09-mock-radio.md:121`), so the end is unknown at the fault; hence #35's clamp at the pending cut was withdrawn (`mr_20_a_fault_between_cold_clocks_is_not_applied`).
- VERIFIED, beyond the issue — a cold change is one end among others. A sequence error at 1 ms followed 100 µs later by a `Stop` of `<device>/rx`, or by `device_lost`, also records `lost: 2000` and emits `RX_OVERFLOW` 2 000, while the stream lost 100 samples to it and no gap is delivered (probe). The fault truncates its loss only at an end already set when it applies (`lib.rs:540-544, 556`).
- VERIFIED — the hardware's behaviour: uhd-rx keeps an overflow report pending and emits `RX_OVERFLOW` only when the next block arrives, with that block's jump as `lost` (UR-18; `crates/ezsdr-radio-uhd/src/provider/rx.rs:315-321, 410-446`); a stream that ends first — at a cut, a cold switch (UR-25) or a lost device — drops the report (`rx.rs:51-84, 499-525`). RM-17 and RM-18 say the event "is emitted" without that condition (`design/07-radio-model.md:149-150`), so uhd-rx already departs from their letter. Vision §17 asks an injected fault for "the same typed RuntimeEvent, the same SampleBlock flags and the same timing consequence as the equivalent hardware fault".
- INFERRED (the issue's) — Phase 8's parity could count the difference. Agreed. The issue's expected values — row 2 `lost: 1`, rows 1 and 3 `applied: false` — are what the recommendation gives, and its "MockRadio only" holds, since uhd-rx already behaves so. No claim of the issue is wrong.

**Decision for the owner.** What a receive fault's record, its `RX_OVERFLOW` and the blocks show when the stream ends before the block that would carry its loss, given that the end is unknown when the fault applies; and whether the Radio Model says so for every Provider. *Decided 2026-10-06: accepted as recommended (Owner decisions).*

**Recommendation.** Settle the loss when it is known, as a USRP's stream does: the fault cuts the stream at once as today, but its event and its record wait for the stream's next block, which carries the loss, or for the stream's end, which no block follows. RM-17 and RM-18 state the condition for a loss the stream reports, so that both Providers meet their Vocabulary's text, and `radio` becomes 1.4.0; a block the Provider drops itself stays reported at the drop (MR-19, SC-20a).

*Re-evaluated under the owner's pre-release premise (2026-10-06):* unchanged. No alternative was rejected for a compatibility cost — a retraction event was rejected because a client may already have acted on the first event, a truncated event because no USRP produces one, settling MR-19's drop because SC-20a forbids a silent discard — and the one cost the draft had weighed, a `radio` version, it already pays.

`design/09-mock-radio.md` MR-20a (new, after MR-22):

> **MR-20a** An `rx_overflow` or `rx_sequence_error` that meets a running receive stream cuts it at `f` as MR-21 and MR-22 say — the block in progress ends at `k_f`, and no sample before `k_g` follows — and its loss is settled later, by that stream. The first block the stream publishes at or after `k_g` carries the loss (MR-21; a block MR-19 drops is not published, and the next one carries both losses); with it `radio.RX_OVERFLOW` is emitted, with RM-17's or RM-18's time `k_f` and the fault's own `lost`, `k_g − k_f` (MR-37), and the fault is recorded `applied: true` with that `lost`. A stream that ends before publishing such a block — at a `cold` change's `e₁` (MR-18), or at the end of a `Stop` or of `stop`, after the tail of an orderly one (MR-25) — carries the loss in no block and emits no `RX_OVERFLOW` for it (RM-17); with `k_e` the first sample at or after that end, the fault is recorded `applied: true, lost: min(k_g, k_e) − k_f` if `k_f < k_e`, and `applied: false, lost: 0` otherwise (spec 20, VF-4; issue #45).

**Decision for the owner.** Which instant a receive stream enabled from 0 channels starts at; where the leads it and a restarted stream wait are stated; and whether MockRadio waits them too. *Decided 2026-10-06: accepted as recommended (Owner decisions).*

**Recommendation.** Two members join the device profile's timing envelope. `restart_lead_ns` runs from a `cold` change's `e₁` to its new clock's first sample and covers what a restart needs — the untimed stop, the reconfiguration and the timed start (UR-25). `start_lead_ns` runs from the end of a receive stream's configuration to the first sample of its timed start, which is all a stream enabled from 0 channels needs, and all a missed start's restart needs, from `now` (UR-17). RM-25 uses them: a `cold` change's new clock starts at the first lattice instant at or after `e₁` plus the restart lead, and a receive stream enabled from 0 channels at the first lattice instant at or after both `e` and the end of its configuration plus the start lead — the issue's third reading — while a transmit stream, which starts without a command, adds none. Both Providers declare and honour them: the X310 profiles 50 ms each, the UHD Module's one constant, INFERRED until Phase 8 measures them; MockRadio's `x310-like` the same; `ideal` 0 and 0. The UHD Module records `e` and the end of its configuration, so that a test checks the origin exactly.

*Re-evaluated under the owner's pre-release premise (2026-10-06), twice:* the first recommendation wrote the UHD Module's constant into spec 18 and stated MockRadio's lead as zero, leaving Phase 8 to decide whether the Mock should wait it; the second put one member in the envelope for both leads, on the ground that nothing had measured them apart. That was an argument about values, and the two leads differ by definition — one from `e₁` over a stop and a reconfiguration, the other from the end of a configuration over a timed start alone — so each is a member (the fifth review). A quantity that both Providers must honour belongs in the envelope that already holds the restart gap, the stop tail and the command lead, where the Manifest records it and the Mock enforces it (Vision §13, §34, §59).

*Determinism, parity and Phase 8.* MockRadio stays deterministic: the leads are profile constants, and its configuration of a receive stream enabled from 0 channels ends when it receives the update, a simulated instant; the UHD Module's `c` is wall-clock time, as today. An `x310-like` Mock now starts a restarted or newly enabled receive stream when the X310 Module does, instead of up to 50 ms earlier — the looser direction §59 forbids. Phase 8 measures what the X310 needs on each path (the bench measured raw restarts only) and sets both members in both profiles, and its parity test compares each Mock value with its measurement. - *Anchor at booking (the issue's second reading).* A configuration slower than the lead would put the origin before the timed start is issued: a missed start and a gap again.
