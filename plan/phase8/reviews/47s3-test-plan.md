## 0. Decisions this plan takes, and the questions it leaves

Each decision is the plan's recommendation; the orchestrator may overrule any of them before code.

- **D1 One shared pure type decides what a staged value is** (new `crates/ezsdr-radio/src/staging.rs`, pure, like `timeline::command_instant`). Both Providers hold one and call it; the Providers' own code is only wiring (event emission, snapshot storage). Reason: AGENTS §6's mechanism rule ("a rule implemented twice, in MockRadio and a hardware Module"); the VH differential then proves the wiring, and a generator-side oracle written independently (D10) proves the type. API (rev 3; names are the plan's, not binding): `Staging::new(config)` (the Run's configuration of record); `set(&mut self, key, value, has_at, streaming: impl Fn(u32) -> bool) -> Result<(), Refusal>` (`streaming(k)` is the Provider's answer for stream `k`, D2: the type holds **no** streaming flag, so the fact has one representation, the line's); `snapshot(&self) -> BTreeMap<Key, Value>` (the values a `start_rx` takes at its booking). `Refusal` is an enum (`Instant`, `NotStaged`, `NoStream`, `Streaming`) whose `reason()` text, without a rule prefix, differs per cause. `Stop`, loss and `Provider::stop` do nothing to it.
- **D2 (rev 3, re-check D2) "Streaming" is the line's final state after replay.** A receive stream is streaming when its line, replayed over **every item booked so far in the order they take effect** (`(e, seq)`, `timeline::sorted`), ends `on` (RM-21): new `Line::streaming(&self) -> bool` beside `Line::halted` (the pruned items are in `start`). The Run's start is `on`; a booked `Stop` turns it off; a booked `start_rx` turns it on again **at its effective instant**, whether or not the device later accepts the start. So a start refused by the device (RM-25 halt) leaves the stream "streaming" (the line has `on` and `halted`): the user sends `Stop`, a corrected value, `start_rx` (S6). Reason: the refusal is booked later by uhd-rx (rx.rs:416 `refuse_segment`); a rule that read it would race a client that sends the next value right after `start_rx` returns. **Why not an arrival-order flag** (Opus D2): `Stop` is booked at `e = now` and does not cancel a later-effective start, so `Stop`, `start_rx(at = now + 1 s)`, `Stop`, set f2 would be accepted while the start still begins at +1 s with its f1 snapshot; reading the line's final state refuses it, with no second record of the same fact (AGENTS §9 maintainability 2). Rejected: a `Stop` that cancels pending starts (changes RM-21 and Mock parity). The Provider passes `|k| line(k).is_some_and(Line::streaming)` to `Staging::set`.
- **D3 Refusals beyond "streaming"** (each one branch of `Staging::set`, each tested in `Staging` and per Provider): a channel that is in no stream (`radio.rx.c<n>.stream` = -1 in the Run's configuration; nothing would ever use the value); an update that carries `at` (a staged value takes effect at the next start, never at an instant: ignoring `at` silently would be a trap); any key that is not `radio.rx.c<n>.{frequency_hz,gain_db,antenna}` (the stage-2 guard text stays: rate, stream, every transmit key, every other leaf). **A Spec `schedule` entry for a receive value is such an update** (rev 2, M1): its Action carries `at: Some(..)` (`crates/ezsdr-kernel/src/event.rs:929-933`, `resolve_template`), so it passes `validate` (the key is `cold`; the class comes from the declaration, admission.rs:123-130) and the Provider refuses it at run time with the instant named. Successful scheduled staging is out of scope: values change through Session actions only (B3 says why).
- **D4 (rev 3, ruling 7 as corrected by the re-check) The configure time and the start lead.** The origin is the plan's (RM-25, `crates/ezsdr-radio/src/timeline.rs:508-523`) and never moves: `ready` is the booking instant (`ready: now`, uhd-control control.rs:297; MockRadio lib.rs:1459), after a cut the later of the booking and cut + release window + one receive call + allowance (`timeline.rs:516-521`); the configure runs afterwards in the owner (`begin` -> `owner_configure`, rx.rs:354, core.rs:1304), so it lies inside the start lead. Keeping the origin fixed at booking keeps the plan identical in MockRadio and the UHD Module and needs no re-planning after booking (the machinery stage 2 deleted). Rejected: moving the origin to completion + lead (HEAD's form: re-plans after booking and makes the plan depend on the host's timing); a full-lead threshold (it fires on every restart, because the origin was planned as booking + that same lead). **Rule:** the receive start lead must cover the start's configure (spec 07 keeps "from the instant its Provider is ready" and adds "and covers the start's configure"). When `begin` is about to issue `rx_start` (rx.rs:371, after `owner_configure` returned), with `completion = core.now()` and `min_lead = min_timed_command_lead_ns` in root ticks (RM-6, "the declared command lead": the device's lead plus the delivery allowance, which the owner thread does not spend; conservative, no new constant), the decision is one pure function `ezsdr_radio::timeline::lead_left(origin, completion, min_lead) -> Option<i64>`: `Some(origin - completion)` only when `completion < origin` **and** `origin - completion < min_lead`, otherwise `None`. On `Some` the Provider emits one **`radio.START_LEAD_SHORT`** and **still issues the start at the planned origin**. When `completion >= origin` the start is already missed (my reading of the ruling): no pre-start report, and the device's `LateCommand` path (rx.rs:472-489, UR-17) reports it as today (one `LATE_COMMAND`, `GAP_BEFORE`, origin unchanged): each begun segment has at most one pre-start report and one missed-start report, and a missed-start restart never re-reports (it goes through `RxRecv::LateCommand`, not `begin`). **Why a new kind and not `radio.LATE_COMMAND`** (ruling 8): LATE_COMMAND's `applied` states the instant a command was applied (RM-22, lib.rs:769-776) and its `mark_artifact` reaction would mark a Run's artifacts for a start that happened on time. New kind: `Warning`, reaction `continue`, source the receive stream's node (as a receive `LATE_COMMAND`, RM-11), payload `{ "requested": TimePoint /* origin */, "configured": TimePoint /* completion */, "lead_left_ns": int, "min_lead_ns": int }`; rows in RM-11's and RM-22's tables, one entry in `radio_event_kinds` (lib.rs:198-215), a payload struct beside `LateCommandPayload`, the schema regenerated and `schema_freeze` green. MockRadio's configure takes no time and its start is never short of lead: it never emits the event, a **recorded parity limit** (KL-16's line, MR-34's text, S7). The deleted scenario `ur_25_a_receive_enable_counts_its_start_lead_from_the_end_of_its_configuration` (`git show 45a4294:crates/ezsdr-radio-uhd/tests/fake.rs`, ~2783) has two successors in S7: the partial-consumption case and the configure-past-origin case. The `rx_start_lead_ns` the bench measures (item 8) is the lead that makes a restart-with-configure never a missed start, so the profile value includes the configure.
- **D5 Labels of Provider refusals** (item 8): the start's refusal (rx.rs:416, and the declare-failure path rx.rs:393 once it refuses the start) is kind `"command"` with the start's `ActionId` (the kind the Mock and control.rs:285 already use for `start_rx`); rx_stop failures (rx.rs:293, 393's stop) are `"stop"`; the clock-end failure (core.rs:674) is `"stop"`; the RM-25 book errors (core.rs:531, 551) carry the kind of the Action being booked. To name the Action, the start's snapshot entry (`configs` map, control.rs:296) carries its `ActionId`; a start whose action is unknown (the first segment, a restart) keeps `None`.
- **D6 Q4 (phase draws)**: MockRadio draws one fresh phase per `random`/`random_unless_timed_tune` channel for each receive segment that **begins** (reaches its origin) from a `start_rx`, whatever the values (same value, changed value). A start cancelled before its origin (Stop, loss, `Provider::stop`) draws nothing. MockRadio models no failed configure (its `Item.refused` is always false), so a failed configure has no Mock case; UHD has no phase model. This is today's `tune()` behaviour (lib.rs `tune_next`/`tune`), so the step only pins it. The real device's phase after an untimed tune is not promised (Q4, KL-3, KL-32).
- **D7 O2 reply shape**: `Response::Submitted` gains `refused: Vec<Event>` — the events of kind `radio.COMMAND_REJECTED` that exist when submit returns and whose payload `action` is one of the entry's `dispatched` ids. When the Run is no longer Running after a submit that dispatched to a Provider, the server answers with the existing `Ended` error instead (the entry stays in the log): a refusal could have been missed because the Kernel's wait returned early (paced.rs:185-202). A Session `Stop`/`Abort` dispatches to no Provider, so it is unaffected. Python keeps `Session.submit(...)` returning the entry; the wrappers use a private `_submit` returning `(entry, refused)` and `_admitted(entry, refused)` raises `Rejected(entry, event)`.
- **D8 §58 #16** (item 6): the RF envelope covers transmit frequency and gain bands, `tx_enabled`, and `antenna_ports` for **both** directions (lib.rs:424-479); it has no receive frequency band. So on a stopped **receive** stream the envelope form is the receive antenna: an antenna outside `antenna_ports` is refused at admission by `radio.rf_envelope`, logged, never dispatched. A receive frequency outside the board's tunable range is refused at admission by the Provider's `coerce` (RM-30). The transmit frequency-band form cannot return before stage 4 (transmit keys are classless); `v58.rs` keeps the stage-2 form for it and the gap is recorded again in note 47 (it was already recorded as a temporary hole).
- **D9 Observables**: MockRadio's `segments` section rows (MR-27) gain `values` for receive rows: `{"c<n>": {"frequency_hz", "gain_db", "antenna"}}` for the segment's channels, the configuration the segment began with. UHD's observable is the device's `apply` call values per segment (fake calls) and, for uhd-control alone, the snapshot in `streams.stream(k).configs[seq]`. (UHD's `plan` rows are built from the pruned line and cannot carry the snapshot; not changed.)
- **D10 The generator gets a class `Value`** (after `StartRx`, before `Fault`) with `Op::Set { stream, leaf, v }` and an oracle in the generator that scans the ops in arrival order (D1's independent check). Details in S11.
- **D11 Python reply order**: `rx.start(at, frequency=…, gain=…, antenna=…)` sends frequency values, then gain, then antenna, each by ascending channel number, then `start_rx`; the order is documented because S9's "the first value stays staged" depends on it.

## 2. Shape of the change (what the tests name)

1. `radio.rx.c<n>.{frequency_hz,gain_db,antenna}`: `update_class = Some(Cold)` (`crates/ezsdr-radio/src/lib.rs:radio_keys`, receive direction only). All else classless.
2. `Staging` (D1, rev 3) in `ezsdr-radio`: values only. A receive `UpdateParameter` calls `Staging::set(key, value, has_at, |k| line(k).is_some_and(Line::streaming))`; a `start_rx` takes `Staging::snapshot()` at its booking; `Stop`, loss and `Provider::stop` touch the staging not at all (they are items on the line, which is where "streaming" lives, D2). The "values" map is the Run's configuration (`radio.rx.c<n>.stream` gives the channel's stream).
3. UHD: `Control.config` becomes a `Staging`; `Control::book` of `UpdateParameter` calls `set` with the stream's line (`streams.line(stream_key(Dir::Rx, k))`); `StartRx` snapshots `staging.snapshot()` into `configs.insert(seq, ColdConfig::new(snapshot))` (control.rs:296); `Stop` arms book their line items as today. No device call at booking. The owner's `configure` already reads the segment's `ColdConfig` (control.rs `Planned::configure`).
4. MockRadio: `start_rx` → `staging.snapshot()` stored by `seq` in the receive stream's state (the `Item`'s `seq`, which becomes the segment's `by`), applied in `tune()` at the segment's origin tick (pushes into the channel `Timeline`s, instant order guaranteed because each channel belongs to one stream and origins increase), `UpdateParameter` → `staging.set` with the stream's line. `Stop` is as today.
5. Server: `Submitted.refused` and the Ended rule (D7); schema `schemas/` for the reply if one exists (EA-11).
6. Python: `Rx.start` keywords, the channel setters, `_submit`.
7. Generator, oracle, differentials (S11).
