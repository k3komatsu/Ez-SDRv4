## 2. The widened rule

**KC-24a rule text** (replaces the second paragraph of KC-24a; DA-1 form, no issue numbers):

> The coordinator calls no method of the Authority, of its time handle, of the host clock or of a `DataLink` while it holds a lock of its own other than a Module's slot lock. A value needed under a lock is read before it; a handle or an object to be called is copied out under the lock and called after it. The freeze gate is held across `TimeAuthority::cancel` and across the `now()` that stamps a `DEVICE_LOST` event, and across no other call of those objects.
>
> *Ceiling:* a registered check (KC-24 step 13) and a Provider's `coerce` (KC-26) run under `admission`; plan compilation calls `Provider::instance()`, `Sink::descriptor()`, the registered checks and `Authority::descriptor()` under every Provider and Sink slot lock; a Module's methods run under its slot lock; `Provider::stop` on the data thread's early stop runs under the freeze gate as well; the `now()` of a `DEVICE_LOST` event runs under the slot lock of the Sink or Executor whose `stop` failed. ## 3. Designs

### 3.1 #120 — the wake

```
struct WakeList { handles: Vec<PendingWake>, closed: bool }       // Locked<WakeList>, replaces wake_handle
struct PendingWake { generation: u64, handle: ScheduleHandle, fired: Arc<AtomicBool> }

wake(shared, unconditional):
  if wake_list.lock().closed { return }                                        // nothing waits for a wake once the cleanup's performance ran
  if !unconditional && wake_pending != 0 { return }
  g = wake_next += 1; wake_pending = g
  fired = Arc<AtomicBool>(false)
  clear = move |_| { fired.store(true, Release); CAS(wake_pending, g -> 0) }   // atomics only: no coordinator lock on the Authority's thread
  at = shared.now()                                                           // before any lock, as today
  match shared.schedule(at, clear):                                           // NO lock held
     Ok(h)  => { let mut list = wake_list.lock();
                 if list.closed { drop(list); let _ = shared.cancel(h) }      // no lock held; nobody else holds h
                 else { list.handles.retain(|w| !w.fired.load()); list.handles.push(PendingWake { g, h, fired }) } }
     Err(_) => CAS(wake_pending, g -> 0)
freeze_held(last):   // after drop(admission), under the freeze gate
  handles = { let mut l = wake_list.lock(); l.closed |= last; take(l.handles) }   // every handle cancelled once, under the gate
  // `last` is true only for the cleanup's FreezeDispatch performance; the data thread's early stop passes false
```
- **Shape 1 (deadlock)**: no lock is held across `schedule`, so a worker holding what an ordinary wake's `schedule` needs can call `disconnect_signal` (its own `schedule` and a short push are all it does) and the freeze does not wait for the parked `schedule` at a coordinator lock.
- **Shape 2 (lost handle)**: the list keeps every unfired handle, so an ordinary wake overwritten by the unconditional one is cancelled by the freeze (and the cancel returns `true`: the wake was still pending).
- **Bound**: an entry leaves the list when its callback fired and a later publish ran; a fired handle that nobody published after stays (one entry). So the list holds the unfired wakes plus at most one fired handle plus the one just published. Unfired wakes: at most one ordinary per `pending == 0` decision and at most one unconditional per Run (only the request that sets `end` wakes unconditionally: `ending.rs:210-216`, `mod.rs:524`, `paced.rs:75-77`).
- **Ownership cutoff, defined once** [F5]: the coordinator *holds* a wake's handle from the moment `schedule` returned it, and from then on exactly one party cancels it:
  1. the publisher found the list open and pushed it: the next performance of step 1 that takes the list cancels it (the data thread's, or the cleanup's);
  2. the publisher found the list closed, i.e. the cleanup's performance, the last one, had already taken the list: the publisher cancels it itself, outside every lock. Nothing else will, and the control thread is already in cleanup, so the wake has no job left.
  The decision and the push are one critical section of the list's lock, and `closed` is set in the same critical section as the take, so a handle is in exactly one of: taken by a performance, pushed for a later one, or cancelled by its publisher. **No accepted handle is left scheduled once the cleanup's performance has run**, and the Authority's `schedule` that started before a performance and returned after it is cancelled too.
- **The pre-check keeps the publisher's cancel rare**: the data thread's ordinary wakes continue until RS-6 step 3 joins it, i.e. through the cleanup's step 2, so without the check every delivery after the cleanup's performance would schedule and at once cancel a wake beside `Provider::stop`. With it, a wake that starts after the cleanup's performance schedules nothing; only a wake whose `schedule` straddles the performance (one in flight per thread: the data thread's, a Module thread's `disconnect_signal`) ends in the publisher's cancel. The check and the later decision are separate looks at `closed`, which is why the publisher still decides under the list lock.
- **Why the publisher's cancel is safe next to the Provider stops** (INFERRED, argued from RS-7's last clause): RS-7 orders a later performance's cancel after the data thread's Provider stops only for a handle whose callback might call a Provider; a wake's callback holds two atomics and calls nothing, so the one straddling cancel may overlap a cleanup stop. The cancel is made with no coordinator lock, so it cannot deadlock a `cancel` that waits on a lock a Module thread holds.
- **Why `closed` is set by the cleanup's performance only**: the data thread's early performance is followed by its own unconditional end-wake (KC-46b), which must stay scheduled and fire to wake a control loop waiting in `next_wakeup`; closing the list at the first performance would cancel it. The late-handle rule of #111 therefore holds unchanged for a handle published after the data thread's performance: the cleanup's later performance cancels it after the stops (RS-6, RS-7).
- **A wake published after the data thread's performance and before the cleanup's** (the end-wake) is in the list and is cancelled by the cleanup's performance if its callback has not fired; one that fired is a no-op entry the cleanup's performance cancels (the cancel returns `false`, as the existing test `kc_24a_freeze_a_handle_fired_before_its_cancel_is_not_a_failure` accepts).
- `FreezePoint::BeforeWakeTake` loses its purpose (it marked the wait for the wake's `schedule`); remove the variant and the hook call (decision Q2). `Done` stays.

**KC-46a text** (replaces "... under a lock held across `schedule`, ..." to the end of the paragraph): "The wake's handle is kept in `Shared` on its own, not among the handles `advance_to` schedules, in a list to which it is added when `schedule` returns, and RS-6 step 1 cancels every handle the list holds with every other scheduled callback. The coordinator holds no lock across `schedule`; an Authority that serialises `schedule` with `cancel` internally may make a performance of step 1 wait for a `schedule` in progress as long as its own contract allows. A wake whose `schedule` returns after the cleanup's performance of step 1 took the list is cancelled by the thread that scheduled it; one added after the data thread's performance and before the cleanup's is cancelled by the cleanup's, after the Provider stops (RS-6, RS-7). A wake's callback holds the pending generation and its fired flag only: it calls no Provider and reaches no part of the Run." **RS-6 step 1** gains, after "cancel every callback the coordinator holds a handle for, once each": "(a handle is held from the moment `schedule` returns it; a wake handle returned after the cleanup's performance took the wake list is cancelled by its own scheduler, spec 06 KC-46a)". RS-7 needs no change.

- **[F1] Acceptance rule**: `link_drops` is read only when step 6 completed, which the outcome says: a step RS-8a abandoned is a `FlushEvents` failure with `timed_out` in `outcome.failures` (`run.rs:565`), and a step that failed otherwise (a panicking `drops()`, KA-18) is a `FlushEvents` failure too; either way `drops` is null for every link. A `drops()` that returns after the timeout was recorded writes a complete snapshot into `link_drops` that assembly ignores (the Manifest has already been given the failure list, which is how the abandoned step shows). No second flag: the failure list is the one representation of "step 6 did not complete".
- After RS-8a abandons a wedged step 6 nothing holds `links` or `link_drops`, so assembly never waits. A panicking `drops()` unwinds outside every guard; `links` is no longer poisoned. The comment "`links` before `link_drops`, the order step 6 takes them in" is deleted (no nesting left). A `drops()` that returns after the Manifest stores one snapshot nothing reads (INFERRED harmless: `link_drops` is written once per Run by step 6 and read only by `assemble_manifest`).
