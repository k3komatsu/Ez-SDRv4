## 0. What the code does today (and one correction to the brief)

- The brief's premise "the booking stays in the book during its configure" is already true since E2b: `issue_configure` leaves it in `held` (`crates/ezsdr-radio/src/staging.rs:810-815`; `txbook_a_configure_keeps_its_booking_held`). **VERIFIED.** What removes it is the *result*: `configure_turn` calls `complete_configure(id, result.is_ok())` (`crates/ezsdr-radio-uhd/src/provider/tx.rs:531`), and `complete_configure(.., false)` takes it out of `held` and `drop_piece`s its region (`staging.rs:819-827`). So the issue's remark that the loss's `streams.end` misses a booking "out of held" no longer describes the code; the booking is held when the loss's `end` runs and is dropped only afterwards by the result. **VERIFIED.**
- A loss books nothing on the list: `Streams::end(.., lost = true)` calls `stop_at` on the record and, for a loss, pushes no halt ("the owner idles and its shutdown cancels with ProviderStop", `core.rs:661-665`). `Tx::step` returns false at once when `core.is_lost()` (`tx.rs:361-364`). `Tx::shutdown` reads the list, then `cancel_all` takes every held booking, and `stop_now(ProviderStop)` writes one note `UR-26: cancelled by Provider::stop` each (`tx.rs:1166-1170`, `:1019-1030`); `cancellation_reports(ProviderStop)` is false, so a note and no `COMMAND_REJECTED`. **VERIFIED** (C4(i)/(iii) snapshots).
- `Core::configure` returns `Err { lost: true }` when the core is already lost at the next channel's apply (`core.rs:1157-1159`); a device that itself answers lost returns the same shape from `device.apply` (`ApplyFails::lost` in tests). `device_failed` branches on `error.lost` alone: lost → `device_lost` (one `DEVICE_LOST`, a no-op when already published: `core.rs:1061-1063`), else `command_rejected` (`core.rs:1078-1084`). **VERIFIED.**
- The Mock has no configure at all: `issue_configure` / `complete_configure` appear only in `ezsdr-radio/src/staging.rs` and `ezsdr-radio-uhd/src/provider/tx.rs`; `grep -n -i configure crates/ezsdr-mock-radio/src` finds only an error-reason string (`lib.rs:1589`). Its lost device cancels held bookings by MR-20's own reason. **VERIFIED** (search: `grep -rn "complete_configure\|issue_configure" --include=*.rs crates`; `grep -rn -i configure crates/ezsdr-mock-radio/src`). No Mock change, no parity row.

## 1. Proposed change (one place)

In `configure_turn` only (`tx.rs:531-534`), the bit that decides "refuse or keep" is the device's own `error.lost`, the same bit `device_failed` uses to decide `DEVICE_LOST` or `COMMAND_REJECTED`:

```rust
let refused = lock(&core.streams).stream_mut(key).book.complete_configure(id, !matches!(&result, Err(error) if !error.lost));
match (refused, result) {
    (Some(held), Err(error)) => core.device_failed(held.settings.action(), "tx_burst", &error),   // unchanged line
    (None, Err(error)) => core.device_failed(None, "tx_burst", &error),                           // lost: the booking stays held
    _ => {}
}
```

- **Why here and not in `complete_configure`.** `TxBook` lives in `ezsdr-radio` and is shared with the Mock; it must not learn `DeviceError`. `lost` is a UHD-Module fact, and `device_failed` is where the Module already maps it. Keeping `complete_configure(id, configured: bool)` leaves `staging.rs` and its ~20 book tests untouched (a lost configure is, for the book, "nothing to take out", i.e. `configured = true`). Rejected: an `Outcome::Lost` enum on `complete_configure` (new API for the book, Mock never uses it); re-inserting the booking from the loss path (the loss runs on any thread, before or after the result, and cannot know whose configure it cut); keying on `core.is_lost()` (this is the existing row E2B-13's text and is wrong for S6 below).
- **One `DEVICE_LOST`.** The new `(None, Err)` arm still calls `device_failed`: when the core already knows the loss (the test hooks, another thread) it is a no-op; when the *device* reported lost first (S1b), it is the one place that publishes it. It cannot publish twice: `device_lost_locked` returns early once `lost` is set (`core.rs:1061-1063`). Invariant the fix relies on, **VERIFIED**: `Err { lost: true }` ⇒ `device_failed` ⇒ the core is lost by the time the turn returns ⇒ the next `step` returns false, so a kept booking is never configured again (the probe asserts no second `apply`).
- The mark: unchanged (`Err(_) => record_configured(key, None)`, `tx.rs:527`).
- Footprint (RM-15): the booking keeps its record region, exactly as the held booking of C4(i); what the loss's own `stop_played` already did to that region is what stays (RM-16: a booking starting before the Stop bound leaves `[t, B)`, one at or after `B` leaves none). The value-rule end (the "stays counted in `Bookings`") stays with it. Shutdown note: `UR-26: cancelled by Provider::stop` (or `... by Stop` when a halt is queued, S4), the same as any held booking under a loss.

**S6, which wins and why.** The code that orders them: `complete_configure` is told `refused` from `error.lost` of *this configure's own result* (new code, and the old `result.is_ok()` equally ignored `core.is_lost()`), and `device_failed` emits `COMMAND_REJECTED` from the same `error.lost` (`core.rs:1078-1084`). One bit decides both, so the book and the events cannot disagree: refused ⇒ one refusal note and no shutdown note; kept ⇒ no refusal and one shutdown note. Keying the book on `core.is_lost()` (E2B-13's text) breaks that: the booking would be kept (shutdown note) *and* `device_failed` would still emit `COMMAND_REJECTED` — two accounts of one booking. The device's refusal also names a real cause (UR-12 read-back, UHD error) which a later loss does not erase. Observation T4 below pins today's behaviour; it is unchanged by the fix and is the test that kills the `core.is_lost()` variant.
