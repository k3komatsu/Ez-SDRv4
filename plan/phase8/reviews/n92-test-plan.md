Decisions settled (adjudication; owner may override with the direction):

**A. A panic inside `device_lost` itself.** No second `catch_unwind`, no `rejected` row "panicked in device_lost", and no T7. A second catch leaves the same missing-event/live-Run failure for a third panic, and T7's always-panicking Authority is a synthetic second failure, not the half-mutated-line state I could only infer (`core.rs:1058-1072`). Reachability stays unestablished (§9). UR-16 makes no claim about a panic in the handler. If a concrete reachable counterexample is found, it is a new issue.

**B. A uhd-control panic during `Provider::stop`.** Uniform fail-closed: it is a `DEVICE_LOST` too, with no `stop.is_some()` branch (a branch would race with `stop`). Sol's reason: `stop` booked does not mean TX/RX shutdown finished (`mod.rs:702-715`), so cleanup cannot assume nothing is left to protect. **Cost, stated honestly** (UR-16 and KL-2, §7): `cleanup` skips `close_streams` for a lost device (`mod.rs:733`, `!core.is_lost()`), and `Device::drop` of a lost device pushes it and its streamers onto a process-wide `KEPT` list and never frees them (`uhd.rs:685-688`). A healthy device whose control thread panicked is thus retained, not closed, for each such Session until the same `args` are opened again in the process (KL-2's workaround, which frees the kept device) or the process exits. "Bounded by process exit" understated it for a long-lived server that opens many Sessions. This already holds for a uhd-rx/uhd-tx panic during shutdown; the change extends it to uhd-control.

**C. UR-30's `plan` row.** Preserved, never an accepted exception: after a uhd-control panic the Manifest holds **exactly one complete** `timing { what: "plan" }` row. `Control::finish` is its only writer today (`control.rs:256-260`, via `Streams::record`, `core.rs:779`), so a dead control never writes it, and `plan_row(..)` in the test helpers panics on absence (`tests/fake.rs:1512`). An unconditional append by the handler would duplicate a row `finish` already wrote (panic after `finish`'s write, or inside `finish` after `core.timing(plan)`). The implementation therefore needs a once-only writer; the tests pin the property (one row), not the mechanism: T9. My recommendation for the mechanism is in the final message (move the write to `Provider::stop` after `join("uhd-control")`: `finish` reads only `core`, so one writer, no flag).

## 1. Seams and the rules that keep them from hanging the manual clock

Every seam is a test-side double of a trait the Module already takes, or an existing `cfg(test)` mechanism. The only production changes the plan needs are §0's.

**The clock rules (new; Sol majors 1 and 2).** M2–M3 (`design/18-uhd-radio.md:365`): a participant is idle only while it waits on the manual clock and busy otherwise, a **standard primitive included**, and the clock stops while any participant is busy. Hence:

- **R1** No test waits for device time while a participant blocks on a std primitive (`Barrier`, `Receiver::recv`, a `Mutex`). Every deliberate block is at a point the body reaches without needing the clock, and is released by the test thread on a *condition* it observes (a flag, an event count, `core.is_lost()`, a joined thread), polled with **wall** sleeps (`std::thread::sleep`, `recv_timeout`), never with `host().sleep` or `Direct::until`, which advance device time and would never return.
- **R2** Every scenario that deliberately blocks a thread or can deadlock (T2a, T3, T4, T5, T6c, T8 and T9 by their seams) runs **entirely** inside an external wall watchdog, *including* teardown (`stop`, `cleanup`, `finish`): `bounded(what, Wall::from_secs(30), move || { … })` (`tests/fake.rs:1790-1802`; the `Direct::until` 10 s `Instant` check, `:1485-1490`, cannot fire once a participant stays busy, because `host.sleep(1 ms)` itself never returns). For the unit tests in `provider/mod.rs`, one `bounded` helper goes into `test_support.rs` (the integration binary keeps its own: two tiny functions in two test targets; the implementer reuses one if `tests/fake.rs` can reach `test_support`).
- **R3** No assertion depends on when a thread runs (`plan/phase8/37-test-thread-timing.md`): triggers are conditions, assertions are records. The `bounded` limit is the only wall time, and a correct run never approaches it.

## 2. What "ended" and "quiet" mean for the transmit stream (Sol major 5)

A loss sends no end of burst: after `device_lost` the Provider makes no new device call (UR-29: "stop using the device"; the existing test says "the lost send is not made, and no close follows it", `provider/tx/tests/e2a.rs:164`), and `Streams::end(.., lost = true)` books an `End` item on every line and pushes no cancel (`core.rs:647-650`). **But `mark_lost` neither stops hardware nor serializes ordinary sends** (`device.rs:2016-2018`: it only records the call; `uhd.rs:1143-1145`), and a uhd-control panic leaves the physical device healthy. A uhd-tx owner that read `is_lost()` false before the loss, planned a send, and calls `tx_send` after `mark_lost` is **in-flight work**, admitted before the loss (`tx.rs:738`: the call follows the plan, outside the lock). So "no calls after `mark_lost`" is not a valid oracle for a concurrent run, and logical clock or burst records do not show RF silence.

**Oracle Q** (replaces the old "no `tx_send`… after `mark_lost`"). It separates what was admitted from what is newly initiated, observes quiescence, and accounts for buffered samples. It is a helper used by T1 and T8, over `device.calls()` and the Manifest:

1. **Loss point.** `M` = the index of the one `mark_lost` in `device.calls()` (and the observed `DEVICE_LOST`). `A` = the transmit/receive call names counted as new work: `tx_send`, `tx_close`, `tx_open`, `rx_start`, `rx_recv`-class calls, `close_streams` (the implementer fixes the exact list from `Device`'s methods).
2. **In-flight bound.** After the loss is published, each owner can make at most the calls of the one pass it had already admitted. So the number of `A` calls with index `> M` is `≤ I`, where `I` = the calls one `tx::step` can make after its `is_lost` check (`tx.rs:295-305, 464-466`; a held tail may add a second send, `tx.rs:738-750`) plus one per receive owner's pass; the implementer reads those paths and fixes `I` as a constant in the test with a comment naming them (INFERRED until then).
3. **Quiescence, not "immediate".** After the `DEVICE_LOST` is observed, advance the manual clock by window `W` (50 ms of device time: at least 10 of the lost branch's 1 ms turns, `tx.rs:299-302`), count `A` calls (`n1`), advance `W` again, count (`n2`). Assert `n2 == n1`: **no newly initiated work after the owners have had turns to see the loss.** The first window may contain in-flight calls; the second may not. This is what the loss path promises, and all that UR-16 will say.
4. **Buffered samples.** The samples already handed to the device before `M` are not recalled and play out; the test records them (the `FakeDevice` transmit record if it exposes one, else `stats.tx_samples` and the `bursts` section, read after `finish`) and asserts the total after the quiescence windows `≤` the total at `M` plus the in-flight bound `I` sends' worth. It does **not** assert when RF stops.
5. **Logical records (not RF evidence).** The transmit and receive `sample_clocks` have `ended_at`, the burst record of the repeat is finished, no further repeat segment is booked. These show the Provider's streams ended, not that the radio is silent.

**What UR-16 will not say.** No promise of immediate silence. The text says: no new device call is initiated once the owners see the loss, work already admitted completes, samples already handed to the device are not recalled; the radio's own stop is a device behaviour, **INFERRED, unmeasured**. A hardware stop-time measurement is the owner's call (§9), not a dependency of #92.

**Reference run.** For T1, the same Session runs once more with `FakeFault::Lost` at the same device instant in place of the panic. Apart from the `rejected` row, the event's message, and the quantities Oracle Q treats as in-flight-dependent (item 2's counts), the structural records (item 5; the event; `mark_lost` before any `close_streams`) are the same: a panic is not a weaker end than a loss. This keeps the test from restating the loss rules.

### 11.1 Major M1 — no test races `Provider::stop`'s 1 s wall join

`join` gives up after `JOIN_BOUND` of wall time, records `did not join` and detaches (`src/provider/mod.rs:390-404`, VERIFIED). A body that is released inside `stop`'s window, or after it, can hit that bound on a loaded shard (8 shards × 4 CPUs under `remote_mutate.py`) and fail correct code, or let a second emission land after the assertions. So R3 gains a clause:

- **R4** No test calls `radio.stop` while a body it released, or a handler that body triggers, may still be running. Before `stop`, the test waits **inside `bounded`**, with wall sleeps (R1), until every thread it started is `is_finished()` (the child `tests` module reads `radio.running.threads`; `JoinHandle::is_finished`, as `join` does at `mod.rs:396`). `stop` then joins finished threads only: it cannot hit the bound.

Per test:
- **T4a / T4b** After releasing the *second* body, wait (in `bounded`) until both `JoinHandle`s in `radio.running.threads` report finished; then `radio.stop(Orderly)`. The assertions after `stop` are unchanged: every emission of both handlers is finished before they are read, and it is now the wait that guarantees it, not `stop`'s join.
- **T4c** Same wait before `stop` (the two bodies meet at the `Barrier`, both panic; wait for both handles).
- **T5** `stop` no longer races its own window. The test books the end exactly as `stop` does, then releases the body, waits for it to finish, and only then calls `radio.stop(Orderly)`: under one lock, `streams.stop = Some((at, Orderly))` and `test_support::end_streams(&core, at, false, false)` (`test_support.rs:250-254`; `end_streams` does not set `stop`, so the test sets it in the same guard, or calls `end_streams` and writes `stop` under the same lock; the implementer picks one). The helper thread of the old T5 is gone: the test thread books, releases, waits. `Streams::end` on an ended line is a no-op (`core.rs:641-643`, per the re-check), so `stop`'s own booking changes nothing and "one `End`" holds, with **the booked instant `at` being the test's**, which the assertions read (not a `stop`-time instant). `radio.stop` then joins a finished uhd-control. What T5 pins is the state "a panic after the end is booked": one `DEVICE_LOST`, no second `End`, `cleanup` skipping `close_streams`, no `did not join` and no `leaked` row (the latter now valid because nothing can be detached). A literal panic *during* `join` adds only scheduler luck and is **not** planned.
- **T9b** Uses the direct-end variant: the end booked by `end_streams` (as T5), never by `radio.stop`, before the body runs; see §11.2.
- **T6c** Releases the body after `core.device_lost("scripted")` was observed, waits for the body's handle to finish, then `stop`. (Same rule; the old text had `stop` after the release only implicitly.)

### 11.3 UR-16 wording and the KL question

**UR-16 text** (replaces §7's first bullet's proposed text). Three corrections: the end is stated on its own and for every Policy, `continue` has its consequence, and the detached-thread list names uhd-control:

> Every thread body runs under `catch_unwind`; a panic is recorded in the `rejected` section and reported as `DEVICE_LOST` with the message `"a Provider thread panicked"` (MA-9a), whichever thread it was — uhd-rx, uhd-tx or uhd-control —, a panic during `stop` included. Under every Policy the Provider's streams are then ended, and no new device call is initiated once its owners see the loss; work already admitted completes, samples already handed to the device are not recalled, and the Provider does not promise the radio is silent at once. Under the default Policy the Run ends. Under a Policy that maps `DEVICE_LOST` to `continue` the Run goes on without a working Provider: the next Action submitted to that radio waits KC-21a's budget and fails the Run. A device lost this way is not closed by `cleanup` (UR-29); it and its streamers are kept until the same `args` are opened again in the process or the process exits. Every join the Provider makes is bounded: 1 s per thread, … ; a thread that does not join in time is recorded in `rejected` under its name — `uhd-rx-s<k>`, `uhd-tx-s<k>` or `uhd-control` — and left detached, and then `cleanup` does **not** call `close_streams`, …

Evidence for each clause: the end is booked by `device_lost` (`src/provider/core.rs:1064-1066`) and the owners idle on `is_lost` (`tx.rs:298-301, 464-466`; `rx.rs:207-212, 296, 310`), under every Policy (VERIFIED by the re-check); under `continue` nothing drains the control queue, so the pending submit waits out the budget (`crates/ezsdr-kernel/src/coordinator/paced.rs:177-205`, VERIFIED); `join("uhd-control")` is bounded and detaches like the others (`mod.rs:390-404`, VERIFIED; today's text lists only rx/tx); kept device: `uhd.rs:685-688` pushes it onto `KEPT` and `reclaim` frees a kept one that `answers()` at the next `open` of the same `args` (`uhd.rs:643-665`), VERIFIED for `UhdDevice`; that this works on a healthy, panic-lost X300 is **INFERRED, never run**, and the rule's text says only what the code does. Test clause: T1, T2c, T3, T4, T5, T6, T8, T9; drop the "none named for … a panicking `uhd-tx` … and a panicking `uhd-control`" clause.

**UR-30**: "the plans the streams were carried out by, written once at `Provider::stop` after uhd-control is joined, and not at all when `start` was refused before uhd-control was spawned." *Test:* T9, and `ur_30_the_plan_names_every_stream_at_the_stop` (exactly one row).

**KL-2 is NOT amended** (retracts §7's third bullet). KL-2's Symptom (1.1 s / 3.0 s after the link drops; the abort at exit on a direct cable), Workaround and Status all describe a dead link and UHD's static teardown (`KNOWN_LIMITATIONS.md:23-30`; `uhd.rs:668-672`). Adding "or a Provider thread panicked" to *When* would make those lines false for a healthy device: a panic ends the Run at once and the abort-at-exit is a dead link's `deinit`. The user-visible fact after a panic is different: **the device stays opened and unclosed by the process until the same `args` are opened again or the process exits** (on an X300 it may stay claimed against another process; INFERRED). If wanted, the draft (next number KL-32 at the time of writing, `KNOWN_LIMITATIONS.md` ends at KL-31; the number is fixed when committed, and a number is never reused):

> ### KL-32 A Provider thread panic keeps the device open
> - **Symptom:** after a Provider thread (uhd-rx, uhd-tx or uhd-control) panics, the Run ends `Stopped { policy { DEVICE_LOST } }` (or goes on, under a Policy that continues it) with the Manifest written, and the device is not closed: the process keeps it open, and any of its radio output already sent is not recalled. Another process that opens the same `args` may find it claimed.
> - **When:** a Provider thread panics. It is a bug, recorded in `rejected` as `{ thread, reason: "panicked" }`.
> - **Workaround:** open the same `args` again in the same process (the kept device is freed) or end the process. Report the `rejected` row.
> - **Evidence:** UR-16, UR-29 (`design/18-uhd-radio.md`); `src/uhd.rs:643-665, 685-688`.
> - **Status:** INFERRED: the freeing on a healthy device has not been run; a device marked lost is kept by design (UR-29).

Also stated, not decided: **a hardware consequence UR-16 does not name** (INFERRED, owner's call, not a #92 blocker). After the loss a healthy device gets no transmit end of burst and no `rx_stop`: no device call follows the loss (UR-29, `design/18-uhd-radio.md:326`) and `cleanup` skips `close_streams` (`mod.rs:733`). Whether the next `uhd_usrp_make` on the same `args` resets the DUC's timeline is unverified; UR-33's model keeps it "until its EOB word" (`design/18-uhd-radio.md:347`). This holds today for a uhd-rx/uhd-tx panic. Added to §9.
