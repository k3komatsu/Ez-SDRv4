## Why
`plan/maintenance/failure-mechanisms.md`'s mechanism `mech:admission-per-origin`: "A check on incoming Spec or Action content is written into one origin's path or one traversal … instead of the single point every input crosses, so another origin or a nested position skips it." Bugs: #5, #25, #27 and now #104 (2026-11-18: SB-9a's non-ASCII key check ran at the Session, Action, control-event, section and `from_json` doors, but not on Provider-supplied content — `PrepareReport.effective` copied into `Manifest.prepare`, a `CoerceReport`'s coercions into `Manifest.admission` — so a Run transmitted and then failed to seal its Manifest). #104 was fixed at those doors (commit 272bc6ff; records `plan/phase8/reviews/n105-*`) without the design note the fourth strike called for. The ledger's candidate remedy: "one `admit()` that every input crosses", before the v4.0 Kernel freeze.

## The question (AGENTS §6: ask it, do not force a rewrite)
1. Inventory: every place the Kernel takes in content from outside its own code — the Spec and BindingProfile, a Session entry, ControlOps, a Module's submission (MA-14a), Provider/Executor/Sink reports (`PrepareReport`, `CoerceReport`, events, `Violation`s from registered checks, step outcomes), documents read back (`from_json`), the Python client's requests through `ezsdr-server` — and, for each, which content checks it runs (ASCII keys SB-9a, schema/`deny_unknown_fields` SB-9, value kinds, size bounds, namespaces) and where (path:line). Mark the ones that skip a check another door runs.
2. Is the concept removable or mergeable: can every inbound document cross one typed entry point (a constructor or a validating newtype per document kind) so a door cannot forget a check? Or is "one `admit()`" the wrong shape because the checks differ by kind (e.g. Actions need KC-24's order; reports need only SB-9/SB-9a)? Propose the smallest structure that makes a forgotten check impossible or caught by a test — e.g. a per-kind entry function plus a test that enumerates the doors (a registry checked by a governance test), versus a typed wrapper. At least two alternatives with the reason each is rejected; what each costs (code, Kernel surface under OV-23, schemas).
3. Is any rule implemented twice, or is the spec text (SB-9, SB-9a, KC-24, RS-11, MA-*) too complex? Name the texts that would change.
4. What the outcome would be: an amendment (which rules, which code), or the reason the design stands together with the tests that pin it (and which test would have caught #104).
5. Does any answer change what a user sees (a refusal's place or text, EA-16's promises)? Those are the owner's to decide; list them separately.
