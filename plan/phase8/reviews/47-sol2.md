## 2. O1〜O3の整合性

### O1：Spec側に置く判断は正しい。ただし「今日ある経路」ではない

現行の `ExperimentSpec.resources[name].requires` は、membershipや初期frequency/rateを **`Constraint::Eq` として表現できる**既存の器です。しかし、Sessionの `connect` からそこへ渡す入口はありません。

- `crates/ezsdr-kernel/src/session.rs:461,487-489`  
  暗黙Specを新規作成し、Provider resourceの`requires`を空にする。
- `crates/ezsdr-kernel/src/coordinator/mod.rs:165-175`  
  入力はprofile・assembly・leaseだけ。暗黙Spec生成直後にhashとpipelineへ進む。
- `crates/ezsdr-server/src/protocol.rs:55-63`、`python/ezsdr/session.py:689-705`  
  wireにもPythonにも初期要求の欄がない。
- `design/04-run-and-session.md:164`（RS-12）、`design/03-spec-and-binding.md:210,241`（SB-22c、SB-T2）  
  空の`requires`を明記している。

したがって、**Action形状・runtime admissionは維持できるが、KernelのSession入口と暗黙Spec生成規則は変更対象**です。

**RM-31との衝突は、現在の既定antennaにはありません。**

- UBX・OBX・CBXのRX既定値はすべて`RX2`：`design/07-radio-model.md:299-301`。
- 実装もboardのRX antenna列の先頭`RX2`を採る：`crates/ezsdr-radio/src/x3xx.rs:153-154,288-295`。
- RM-31の実装は同じtimekeeper・slotのRXを調べる：`crates/ezsdr-radio/src/channels.rs:592-620`。
- Basic/LFは`board() == None`なので、このduplex制約の対象外。同ファイル`:598-600`。

**既定antennaを変更する必要はありません。** ただし、明示した`RX=TX/RX`と既定TX membershipの組合せは拒否対象です。

### O2：通常のbooking拒否なら、両クラスでsubmitの返却前に判断される

**Device-paced Run：VERIFIED。**

1. dispatch後に`wait_finished`：`crates/ezsdr-kernel/src/coordinator/pipeline.rs:1034-1038`。
2. UHD controlは`book`してから次の`recv()`を呼ぶ：`crates/ezsdr-radio-uhd/src/provider/control.rs:359-365`。
3. 次の`recv()`が前Actionのfinishedを公開：`crates/ezsdr-kernel/src/coordinator/state.rs:70-80`。
4. submit内のroundがeventをdrainする：`pipeline.rs:1045-1049`、`stepping.rs:149-151,214-230`。

これはKC-21aとMA-14bの意図どおりです。ただし**booking完了であって、将来のconfigure/send完了ではありません**（`design/05-module-api.md:173`）。

**既定Simulation Session＋MockRadio：VERIFIED。**

```text
RunHandle::submit
→ pipeline::submit
→ stepping::round(now)
→ step_until_quiescent
→ MockRadio::step
→ ActionReceiverを空まで読みhandle_action
→ event drain

```

根拠：

- `crates/ezsdr-kernel/src/coordinator/pipeline.rs:1045-1049`
- `crates/ezsdr-kernel/src/coordinator/stepping.rs:159-181`
- `crates/ezsdr-mock-radio/src/lib.rs:2855-2879`

したがって、O2の「simulationでも判断済みか」は通常のbooking拒否について解決しています。

## 3. Findings

### 1. §4段階1・O1：初期要求を暗黙Specへ運ぶ契約が未定義

**問題**：O1は適切な置き場所を選びましたが、引数・型・生成順・Vocabulary宣言が決まっていません。§冒頭の変更対象にもspec 03・04・06がありません。

**最小系列と誤結果**：

```text
connect(tx={0:[0,1]})
→ 現行connectには渡せない
→ requiresだけ後付けしてもrequirements.vocabulariesは空
→ validateでUnknownKeyPrefix
```

**証拠**：

- `crates/ezsdr-kernel/src/session.rs:461,487-489`
- `crates/ezsdr-kernel/src/spec.rs:1074-1089`
- `crates/ezsdr-kernel/src/plan/validation.rs:304-320`
- `design/04-run-and-session.md:164`
- `design/03-spec-and-binding.md:210,241`

**訂正**：radio非依存の初期要求をSession入口に渡し、**hash・validate前**にresourceの`requires`へ組み込み、必要なVocabulary majorも宣言する契約を定義してください。RS-12、SB-22c/SB-T2、KC-1、EA-6/EA-10を改訂対象に追加する。接続後のsetterや`start_spec_run`への迂回では代替できません。

### 2. O1・§2.4：membership dictの省略・空・重複の意味がない

**問題**：`tx={...}`が方向全体の組を置換するのか、既定値へ部分的に重ねるのか不明です。membership固定後は、この違いをRun中に訂正できません。

**最小系列と誤結果**：

```text
connect(tx={1:[1]})
→ 部分overlayなら既定tx c0→s0も残る
→ 利用者が指定していないs0にもchannelが所属
```

`rx={}`も、RXなしなのか既定c0を残すのか定まりません。同じchannelを二つのstreamへ書いた場合も未定義です。

**証拠**：

- メモ47`:74,101,117`
- `crates/ezsdr-radio/src/channels.rs:423-438,754-755`
- `design/07-radio-model.md:310`（RM-30）

**訂正**：指定した方向のmapは完全なmembership指定とし、未列挙channelはnone、省略した方向は既定値、といった一意な規則を明記してください。空map、重複channel、存在しない番号、複数radio時の宛先も定義する。sample順はRM-3のlogical番号順を維持します。

### 3. §2.4・O2：複合呼出しの失敗条件がKernel拒否のまま

**問題**：§2.4は「KernelのRejectedなら開始を送らない」とだけ規定しています。O2で追加したProvider拒否を、この停止条件へ統合していません。また「submitまでに分かる拒否」と将来の実行時拒否を区別する必要があります。

**最小系列と誤結果**：

```text
RXが流れている
→ rx.start(frequency={0:B})
→ updateはadmitted、Providerは拒否
→ Kernel outcomeだけを見る実装はstartも送る
```

本来失敗した複合呼出しが余分なActionを送ります。

**証拠**：

- メモ47`:77-79,119`
- `python/ezsdr/session.py:110-113,568-575`
- `design/05-module-api.md:173`：finishedはbooking/application-at-receiptまで。
- `crates/ezsdr-kernel/src/coordinator/paced.rs:185-202`：終了・freeze・timeoutでは完了待ちを打ち切る。

**訂正**：各updateの**Kernel拒否または当該dispatched idのProvider booking拒否**で高水準呼出しを止め、残りのupdateと開始を送らない、と統合してください。将来のconfigure失敗・LatePolicy移動後の拒否は非同期eventとして別扱いにする。待機中にRunが終了した場合も、拒否eventがないことを成功の証拠にしない規則が必要です。

### 4. §2.1(2)・§2.4・O3：stagingと属性の読み戻しが同一視されている

**問題**：「残った値をstreamのconfigurationとして読める」は、現在の属性getterではProviderのstagingを意味しません。

**最小系列と誤結果**：

```text
ProviderはAで受信中
→ frequency=Bを設定
→ Provider拒否、PythonはRejected
→ frequency属性を読むとB
→ Stop→引数なしstartはProviderのstaging Aを使う
```

読み戻しから予想した設定と再開時の設定が違います。

**証拠**：

- メモ47`:30,33,77`
- `design/06-kernel-coordinator.md:335`（KC-27）
- `python/ezsdr/session.py:187-203`：getterは`session.effective`を読む。

**訂正**：属性・`effective`は**admitted configuration**であり、Providerのstaging/applied値ではない、と明記してください。Provider拒否でstagingは変えず、Kernel値は戻さない。実際のstagingを読めると約束するなら、そのProvider側の読取り経路を別途定義する必要があります。

### 5. §2.1(3)(5)：設定失敗後、次のTX burstがbookingまで到達できない

**問題**：「新clockは設定付きburstのbooking時に登録」と、残すRM-25のconfigure refusal後のclock終了を組み合わせると、再試行の入口がなくなります。

**最小系列と誤結果**：

```text
設定付きburstをbookingしてclock Cを登録
→ 装置が設定を拒否
→ Cをoriginで終了、streamはhalt
→ 修正値をstaging
→ 次の設定付きburstをsubmit
→ Kernelが「running transmit SampleClockなし」で拒否
→ Providerのbookingへ届かず、新clockを登録できない
```

**証拠**：

- メモ47`:37,41`
- `design/07-radio-model.md:255-256`
- `crates/ezsdr-kernel/src/coordinator/admission.rs:150-162`
- `crates/ezsdr-kernel/src/coordinator/state.rs:336-339`
- `crates/ezsdr-radio-uhd/src/provider/tx.rs:1169-1180`
- `crates/ezsdr-radio-uhd/src/provider/core.rs:1023-1028`

**訂正**：拒否された送信用clockの終了と、次のburstをadmitするためのclock寿命を合わせて定義してください。**Kernel admissionを変えずに再試行がbookingへ到達する具体的な経路**が必要です。段階4のテスト計画に、この失敗→修正→再送系列を必須で追加する。

### テスト計画に必要な操作系列

1. **入力省略→connect**  
   RX/TX c0がs0、他channelはnone。既定antennaでRM-31違反なし。TX membershipだけでは波形を送信しない。

2. **一方向だけ指定／空map→connect**  
   指定方向の完全置換、省略方向のdefaults、明示的な全channel noneをそれぞれ確認。

3. **二channel・非連続channel・別stream指定→prepare→開始**  
   正しいchannel集合・logical番号順・stream別clock。接続後のmembership Actionを必要としない。

4. **初期frequency/gain/rate/antenna→connect→最初のsample/burst**  
   初回から指定値を使う。UHD FakeDeviceではconfigureがarm/startより前であることをcall traceで確認。

5. **重複channel／範囲外channel・stream／不正型→connect**  
   明示した規則で拒否し、黙ったlast-winsやdefaultsへの退避をしない。

6. **TXあり＋同boardのRX antenna=TX/RX→connect**  
   RM-31で拒否。RX channelがstream noneでも対象であることを含める。

7. **throughput超過／RF envelope外／TX禁止→connect**  
   pipelineの適切な段階で拒否し、stream開始・送信しない。TXなしを明示したreceive-only構成は成立する。

8. **coerceされる初期値→connect→finish**  
   requested、effective、coercion/warning、Manifestを照合。暗黙SpecにVocabulary majorがあり、同じ要求は同じhash、異なる要求は異なるhash。

9. **既定profile／明示profile／設定済みdefault profile**  
   同じ初期要求が同じ意味になる。複数Providerでは宛先を取り違えない。

10. **MockとFakeDeviceで同じ初期構成→最初の受信・送信**
