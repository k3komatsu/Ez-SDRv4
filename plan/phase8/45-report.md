## 3. 失敗とその原因

### 3.1 毎秒 10 万 block での速さ

**原因（コードで確認）**：

- 新しい形では，時刻つきの値の in-flight の枠は，R が sample の中で消費を見るまで空かない（`brain/core.rs:629-674`）．
- 今の owner では，命令の queue の枠は装置の時刻で空く（`provider/control.rs:659-666,688-689`）．
- そのため，host で受信が遅れる（backlog）と，新しい形ではそれが設定の遅れになる．今の形では受信の遅れが設定に及ばない．

**backlog の出どころ**：FakeDevice は block ごとに DSP の履歴を走査する（`device.rs:548-553`）．これは両方の owner に共通である．

- 適用した値が増えると R の一 block の仕事が倍になり（約 9 → 18 µs），R が飽和する．
- 上限を 4 から 16 にすると，失敗は間隔ありで約 4.6 分の 1，まとまりで約 1.6 分の 1 に減るが，0 にはならない．

**意味**：これは設計の一つの規則が生む弱さで，速さの全体の問題ではない．

- 上限は「装置に残っている命令の数」（装置の時刻で減る）と「処分を待つ値」（証拠を待つ）の二つを一つで数えている．
- 分ければ，受信の遅れは処分を遅らせるだけで，設定を遅らせない．これは §4.5 の書き換えになる．
- 実機の X310 の DSP の履歴に，FakeDevice の走査の重さはない．これは推測である．
- 一方で，受信が数十 ms 遅れることは実機でもありうる．だから規則の弱さは現実の問題である．

**測る前に除いたもの**：測定の adapter の重さを，Sol のレビュー 3 回で除いた．重さは三つあった．

- sample ごとの作り直しと，履歴の複製．
- block ごとに，共有の condvar を毎秒約 20 万回 broadcast していたこと．
- 際限なく伸びる呼び出しの記録．

除く前の結果（R が毎秒約 1 万 block しか回らない）は，設計の判定に使っていない．

### 3.2 独立に選んだ誤り（holdout）

Sol は，実装より前に設計メモだけから 20 件を選んだ．実行の前には，訳が誤りに忠実かを Sol が確かめた．4 件は Sol の訳に差し替えた．数え方の裁定は `reviews/45e3-rulings.md` にある．

**見つけた 14 件**：H01，H02，H04，H06，H07，H08，H09，H11，H13，H14，H15，H16，H19，H20．どれも oracle か，進む性質の検査で落ちた．

**見つからなかった 6 件**：

| 誤り | 何が足りないか |
|---|---|
| H03 進み切った cell に予約できる | 同じ区間で，別の規則が先に受け付けを閉じる．このため変異した guard は使われない．<br>どの case も二つの規則を分けられない．守りが二重で，片方は単体のテストだけが固めている |
| H05 止まると決めた cell が開き直る | **oracle がない**．「Stopping は許された開始なしに開かない」という不変条件がない |
| H18 上限で cell が満ちたとき，待つ値を黙って捨てる | **case がない**．in-flight が上限（4）を超える case がない．<br>E2b の測定で見つかった進まない誤り（`u14b`）を DST が見逃したのも，同じ穴である |
| H10 loss の記録の前に F を立てる | 模型に loss の記録がない |
| H12 native の handle の解放と保持 | 模型に handle の破棄がない |
| H17 shutdown の時間切れの後始末 | 模型に join の時間切れがない |

模型にない 3 件は，note 45 の本番の設計（§4.5，§4.7，§4.9）には必要である．したがって，数えから外すことはしない．

### 3.4 再現の穴

`s1c_whole_walks_wide` は，seeded の構成の whole walk をスレッドで再現して world と比べる．seed 1〜2,000 では通った（E2a の gate）．

- seed 2,001〜10,000 では，分類できない食い違いが 7 本ある．E2b の前の commit でも同じ 7 本なので，E2a からある．
- trace の縮めは 0 件の出来事を返しており，縮めがうまく働いていない．
- **一つは確かめた（Sol，コードで確認）**：E2a の二つの包みの間で，受信の送りの順が違っていた．
  - world は `REnd` で `LateCommand` を積み，その後ろに公開の境界を足す（`world.rs:1044-1045,1094`）．
  - スレッドは公開の境界を `LateCommand` の前に送る（`threads.rs:911-921`）．
  - 判断役の inbox の順が変われば，判断役の操作の数も変わる．そのため 4 本（seed 2005，2619，6348，7047）の「BStep のはずが BOp」は，この順の違いで説明できる見込みである．これは推測である．
- **残る 3 本**（「RSend と RCheck」の取り違え）：直前の公開の判断に入る値が違う可能性がある．候補は，受け付けを見せる時刻の違いである．world は `SEffect` で受け付け，スレッドは `SUnlock` の後で受け付ける．これも推測である．
- **「縮めて 0 件」の理由**：縮めるのは最初の 3 本だけで，残りには空の列を置いていた（`thread_tests.rs:643-644,653`）．誤解を招く表示で，縮める処理の誤りではない．
- **扱い**：どれもまだ「再現の限界にすぎない」とは言えない．送りの順は，二つの包みが同じ手順を踏むという E2a の前提（AGENTS §9 Maintainability 1）を破っている．E4 では，順を一つに揃えてから 7 本を分類し直す．診断の記録は `reviews/45e3-sol-s1c-diagnosis.md` にある．

## 4. 実験が見つけたもの（条件の外）

- **E1**：探索は，コードレビューが見逃した設計の穴を多数見つけた．最も多かったのは「渡した仕事が変える cell の状態から判断する」機構で，4 回以上あった．ほかに，shutdown の順序，flush の残り，Close／Open の受け付け，panic の後の判断役．
- **E2a**：
  - 適合試験（FakeDevice と模型の差分）が，E1 の模型の誤りを見つけた．期限で packet の途中まで返していた．
  - スレッドの guard の手順で Sol の指摘が同じ機構に 3 回続いたので，一本の直線の手順に作り直した．
  - Q1 の差（受け付けの時刻を call の戻りで記録するか，`effective` で記録するか）は保守側の差である．今の予約の下限があるので，g2 には届かない．
- **E2b**：
  - 測定が，核の進まない誤りを見つけて直した（上限で待った値が，空いても予約されない，`u14b`）．
  - 遅れて再び予約することは，今の規則のまま固めた（`u14c`）．時刻を過ぎた値を断るべきかは M1 の問いとして残る．
- **Sol の価値**：独立のレビューは，各段の major をほぼすべて出した．E2b の測定の 3 回の REVISE は，どれも測り方の偏りを正しく指していた．実装役（Claude Sonnet）が自分で見つけたのは，その一部である．
- **G09**（phase7 の Kernel，`coordinator/stepping.rs` の `drain_and_react`）：反応を `delivered` の lock の外で適用する変異が，μs の競合なので黒箱のテストで殺せない．これは E2a の trace の強制と同じ手で殺せる見込みがある．Kernel に強制の hook を足すかどうかは別の判断になる．
- **#76**：負荷で落ちる 6 本のテストを，design note 37 の規則で直した．`mech:wall-clock-test-oracle` の 4 件目になる．規則を機械で検査するか（`rules.py`）は，owner の判断待ち．
- **大きさ**：`brain/` は合計 17,791 行．E2a と E2b で 8,876 行を足した．E2a は計画の上限 2,000 行を超えた（実行役と模型で 2,214 行，試験で 2,084 行）．note 45 の見込み（2,500〜4,000 行）は楽観だった．DST の world と case が大きい（`world.rs` 2,445 行，`core.rs` 2,012 行）．

## 5. 推奨：第 2 回（E4）を一度だけ

**目的**：二つの失敗が，それぞれ一つの原因で説明できるかを，前もって固めた条件で確かめる．

| 項目 | 中身 |
|---|---|
| 設計の改め | §4.5 の上限を二つに分ける．<br>・**装置の容量 K**：装置ごと（chain をまたぐ）の保守的な予約の枠．呼び出しが成功か途中まで効いた失敗で終わり，値の時刻に装置の時刻が達したら空く（終わらない呼び出しは時刻を過ぎても数える）．UR-24 の booking の上限とは別．<br>・**cell に残る値 D**：chain ごとに，予約から残るすべての値（K の値と `left` も）を数える．cut の報告は記録を確定するだけで，残りの義務を消さない．<br>文面は設計メモ 45 §4.5「上限は二つ」（Sol の設計レビュー 2 回，2026-11-03） |
| DST の穴 | ・oracle「Stopping は許された開始なしに開かない」（H05）を足す．<br>・上限を超える値を持つ case（H18，`u14b`）を足す．<br>・H03 の二重の守りは，片方を消すか，case で分けるかを決める．<br>・模型にない 3 つ（loss の記録，handle の破棄，join の時間切れ）を模型に入れるかを決める．入れないなら，E4 の範囲の外と明記する |
| 新しい holdout | 今の 20 件は見てしまったので，二度は使えない．Sol が改めた設計メモだけから新しい 20 件を選び，E4 の前に固める |
| 再測定 | 毎秒 10 万 block と 1 MS/s を，同じ表と同じ判定で測る．FakeDevice の走査の重さは両方の owner に共通なので，そのまま残す．FakeDevice は変えない |
| 再現 | 受信の送りの順を world とスレッドで一つに揃える．縮めの表示を直す．そのうえで §3.4 の 7 本を分類し直す |
| 成功の条件 | §7 と同じ．速さは p99 の差 < 100 µs，p99 ≤ 300 µs，取りこぼしは今以下，全件を勘定する．誤りは 20 件中 16 件以上 |
| 大きさ | 設計の改めは core と cell の小さな変更で済む見込み．DST の case と oracle を足す．測定は E2b の道具をそのまま使う |

**退けた案**：

- **ここで失敗と決め，§9 の第一の代わり（今のスレッドの中で判断を純粋な関数として取り出す）に移る**：前もって決めた手順どおりではある．しかし，二つの失敗はどちらも原因が一つずつ特定でき，直し方も小さい．一方で E1〜E3 は，DST が今の形では見つけられない設計の穴を見つけることを繰り返し示した．その証拠を捨てるのは，長い目で見て損である．
- **数え方を変えて成功とする**（模型にない 3 件と H03 を除けば 14/16）：結果を見てから基準を動かすことになる．採らない．
- **このまま移行する**：前もって固めた条件を二つ満たしていない．採らない．
