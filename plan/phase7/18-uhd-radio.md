## 1. Purpose

Vision §59 asks whether experiments written against MockRadio run on a USRP by changing only the BindingProfile. This Module is the other side of that comparison: it implements spec 07 on an X310 as MockRadio implements it in simulation, reports what the device does through the same events, flags and records, and declares what it cannot promise. It is written so that everything except the device itself runs without hardware: the Provider's logic talks to a `Device` trait, and the tests drive it with `FakeDevice`, a wall-clock double of a USRP, through the real coordinator.

## 2. Evidence

- **UHD's C API is a narrow bridge already** (VERIFIED, UHD 4.10 headers on this Mac, `/opt/homebrew/include`): every C entry point wraps its body in `UHD_SAFE_C`, which catches `uhd::exception`, `boost::exception`, `std::exception` and `...`, stores the text for `uhd_get_last_error` and returns a `uhd_error` code (`uhd/error.h:89-104`). Handles are opaque pointers, structs are POD (`uhd/types/metadata.h`, `tune_request.h`, `usrp/usrp.h`). This is what Vision §35 asks the bridge to be.
- **Receive metadata codes** (VERIFIED, `uhd/types/metadata.h:80-92`): `NONE 0x0`, `TIMEOUT 0x1`, `LATE_COMMAND 0x2`, `BROKEN_CHAIN 0x4`, `OVERFLOW 0x8` (with `out_of_sequence` distinguishing a sequence error), `ALIGNMENT 0xC`, `BAD_PACKET 0xF`. **Asynchronous transmit codes** (`:232-244`): `BURST_ACK 0x1`, `UNDERFLOW 0x2`, `SEQ_ERROR 0x4`, `TIME_ERROR 0x8`, `UNDERFLOW_IN_PACKET 0x10`, `SEQ_ERROR_IN_BURST 0x20`, `USER_PAYLOAD 0x40`.
- **Timed commands** (VERIFIED, `uhd/usrp/multi_usrp.hpp`, `set_command_time`): "A timed command will back-pressure all subsequent timed commands … If the time spec is late, the command will be activated upon arrival." The device neither refuses a full queue nor reports a late command: the Provider must count and judge both itself (UR-24).
- **Setting device time** (VERIFIED, `set_time_unknown_pps`): "a 2-step process, and will take at most 2 seconds", and "when changing clock sources, a previously set time will most likely be lost … set the time after changing the clock source". v3 sets the clock source, then the time source, in that order (`v3/cpp/uhd_usrp/multiusrp.cpp:332-347`, cited by the spike).
- **Sensors** (VERIFIED, `uhd/usrp/usrp.h:448`, `uhd/types/sensors.h:55-121`): `uhd_usrp_get_mboard_sensor` and `uhd_sensor_value_to_bool` read `ref_locked`.
- **Alignment** (VERIFIED by Phase 4 Review D in UHD master `0d7ed3b`, `rx_streamer_impl.hpp`, `get_aligned_buffs.hpp`): an alignment failure yields no samples, or only aligned ones, and discards packets whose timestamps disagree; never a partial channel set.
- **Overflow**: UHD restarts a continuous stream `OVERRUN_RESTART_DELAY` = 0.05 s after an overflow (VERIFIED, audit Finding 3; MR-3).
- **The X310 values** of MockRadio's `x310-like` 1.1.0, with the sources MR-3 marks (spec 09 §2).
- **The spike** (`spike/uhd`, VERIFIED on its fake device and against libuhd with no device): the C API slice of ~40 functions, the anchor-and-extrapolate Authority, the thread structure, and findings K1–K13.
- **INFERRED** (checked on the bench, `bench.md`): the device lead, the delivery allowance, the restart lead, the in-flight window and the release window of §3; how many timed UBX commands the device's queue holds before it back-pressures (UR-24); which UHD errors mean a lost device (UR-29); the drift bounds of UR-8; and every INFERRED value of UR-9. **Measured on the bench and applied** (design-notes §11, the owner's decision of 2026-09-30): the X3x0 ignores the time of a continuous receive stream's stop and stops at once (VERIFIED: UHD 4.10's `radio_rx_core.v` and `hw_b8_raw_rx_timed_stop`), so UR-25 hands the device no timed stop; the X300 drops a timed start-of-burst at the tick its previous burst ended (`hw_b8_raw_burst_gap`), so UR-23 continues the device burst there.

## 3. Model

```text
                         runtime (server catalogue / test assembler)
                               │ open(args) ──► Arc<dyn Device> ◄── FakeDevice::new(..) (tests only)
               ┌───────────────┴────────────────┐
         DeviceAuthority (Authority)        UhdRadio (Provider, not stepped)
         root = device master clock           │ prepare: apply, verify, declare clocks
         now = anchor + host elapsed          │ arm: streamers, transmit clock on the lattice
         uhd-clock: re-anchor every 100 ms    │ start(T0): receive clock at T0, timed start
         next_wakeup: nap ≤ 20 ms             │
                                              │
            threads:  uhd-control ── ActionReceiver (MA-14b loop, 1 ms): books Actions, releases
                                     held timed commands, checks reference and device time
                      uhd-rx ─────── owns the receive streamer: recv → blocks → Links;
                                     RX_OVERFLOW on the hot path; performs receive switches
                      uhd-tx ─────── owns the transmit streamer: bursts in target order → send,
                                     BurstTracker; async reports; performs transmit switches

 Kernel side (spec 19): data thread steps the capture Sink (KC-46); KC-21a waits for uhd-control to
 finish a Session's Actions; a DEVICE_LOST from uhd-rx stops the radios at once (MA-9a, KC-46b).
```

A tick of the Run's primary root is one master-clock tick of the device (200 MHz). Every SampleClock is `root_ticks_per_tick = N` for the device's integer decimation `N` (UR-12).

The Module's own constants, all INFERRED and measured at bench step B8, are: the **device lead** 2 ms (the lead it needs from receipt, UR-21, UR-24); the **delivery allowance** 3 ms (UR-14; the declared lead is their sum, 5 ms); the **restart lead** 50 ms (UR-25); the **in-flight window** 10 ms (UR-23); the **release window** 3 ms (UR-24).

## 4. Rules

### Identity and the device boundary

- **UR-1** The Module is `ModuleDescriptor { id: ezsdr.radio.uhd, version: 0.1.0, kernel_api: 4.0.0, roles: [Provider, Authority], vocabularies: [{ radio, ^1.3.0 }], deployment: InProcess, impl_hash: Some(ContentHash::of_bytes(b"ezsdr.radio.uhd 0.1.0")) }`, returned by `ezsdr_radio_uhd::descriptor()`; `module_ref()` returns its `{ id, version }`. A runtime registers it with `Factories { provider: true, authority: true }`. *Checked by `ur_01_the_descriptor_registers`.*
- **UR-2** Everything the Provider and the Authority do to a device goes through the object-safe trait `ezsdr_radio_uhd::Device: Send + Sync`, whose methods are exactly:

  ```rust
  fn describe(&self) -> serde_json::Value;           // identity for the Manifest (UR-30)
  fn fidelity(&self) -> Fidelity;                    // UR-31
  fn master_clock_rate(&self) -> u64;                // integer Hz
  fn channels(&self, dir: Dir) -> usize;             // Dir::{Rx, Tx}
  fn front_end(&self, dir: Dir, chan: usize) -> Result<String, DeviceError>;  // UHD's name, e.g. "UBX RX" (UR-5)
  fn set_sources(&self, clock: &str, time: &str) -> Result<(), DeviceError>;
  fn set_time_zero(&self, at_next_pps: bool) -> Result<(), DeviceError>;
  fn time_now(&self) -> Result<i64, DeviceError>;    // master-clock ticks since the time was set
  fn ref_locked(&self) -> Result<Option<bool>, DeviceError>;  // None: the device has no such sensor
  fn apply(&self, dir: Dir, chan: usize, s: &Settings, at: Option<i64>) -> Result<Applied, DeviceError>;
  fn rx_open(&self, channels: usize) -> Result<(), DeviceError>;
  fn rx_start(&self, at: i64) -> Result<(), DeviceError>;
  fn rx_stop(&self, at: Option<i64>) -> Result<(), DeviceError>;
  fn rx_recv(&self, n: usize, timeout: std::time::Duration) -> RxRecv;
  fn tx_open(&self, channels: usize) -> Result<(), DeviceError>;
  fn tx_send(&self, samples: &[&[Iq]], at: Option<i64>, sob: bool, eob: bool,
             timeout: std::time::Duration) -> Result<usize, DeviceError>;
  fn tx_async(&self, timeout: std::time::Duration) -> Option<TxReport>;
  fn close_streams(&self);
  ```

  with `Iq = [f32; 2]` (UHD's `fc32`); `Settings { rate, freq, gain: Option<f64>, antenna: Option<String> }`, `None` leaving a setting alone; `Applied { rate, freq, gain: f64 }`, read back after an untimed change; `DeviceError { lost: bool, message: String }`, `lost` meaning the device is gone (UR-29); `RxRecv` one of `Samples { first_tick: i64, samples: Vec<Vec<Iq>> }` (one vector per channel, all the same length ≥ 1), `Overflow { out_of_sequence: bool }`, `LateCommand`, `Alignment`, `BadPacket`, `Timeout` and `Failed(DeviceError)`; `TxReport { code: TxCode, tick: Option<i64>, channel: usize }` with `TxCode` one of `BurstAck`, `Underflow`, `UnderflowInPacket`, `SeqError`, `SeqErrorInBurst`, `TimeError`, `Other(i32)`. Ticks are master-clock ticks; no floating-point time crosses the trait. *Checked at compile time (`ur_02_device_is_object_safe_and_shared`).*
- **UR-3** `UhdDevice` (module `src/uhd.rs`, feature `uhd`) implements `Device` on UHD's C API. The module is the crate's only `unsafe` code (GZ-3). It declares by hand exactly the functions it calls — `uhd_get_last_error`, `uhd_usrp_last_error`; `uhd_string_vector_{make,free,size,at}`; `uhd_usrp_{find,make,free,get_pp_string,get_master_clock_rate,get_time_now,set_time_now,set_time_unknown_pps,set_command_time,clear_command_time,set_clock_source,set_time_source,get_mboard_sensor,get_mboard_sensor_names}`; `uhd_sensor_value_{make,free,to_bool}`; `uhd_usrp_{get,set}_{rx,tx}_{rate,gain}`, `uhd_usrp_set_{rx,tx}_freq`, `uhd_usrp_get_{rx,tx}_freq`, `uhd_usrp_set_{rx,tx}_antenna`, `uhd_usrp_get_{rx,tx}_num_channels`, `uhd_usrp_get_{rx,tx}_subdev_name`; `uhd_{rx,tx}_streamer_{make,free,max_num_samps,last_error}`, `uhd_usrp_get_{rx,tx}_stream`, `uhd_rx_streamer_recv`, `uhd_rx_streamer_issue_stream_cmd`, `uhd_tx_streamer_send`, `uhd_tx_streamer_recv_async_msg`; `uhd_rx_metadata_{make,free,has_time_spec,time_spec,error_code,out_of_sequence,strerror}`; `uhd_tx_metadata_{make,free}`; `uhd_async_metadata_{make,free,channel,has_time_spec,time_spec,event_code}` (all present in UHD 4.10.0's headers, Review J; the two `subdev_name` calls, added for UR-5 on 2026-09-30, in `usrp.h` of v4.10.0.0) — with the structs `uhd_stream_args_t`, `uhd_stream_cmd_t`, `uhd_tune_request_t`, `uhd_tune_result_t` laid out as the UHD 4.x headers lay them out. Every call's `uhd_error` other than `UHD_ERROR_NONE` becomes `DeviceError { lost, message: "<call>: UHD error <code>: <text>" }`, the text read from the handle the call was made on — `uhd_usrp_last_error` under the control-call mutex, `uhd_{rx,tx}_streamer_last_error` by the streamer's owner — and from `uhd_get_last_error` only for a call on no handle, because UHD's global string is overwritten by every other thread's successful call ("None") (Review L, P1-2). A streamer value owns its handles from their creation and is moved into its `Arc` (Review L, P0-1: a copy freed them twice), and an open releases the old streamer before it makes the new one (Review L, P1-3). Streams are `fc32` on the host and `sc16` on the wire (`radio.perf.wire_bytes_per_sample` 4). **Time conversion** (TM-20): a tick `t` is sent as `full = t.div_euclid(mcr)`, `frac = t.rem_euclid(mcr) as f64 / mcr as f64`; a time spec `(full, frac)` is read as `full · mcr + round(frac · mcr)`, rounding to nearest, ties away from zero, with `checked` arithmetic (an overflow is a `DeviceError`); a tick converted to a time spec and back is the same tick for every tick in `0 ..= 2^53` (`rem < mcr < 2^28`, so the round trip is exact). `open` refuses a device whose master clock rate is not a positive whole number of hertz. **Threads.** The handles are shared by the Module's threads under two rules: every **control call** (`apply` with its `set_command_time`…`clear_command_time` bracket, which is per-motherboard state; `set_sources`, `set_time_zero`, `time_now`, `ref_locked`; and the timed stream commands of UR-15, UR-17 and UR-25) is made under one `UhdDevice` mutex, and a time read used for an anchor or a relation takes its host brackets around `Device::time_now`, which takes the mutex inside, so that a read that waited for the mutex is widened and UR-7's 1 ms rule discards it (the `Device` trait has no bracketed read; Review L, deviation 6); and each **streamer** has one owning thread at a time — uhd-rx owns the receive streamer (`recv`, the stream commands, and its reopen, UR-25), uhd-tx the transmit streamer (`send`, `recv_async_msg`, and its reopen) —, each streamer's handle being kept alive by an `Arc` its owner holds, so that `close_streams` frees only a streamer no thread holds (UR-16). `UhdDevice` is `Send + Sync` on that basis, stated at its `unsafe impl` (INFERRED from UHD's documented thread safety of `multi_usrp` control calls; the bench runs every step with these threads). *Checked by `ur_03_time_specs_round_trip` (default build: the conversion functions live outside `uhd.rs`), and with the feature by `uhd_api_find_returns`, `uhd_api_open_of_an_absent_device_is_an_error_with_uhd_s_text` and `uhd_api_struct_sizes_match_the_headers`.*
- **UR-4** `ezsdr_radio_uhd::open(args: &str) -> Result<Arc<dyn Device>, String>` opens the device UHD's device string `args` names (`uhd_usrp_make`). Built without the feature `uhd` it returns `Err("ezsdr.radio.uhd: built without UHD (feature `uhd`)")`. It never returns a `FakeDevice`, whatever `args` says (GZ-9). A runtime calls it once per binding, and the Provider and the Authority built from that binding share the returned object (UR-6). *Checked by `ur_04_open_without_the_feature_refuses` and `ur_33_no_document_selects_the_fake_device`.*

### Construction and the Authority

- **UR-5** `UhdRadio::from_binding(binding: &Binding, device: Arc<dyn Device>) -> Result<UhdRadio, ModuleError>` refuses with `Rejected`: a `module` other than UR-1's; a `profile` other than `x310-ubx`, `x310-obx` or `x310-cbx` 0.1.0 (absent is refused); a `feed`; a selector key other than these, or one of the wrong kind or out of range; a device whose master clock rate is not the profile's 200 000 000 Hz (reason `"UR-5: profile <p> needs a 200 MHz master clock; the device runs at <n> Hz"`); and a device that has fewer channels in a direction than the profile's (reason `"UR-5: profile <p> needs <k> <rx|tx> channels; the device has <m>"`) or whose front end on one of those channels `Device::front_end` names otherwise than the profile's (`UBX…` for `x310-ubx`, `OBX…` for `x310-obx`, `CBX…` for `x310-cbx`, as UHD names them: `UBX RX`, `OBX TX`, `CBX-120 TX`; reason `"UR-5: profile <p> needs <UBX|CBX> front ends; <rx|tx> channel <c> is `<name>`"`). The last two exist because UHD clips a tune to the front end's range widened by the DSP's reach (min(DSP range, bandwidth / 2), `multi_usrp_utils.hpp`) without a warning — it is in `tune_result.clipped_rf_freq` and the read-back, which UR-12 records but does not refuse — after the RF envelope (RM-19) passed the claimed frequency: `x310-ubx` on a CBX would transmit at about 1.18 GHz (1.14 GHz on a CBX-120) a Run the envelope allowed at 1 GHz (VERIFIED, UHD 4.10.0.0; Review of 09f11b4, P2-1). A real X310 with one CBX in slot A and slot B empty reports 2 + 2 channels, channel 0 the CBX and channel 1 UHD's unknown board (`db_unknown.cpp`), so only the profile's own channels are checked:

  | Selector key | Kind | Default | Meaning |
  |---|---|---|---|
  | `args` | str, required | — | UHD's device string; read by the runtime's `open` (UR-4) and recorded (UR-30) |
  | `id` | str, one `ResourceId` segment matching `^[a-z][a-z0-9_]*$` | `"usrp"` | the device node's path and the `<id>` of UR-30's section names |

  *Checked by `ur_05_from_binding_refusals`.*
- **UR-6** The Authority role is taken by the radio's own binding: the BindingProfile's `authority` names the binding of `ezsdr.radio.uhd`, and the runtime builds `DeviceAuthority::new(device, clocks, clock_source, time_source, args)` from it, with the same device object as the Provider (SB-22c; spike K4). The Provider refuses in `prepare` a primary root that is not its own device's: the root's `EpochRef::Arbitrary { set_by }` must be `"ezsdr.radio.uhd.set_time_now:<args>"` or `"ezsdr.radio.uhd.set_time_unknown_pps:<args>"` with the Provider's own `args` (reason `"UR-6: the primary root is not this device's; bind the Authority to the radio's own binding"`). *Checked by `ur_06_the_provider_refuses_another_root`.*
- **UR-7** `DeviceAuthority` implements `Authority` with pacing `Device`. `new` sets the reference sources (`set_sources(clock_source, time_source)`, the clock source first), then sets the device's time to zero — at the next PPS edge (`set_time_zero(true)`, up to 2 s) when `time_source` is not `internal`, at once otherwise — and registers the device's master clock as a new Root with rate `master_clock_rate / 1` and UR-6's epoch. Its `TimeAuthority`:
  - `now(root)` extrapolates from an **anchor** (a host `Instant` and a device tick read together) by the host time elapsed since, and is monotonic (a value never below one it returned before). The anchor is re-read from the device by a thread of the Authority's own, `uhd-clock`, every 100 ms for as long as the Authority lives, and at every nap of `next_wakeup` and `wait_until` — a read whose host bracket is wider than 1 ms is discarded and the previous anchor kept (Review K, N-P2-5) —, so the extrapolation never runs on the host clock alone for more than 100 ms, whether or not a client call is running (Review J, P1-4); `now(host.monotonic)` is the nanoseconds since the Authority was built; `now` of a domain derived from the root is the floor conversion (TM-16c);
  - `schedule(t, f)` requires `t` on a governed domain and a tick of the root (TM-16c's `Inexact` otherwise), and at or after the last instant `next_wakeup` fired (`InPast` otherwise; TM-16c as KG-9 amends it for a paced Authority): an accepted `t` at or before `now` fires at the next `next_wakeup`, which returns `t`. It keeps callbacks in `(tick, sequence)` order and wakes a waiting `next_wakeup`; `cancel` removes a pending callback, reports whether it was pending, and wakes a waiting `next_wakeup` (MA-29 as KG-3 amends it);
  - `next_wakeup()` returns `None` at once when nothing is scheduled; otherwise it waits — in naps of at most 20 ms, each followed by a re-anchor, and woken early by `schedule` and `cancel`, after which it re-evaluates (returning `None` if a cancel emptied the schedule) — until `now(root)` reaches the earliest scheduled instant, fires every callback due at that instant in order, including ones they schedule at it, up to 1 000 (TM-17b), and returns the instant; callbacks observe `now()` at or after their instant (TM-16c as KG-9 amends it);
  - `wait_until(t)` sleeps the same way until `now` reaches `t`;
  - it governs its root, the root's derived domains and `host.monotonic` (TM-16a, TM-16a1), and its descriptor is `{ module: module_ref(), governs: [root, host.monotonic], pacing: Device }`.

  A device time read that fails, or that is bracketed more widely than 1 ms, leaves the anchor as it was, so `now` goes on advancing with the host clock from the last good read; both are counted, by `DeviceAuthority::failed_reads()` and `discarded_reads()`, not in the Manifest — an Authority has no section of its own (MA-29) — and the bench prints them (B2); a lost device is found and reported by the Provider (UR-29), not by the Authority. `uhd-clock` ends when the Authority is dropped. *Checked by `ur_07_the_authority_paces_to_the_device`, `ur_07_schedule_wakes_a_waiting_next_wakeup`, `ur_07_schedule_accepts_an_instant_already_passed`, `ur_07_cancel_wakes_a_waiting_next_wakeup`, `ur_07_now_is_monotonic_across_a_reanchor`, `ur_07_now_tracks_the_device_while_no_call_runs` and `ur_07_the_time_is_set_at_the_next_pps_with_an_external_source` and `ur_07_a_read_bracketed_wider_than_1_ms_is_discarded`.*
- **UR-8** `DeviceAuthority::relations()` returns the two relations measured in `new` right after the time was set (TM-18, KG-11). One device time read `t` is bracketed by host reads: the host's monotonic clock and its UTC, each read immediately before and after it. **To `host.monotonic`**: `ClockRelation { source: root, target: host.monotonic, measured_at: t, offset: the midpoint of the two monotonic reads, drift: 0.0, drift_uncertainty: 1e-4, uncertainty: the interval between them, method: "ezsdr.radio.uhd.host_bracket", valid: { from: t, to: None } }` — the same pair of reads the anchor of UR-7 starts from. **To `utc`**: the same with the UTC reads, `drift_uncertainty: 1e-5` and `method: "ezsdr.radio.uhd.host_utc_bracket"`; its `uncertainty` excludes the host clock's own error against UTC, which the Module cannot know (TM-18 as KG-11 amends it). The drift bounds are INFERRED (the X310's internal reference is specified to a few ppm; the host's monotonic clock is a crystal of unknown quality; the host's UTC is disciplined by whatever the host runs); the bench records the drift it observes between re-anchors (B2). *Checked by `ur_08_the_relations_bracket_a_device_read`.*

### The Provider's lifecycle

- **UR-10** `instance()` returns `ProviderInstance { id: <id>, module: module_ref(), profile: the binding's, tree: the description's tree for <id> (RM-2), fidelity: device.fidelity() (UR-31), driving: { stepped: false }, arm_after: [], min_command_lead: Some(Duration(host.monotonic, 5 000 000)), sections: UR-30's }`. *Checked by `ur_10_instance`.*
- **UR-11** `coerce(request)` is the description's `coerce` for `<id>` (RM-26): pure, no device call (MA-11). *Checked by `ur_11_coerce_is_the_descriptions` (19.5 Msps → 20 Msps; 7 GHz rejected; four channels refused).*
- **UR-12** `prepare(fragment, ctx)` refuses with `Unsupported` a class other than HardwareInLoop or Hardware (reason `"UR-12: ezsdr.radio.uhd runs HardwareInLoop or Hardware, not <class>"`), and with `Rejected`: a second call (one fragment per instance, as MR-7); a fragment whose instance or role is not this Module's Provider; a fragment content with no `Requested`; any `rejected` entry of its own `coerce`; a primary root that is not its device's (UR-6); a channel count above `device.channels(dir)`; an attached link that is not a `StreamOut` on the fragment's `rx` port, or one whose policy is `Block` (a device cannot wait for a consumer; it overflows); several links on `rx` are allowed, each receiving every block (UR-17). Then, for each direction whose channel count is > 0, it **configures the direction** (below). It declares the SampleClock of each stream whose count is > 0, `<id>/rx` and `<id>/tx`, on the primary root with `root_ticks_per_tick = N`. It keeps `ctx`'s handles and returns `PrepareReport { fragment, effective: RM-5's ten keys with the applied values, coercions: its coerce's, warnings: [] }` (MA-12). **Configuring a direction** — here, when a stream is enabled or its channel count raised (UR-25), and nowhere else — applies the direction's full current configuration (rate, frequency, gain, antenna) to every channel of its count, untimed, and reads it back: the read-back rate must be exactly the claimed one, with `N = round(200 000 000 / rate)` in 1…512 and `200 000 000 / N` computed in `f64` equal to `rate` — MockRadio's rule (MR-3's `Profile::decimation`), so that every one of UR-9's 512 rates is accepted (Review L, P0-2: an exact-arithmetic reading refused 487 of them, `200e6/3` among them); the SampleClock's ratio is `N / 1`, exact whatever the `f64` rate's last bit (K13's hazard was computing `N` by float division) —, else the configuration is refused (`"UR-12: the device applied <rate> S/s for the claimed <claim>"`, or `"UR-12: <rate> S/s is no decimation 1…512 of 200000000 Hz"`); read-back frequencies and gains are recorded beside the claims in the `applied` section, with their difference, and do not refuse. *Checked by `ur_12_prepare_refusals`, `ur_12_the_applied_values_are_recorded`, `ur_12_a_rate_the_device_does_not_apply_is_refused` and `ur_12_every_advertised_rate_is_accepted`.*
- **UR-13** `arm()` records the arm instant `A = now(root)` and `S = A + startup_latency_ns`; when `clock_source` is not `internal`, refuses with `Rejected` a reference that `ref_locked` reports unlocked (`"UR-13: the <clock_source> reference is not locked"`); opens the receive streamer for the receive channels when their count is > 0 and a link is attached, and the transmit streamer when the transmit count is > 0; and registers the transmit SampleClock, when declared, at the first instant at or after `A` on its lattice (RM-25, TM-13e as KG-14 amends it). It radiates nothing (MA-13). *Checked by `ur_13_arm_cases` and `ur_15_every_clock_starts_on_its_lattice`.*
- **UR-14** The **control thread** `uhd-control`, started by `start`, runs until `stop` a loop that every millisecond drains the `ActionReceiver` with MA-14b's loop, **booking** each Action as UR-21, UR-24, UR-25 and UR-26 say before taking the next: it validates, decides and records what the Action asks and hands device work to its owner — a burst to uhd-tx, a stream switch to uhd-rx or uhd-tx, a timed command to its own release list — and never waits for a device instant (Review J, P1-7). In the same loop it releases held timed commands (UR-24) — a command already inside the release window when it is booked is released before uhd-control takes the next Action (Review K, N-P2-8) —, and every 500 ms it runs UR-27's reference check and reads the device's time (UR-29). The Module's **delivery allowance** (MA-10, KG-8) is 3 ms: the poll period plus the time to book the Actions ahead in the queue; its **device lead**, the lead it needs from receipt, is 2 ms (§3). *Checked by `ur_14_actions_are_finished_before_the_next_recv` (with KC-21a: a `SetParameter` returns after the device call, the fake's `apply` taking 20 ms) and `ur_14_the_control_thread_never_waits_for_a_device_instant`.*
- **UR-15** `start(at)` takes `T0 = at` converted to the root and rounded up (the coordinator always passes `Some`). A `T0` before `S` emits `radio.LATE_COMMAND { key: null, requested: T0, applied: S }` and returns `Rejected` (`"UR-15: the start at <T0> precedes the device's start-up at <S>; the profile needs ezsdr.time.start_lead_ns ≥ 2000000000"`), and no stream starts (MR-11's form). Otherwise, when the receive streamer is open, it registers the receive SampleClock with origin T0 — on the lattice, KC-15 — and issues a timed continuous start at T0 (`rx_start(T0)`), so that the first sample is tick 0 at T0; then it starts uhd-rx, uhd-tx and uhd-control — uhd-rx and uhd-tx whether or not their direction has a stream (an owner without a streamer idles), so that every stream a later `cold` change enables has a running owner (Review K, N-P0-1). `start` returns without waiting for T0. *Checked by `ur_15_start_cases` and `ur_15_every_clock_starts_on_its_lattice`.*
- **UR-16** Every thread body runs under `catch_unwind`; a panic is recorded in the `rejected` section and, in uhd-rx or uhd-tx, reported as `DEVICE_LOST` with the message `"a Provider thread panicked"` (MA-9a), because the stream it served is gone. Every join the Provider makes is bounded: 1 s per thread, so that its `stop` and `cleanup` together stay within RS-8a's 5 s step deadline on a healthy device; a thread that does not join in time is recorded in `rejected` and left detached, and then `cleanup` does **not** call `close_streams` for the streamer that thread owns — it records the leak instead — because the thread may still be inside a UHD call on that streamer (UR-3; Review J, P1-8). *Checked by `ur_16_a_panicking_thread_is_a_lost_device`, `ur_16_a_wedged_thread_does_not_wedge_stop` and `ur_16_cleanup_keeps_the_streamer_of_a_detached_thread`.*

### Receive

- **UR-17** uhd-rx calls `rx_recv(block_len, 100 ms)` in a loop — while a cut is pending, for no more samples than up to the cut and with the wait UR-25 bounds. A `Samples` result's first tick `f` becomes the receive sample index `k = (f − origin) / N` (an `f` off the lattice is rounded to the nearest sample and counted in `stats.rx_off_lattice`). A block `[k, k + len)` after the expected next index `e` carries `GAP_BEFORE` and `lost = k − e`, plus the flags UR-18 and UR-19 leave pending; a block that overlaps what was delivered (`k < e`) is trimmed to `[e, k + len)` and counted (`stats.rx_overlapping`), and one that the trim leaves empty is dropped (SC-18 publishes no empty block). Its bytes are the samples in SC-4's planar `cf32` layout, written into a buffer from a `HostPool` (HD-2) and published as `SampleBlock::new_host(header, HOST_MEMORY, bytes, 8)` (KA-3) with `direction: rx`, `valid` full, `contract: ezsdr.stream.cf32`, to every attached link, the same `BlockRef` to each (SC-11); a publish that does not return `Accepted` is counted (`stats.link_drops_seen`) — the drop-class link records it too. `Timeout` delivers nothing. A `LateCommand` at the stream's start means the device missed T0: the Provider emits `radio.LATE_COMMAND { key: null, requested: T0, applied: T1 }`, issues a new timed start at T1, the first lattice instant at or after `now + 50 ms` (the restart lead), and the first block then carries `GAP_BEFORE` with `lost` its index — the origin staying T0 (SC-18; TM-13b as KG-14 amends it). A missed timed start of a stream a `cold` change started (UR-25's `e₂`) is handled the same way, with `e₂` in place of T0 (Review K, N-P2-10). A `LateCommand` while the stream is being cut (a stop or a switch) is not a missed start: uhd-rx stops the stream untimed and never restarts it (Review M, P1-A). A block whose first tick precedes the stream's origin, or the instant the previous stream's untimed stop was issued, is the old stream's, still in flight after its stop (the bench: one or two blocks), and is dropped and counted (`stats.rx_before_origin`), not published on the new clock (Review M, N-3; Review N, B1: after a late switch the old tail can follow the new origin). *Checked by `ur_17_blocks_carry_the_device_timestamps`, `ur_17_a_missed_start_restarts_with_a_gap`, `ur_17_an_overlap_trimmed_to_nothing_is_dropped`, `ur_17_blocks_reach_every_link` and `ur_26_an_orderly_stop_does_not_restart_the_stream`.*
- **UR-18** An `Overflow { out_of_sequence: false }` is RM-17's overrun: the next block carries `GAP_BEFORE | RESTARTED` with `lost` its whole time jump, and when it arrives `radio.RX_OVERFLOW { cause: overrun, lost, restart_gap_ns: lost · N · 10⁹ / 200 000 000 }` (the jump in nanoseconds) is emitted with time `TimePoint(<receive clock>, e)` (RM-11, UR-20). An `Overflow { out_of_sequence: true }` or a `BadPacket` is RM-18's sequence error: `GAP_BEFORE | SEQ_DISCONTINUITY` with `lost` the jump and `RX_OVERFLOW { cause: sequence, lost, restart_gap_ns: 0 }`. A jump with no preceding report carries `GAP_BEFORE | SEQ_DISCONTINUITY` and no event (a loss the device did not announce). *Checked by `ur_18_an_overrun_is_rm_17s_gap`, `ur_18_a_sequence_error_is_rm_18s_gap` and `ur_18_an_unannounced_jump_is_a_seq_discontinuity`.*
- **UR-19** An `Alignment` result means the device discarded samples to keep the channels aligned: UHD never delivers part of a channel set (§2), so the next block carries `GAP_BEFORE | SEQ_DISCONTINUITY` on every channel with `lost` its time jump, and `radio.ALIGNMENT_ERROR { lost }` is emitted on the control path from the receive stream when that block arrives. SC-31a's per-channel `ALIGNMENT` is never set by this Module. *Checked by `ur_19_an_alignment_error_is_a_whole_stream_gap`.*
- **UR-20** `radio.RX_OVERFLOW` is emitted on the hot path (`EventSink::emit`) from uhd-rx with RM-24's 17 bytes and the `EventHandle` resolved in `prepare` for `(<id>/rx, radio.RX_OVERFLOW)`; every other event is emitted with `emit_control` from the thread that decided it, with RM-11's source, time and payload (RM-11; spike K10). *Checked by `ur_20_rx_overflow_is_emitted_on_the_hot_path` (the delivered payload is the byte array and `RxOverflowPayload::from_payload` reads it).*

### Transmit

- **UR-21** On a `TxBurst` uhd-control refuses with `radio.COMMAND_REJECTED` (RM-13, MR-16's list): a target other than `<id>/tx`; a transmit count of 0; an `at` not in the current transmit SampleClock; a `size_bytes` that is not a positive multiple of `8 · channels`; waveform bytes not in the input store or with a non-finite component; a repeated waveform longer than `repeat_max_samples`; non-empty `metadata`; a start before `S`; a start equal to a held burst's. (A start at or before the open burst's next sample is not refused here: uhd-tx's preemption, below, decides it — Review L, deviation 9.) Otherwise it decides with `LatePolicy::decide(clocks, at, now', 2 ms)`, where 2 ms is the device lead (RM-14 as VE-2 amends it) and `now'` is the first transmit sample at or after the later of its current instant and the transmit clock's origin less the device lead — so that a burst admitted right after a `cold` transmit change, whose clock starts only at `e₂` (UR-25), is late and not `OnTime` (RM-15 as VE-2 amends it; Review K, N-P0-1). `OnTime` holds the burst at `at`; `SendAsap` moves it to the first transmit sample at or after `now' + 2 ms`, emits `radio.TIME_ERROR { cause: late, outcome: send_asap, late_by_ns, target }` and holds it, with `BurstOpen.late` and `requested_target` as MR-17 sets them; `Drop` and `PlanViolation` do not transmit it and emit `TIME_ERROR` with that outcome. A held burst is handed to uhd-tx. **Preemption.** A held burst that would start while another burst is open is decided again by uhd-tx when it takes it, between two buffers of the open burst, against the first sample of the open burst uhd-tx has not yet handed to the device — which only uhd-tx advances, so the decision cannot race the hand-over (Review K, N-P1-2): a start before it is late, and the burst's `LatePolicy` applies as above, the event emitted from uhd-tx; a move that would land on another held burst's start refuses the moved burst with `TIME_ERROR { refused }` and `COMMAND_REJECTED` (RM-14's form) (RM-15 as VE-2 amends it; Review J, P0-2). *Checked by `ur_21_txburst_refusals`, `ur_21_late_policies_on_the_device_lead`, `ur_21_an_untimed_send_is_on_time_after_its_delivery` (a Session `radio.send` with no `at`, admitted at `now + 5 ms` by RS-19, received at most 3 ms later with no burst open, is `OnTime` and emits nothing) `ur_21_a_burst_inside_the_in_flight_window_is_late` and `ur_21_a_burst_before_its_clock_s_origin_is_late`.*
- **UR-22** uhd-tx transmits a burst by sending its waveform with start-of-burst and the time spec of its start; a burst without `repeat` ends with end-of-burst on its last samples. A repeated burst is sent again and again from host memory, each repetition without start-of-burst and without a time spec, never with end-of-burst until the burst ends (UR-23); the device receives one contiguous burst, so the wrap has no gap (v3 behaviour 1). Every sent buffer is fed to the Kernel's `BurstTracker` as a transmit block (SC-29), the first with `START_OF_BURST` and `BurstOpen`, so the Manifest's `bursts` section holds SC-28's records; a send that does not complete within 1 s ends the burst (`BurstTracker::stop`), is recorded in `rejected`, and the burst is not resumed. Between buffers, and while idle, uhd-tx reads the device's asynchronous reports (`tx_async` with a zero timeout; UR-28). *Checked by `ur_22_repeat_is_continuous_across_the_wrap` (on `FakeDevice`, which records a restart for a start-of-burst inside a burst: the received loopback holds the waveform back to back for three wraps, no restart is recorded, and the burst record counts the wraps) and `ur_22_a_single_burst_ends_with_end_of_burst`.*
- **UR-23** Held bursts are transmitted in target order (RM-15). A burst ends at the end of its waveform (without `repeat`), at the start of the next held burst as UR-21 decided it (the current one is sent up to the sample before the next start), at a `Stop` for `<id>/tx` or `<id>`, at a `cold` transmit change (UR-25), or at the Provider's `stop`. **Device bursts.** Where the next burst starts at the current one's next sample — held at that start, or preempting the current one and decided there by UR-21 — the device burst continues: the current one's last buffer goes without end-of-burst and the next one's first without start-of-burst or time spec, because the X300 reports a timed start-of-burst at the tick its previous burst ended as late and drops that burst (design-notes §11 F3; `hw_b8_raw_burst_gap`); the two Kernel bursts keep their own `START_OF_BURST`/`END_OF_BURST` blocks and records, and one `BURST_ACK` answers both. A next burst that starts later is a new device burst: the current one's last buffer carries end-of-burst — or, when that buffer already went out, an empty buffer does (Review L, P1-4: no timed start-of-burst inside an un-ended burst) — and the next starts with start-of-burst and its time spec. A Kernel burst's end is not at once the device burst's: its last buffer goes without end-of-burst, so that a burst booked at its next sample after that buffer went out still continues it (Review N, B3: the last buffer goes out up to the in-flight window before the end, and admission needs only the 5 ms lead); when no burst is booked there by the time that sample is a device lead (2 ms) away, or another burst is next, the device burst is ended with an empty end-of-burst buffer, before it runs dry (the X300 underflows otherwise). A device burst left open for a continuation that does not come (the next burst stopped, cancelled or refused first) and one whose send failed or came up short (Review N, N7) are ended the same way. INFERRED: that one sample of gap suffices at every rate — the bench measured it at 1 Msps; the FPGA checks a timed start only after a cycle in `ST_IDLE` (`radio_tx_core.v`), so at 200, 100 or 66.7 Msps a gap of 1–3 samples may be late too (Review N, N1; Phase 8 measures). uhd-tx keeps at most the in-flight window, 10 ms, of samples handed to the device ahead of its time, pacing itself with `now(root)`, so that a burst stopped at instant `s` ends no later than `s + 10 ms`; its record's end is the last sample actually handed over (RM-16 as VE-2 amends it). *Checked by `ur_23_a_burst_ends_at_the_next_bursts_start` (the next burst 20 ms ahead, outside the window; one device burst: one start-of-burst, one end-of-burst), `ur_23_a_burst_booked_at_a_sent_burst_s_end_continues_it`, `ur_23_a_stop_while_the_device_burst_waits_for_a_continuation_ends_it`, `ur_23_a_burst_alone_is_ended_before_it_runs_dry`, `ur_23_bursts_go_out_in_target_order` and `ur_23_a_stop_ends_the_burst_within_the_in_flight_window` (a margin of 20 ms, so that the fake's 50 ms acceptance cannot pass it); `FakeDevice` counts a timed start-of-burst sent inside an un-ended burst, and the first and `ur_21_a_burst_inside_the_in_flight_window_is_late` assert none.*

### Parameter updates

- **UR-24** A `hardware_timed` update — `radio.{rx,tx}.frequency_hz`, `radio.{rx,tx}.gain_db` — to `<id>` takes effect at `e`: `at` converted to the root and rounded up when present, otherwise the current instant plus the 2 ms device lead (UC-6 as KG-8 amends it). An `at` closer than 2 ms ahead is late: `radio.LATE_COMMAND { key, requested: at, applied: now + 2 ms }` and `e = now + 2 ms`. **Holding and release.** uhd-control does not hand a timed command to the device at receipt: UHD's command queue is in order and back-pressures ("A timed command will back-pressure all subsequent timed commands", §2), so a command far ahead would hold every later one behind it and could block uhd-control inside UHD (Review J, P1-6). It holds the command in its own list, ordered by `e`, and releases it — `apply(dir, chan, settings, Some(e))` on every channel of the direction (`set_command_time(e)`, the setting, `clear_command_time`), under the control-call mutex (UR-3) — when `e` is no more than the release window, 3 ms, ahead. A command whose `e` precedes a command already released is applied late: at the released command's instant, with `LATE_COMMAND`, so that the device queue's order is the effective order (UC-2). The timed stream commands of UR-25 (a start at `e₂`) and UR-17 (a restart) are issued by uhd-rx, which owns them, when it performs them, about a restart lead (50 ms) ahead; uhd-rx hands the device no timed stop (UR-25). They are not in uhd-control's list, so a retune released between a stream command's issue and its instant can precede it in the device's queue (INFERRED: whether stream commands share the device's command queue; B8 checks; Review K, N-P2-12; Review L, deviation 5). With 16 device commands — one per channel of its direction — held or released and not yet in effect, a new one that would exceed them is refused with `radio.COMMAND_QUEUE_FULL { key, depth: 16 }` and not applied (INFERRED: whether 16 UBX tunes fit the device queue without blocking is measured at B8). Each released command is recorded in `applied` with `e`; the value is the one admission already coerced (KA-6). A direction with no channel records the value in the configuration and applies nothing; enabling the direction applies it (UR-12, UR-25). *Checked by `ur_24_hardware_timed_updates` (lead, lateness and its applied instant, queue depth, both directions), `ur_24_an_untimed_retune_is_on_time_after_its_delivery`, `ur_24_a_far_future_update_does_not_delay_a_nearer_one`, `ur_24_the_device_queue_order_is_the_effective_order`, `ur_24_the_queue_counts_a_command_per_channel` and `ur_24_stop_cancels_held_commands`.*
- **UR-25** A `cold` update — `radio.{rx,tx}.channels`, `radio.{rx,tx}.sample_rate_hz` — is booked by uhd-control and carried out on the device by the stream's owner (UC-3 as KG-13 amends it; RM-21; RM-25 as VE-2 amends it). uhd-control first re-runs `coerce` over the configuration with the new value, and a rejection is `radio.COMMAND_REJECTED` with no change (RM-7). The effective instant `e` is `at` (rounded up) or the current instant, moved to at least `now + 50 ms` (the restart lead), an `at` closer than that also emitting `radio.LATE_COMMAND`. As RM-25 says, the old clock ends at `e₁`, the first instant at or after `e` on its lattice (`e` itself when no stream runs), and the new clock, when the new count is > 0, starts at `e₂`, the first instant at or after `e₁ + 50 ms` on its lattice. Before taking the next Action uhd-control ends the old SampleClock at `e₁` (`ClockRegistry::end`, which accepts a future instant) and declares and registers the new one at `e₂`, so that an Action admitted after this one (KC-21a) is judged against the new clock; then it hands the switch to the stream's owner and returns to its queue. **The switch**, performed by uhd-rx for the receive stream and by uhd-tx for the transmit stream: the owner delivers (receive) or transmits (transmit) the old stream up to `e₁` — uhd-rx discards samples at or after `e₁` and stops the stream untimed when its samples reach `e₁` (a block ending at or past it), recording the stop in `applied` with `e₁` and the instant it was issued; it hands the device no timed stop, because the X3x0 ignores a continuous stream's stop time and stops at once, which would end the stream up to its lead before `e₁` with the samples between lost and unflagged (VERIFIED: UHD 4.10's `radio_rx_core.v`, "timed STOP commands are not supported", and the bench's `hw_b8_raw_rx_timed_stop`, `hw_b8_cold_change_capture`; design-notes §11 F1). While a cut is pending uhd-rx asks `rx_recv` for no more samples than up to the cut, so that its last block ends at `e₁` and the stop follows about one delivery (2–4 ms on the bench, INFERRED) after it whatever `block_len` (Review N, B1), and waits no longer than to the cut plus one block plus the delivery allowance (3 ms), so that a stream that stopped yielding before `e₁` is ended soon after it and the start at `e₂` is not missed (§11 F2), while a slow link's last samples before the cut are still waited for (Review N, B2: UHD's `recv` waits per packet, and one cut short is followed by a `TIMEOUT` at once); a stream past that instant and silent for as long is taken to have ended and is stopped untimed all the same, while one still delivering, however late, is waited for. The start at `e₂` is on time while that delivery and the switch take less than the restart lead; uhd-tx ends the open burst at `e₁` (`BurstTracker::stop`) and cancels every held burst of the old clock starting at or after `e₁` with `radio.COMMAND_REJECTED { reason: "cancelled by a cold change" }` —, reopens its streamer when the channel count changed, **configures the direction** as UR-12 says — with the configuration that will be in effect at `e₂`: the change itself and every update admitted before it, while a held timed command with a later `e` stays held (UC-2; Review K, N-P2-9) —, on every channel of the new count, untimed, read back, and starts the new stream at `e₂` (a timed start for receive; the next burst's time spec for transmit). A configuration UR-12 refuses at the switch (a read-back rate that is not the claim) leaves the direction with no stream: the new clock is ended at `e₂` with no sample on it, and `radio.COMMAND_REJECTED` is emitted with UR-12's reason. **A change from 0 channels** has no stream to stop and needs no restart lead (RM-25, KG-13): while booking it, before taking the next Action, uhd-control itself opens the streamer — no thread owns a streamer that does not exist yet — and configures the direction as UR-12 says (device calls, not a wait for a device instant, so UR-14 holds, and KC-21a bounds them), then registers the new clock: for transmit at the first lattice instant at or after both `e` and the configuration's completion (an `at` already passed also emits `radio.LATE_COMMAND`), for receive at the first lattice instant at or after the later of `e` and `now + 50 ms`, with a timed start there (RM-25; Review L, P0-3) (a receive clock's origin is its first sample, TM-13b); then it hands the streamer to its owner, uhd-tx or uhd-rx, idle since `start` (UR-15). A burst admitted after this Action (KC-21a) is therefore on a configured, running transmit stream at the lead RS-19 gives it (spike K5's case: Python `tx.repeat`, §57, `minimal.py`) (Review K, N-P0-1). A change to 0 channels ends the old clock at `e₁` and starts nothing; until `e₁` the old stream still runs, and a change back from 0 channels booked before then is refused with `radio.COMMAND_REJECTED` (`"UR-25: the stream changed to 0 channels is still draining; enable it after its e₁"`; Review M, N-4). Once `Provider::stop` has begun, uhd-rx ignores a switch still in flight, and a switch never moves a cut already set later (Review M, N-1). Nothing between `e₁` and `e₂` is delivered or counted as a gap (UC-3). *Checked by `ur_25_a_cold_rate_change_starts_a_new_clock_on_its_lattice`, `ur_25_enabling_tx_applies_the_configuration`, `ur_25_tx_channels_from_zero_transmits_the_next_burst_on_time`, `ur_25_rx_channels_from_zero_starts_at_its_instant`, `ur_25_a_rate_change_admits_a_burst_on_the_new_clock` (booked before the switch, transmitted after it on the new clock), `ur_25_a_rate_the_device_does_not_apply_at_the_switch_is_rejected`, `ur_25_a_cold_change_the_envelope_refuses_changes_nothing`, `ur_25_the_receive_stop_is_recorded_when_it_is_issued`, `ur_25_the_old_stream_is_stopped_untimed_at_e1`, `ur_25_a_cold_receive_change_delivers_every_sample_before_e1`, `ur_25_a_stream_silent_before_e1_switches_before_e2`, `ur_25_a_long_block_at_a_low_rate_stops_the_stream_at_e1`, `ur_25_a_slow_link_at_a_low_rate_delivers_the_old_clock_to_e1`, `ur_25_the_switch_applies_the_configuration_in_effect_at_e2`, `ur_25_a_cold_transmit_change_cancels_the_held_bursts` and `ur_25_enabling_a_draining_stream_is_refused`.*
- **UR-26** An update to `radio.{rx,tx}.antenna`, or to any key or target UR-24 and UR-25 do not name, is refused with `radio.COMMAND_REJECTED` (admission refuses an antenna update anyway: RM-4 gives it no update class, RS-17). A `Stop` for `<id>/tx` ends the transmit side as UR-23 says; for `<id>/rx` it stops the receive stream with RM-16's tail (below); for `<id>` both, and it cancels every timed command still held (UR-24), while a command already released within the release window is not recalled and is recorded as issued (RM-16 as VE-2 amends it); any other target is `COMMAND_REJECTED`. Another Action kind (`SetTimer`, `PeripheralCommand`) is `COMMAND_REJECTED`. **`Provider::stop(mode)`** cancels the held timed commands, stops the transmit side first — every held burst ended as UR-23 says, end-of-burst sent, 100 ms allowed for the last `BURST_ACK`, uhd-tx joined — then the receive side: under `orderly` it issues the stop and keeps delivering samples up to the stop instant plus `stop_tail_ns` (1 ms), discarding later ones; under `abort` it stops (untimed, recorded in `applied`, and not again when the stream's tail reaches the cut: Review N, N4) and discards at once, publishing no sample at or after the stop instant. uhd-rx is told the stop instant as `stop` begins, before the transmit side's 100 ms, so that the tail and the abort are counted from the stop instant (RM-16; Review L, NONBLOCKING 9); it learns of it between two receive waits, up to one block later, and stops the stream untimed when its samples reach the cut, the cut discarding what follows (UR-25: no timed stop; Review M, P1-A); then it joins uhd-rx and uhd-control (UR-16) and records the stop instant in `timing`. A second `stop` does nothing. **`cleanup()`** stops what is still running, closes the streamers no detached thread owns (UR-16), writes UR-30's sections and drops every handle `prepare` kept (MA-7); the device object stays with the runtime. *Checked by `ur_26_stop_actions`, `ur_26_orderly_stop_delivers_the_tail_abort_does_not`, `ur_26_an_abort_publishes_nothing_after_the_stop_instant`, `ur_26_an_orderly_stop_does_not_restart_the_stream` and `ur_26_cleanup_is_idempotent`.*

### Device reports

- **UR-27** When `clock_source` is not `internal`, uhd-control reads `ref_locked` every 500 ms; the first read that returns `Some(false)` emits `radio.CLOCK_LOST { reference: frequency }` (fatal, default `abort`) once, from `<id>`. A read error is recorded and does not emit. The time reference (PPS) is not monitored (VE-3). *Checked by `ur_27_a_lost_reference_is_clock_lost`.*
- **UR-28** uhd-tx records every asynchronous report in the `async` section with its raw code, channel and tick. `BurstAck` is recorded only. `Underflow` and `UnderflowInPacket` emit `radio.TX_UNDERFLOW { cause: starved }`; `SeqError` and `SeqErrorInBurst` emit `radio.TX_UNDERFLOW { cause: lost }`; both from `<id>/tx` with time the report's tick in the transmit clock (floored), or `now` when it has none. `TimeError` emits `radio.TIME_ERROR { cause: late, outcome: late_at_device, late_by_ns, target }` from `<id>/tx`, where `target` is the start of the earliest burst uhd-tx has sent and not yet seen acknowledged and `late_by_ns` the report's tick less that start, or 0 without a tick (VE-3). `Other` is recorded only. *Checked by `ur_28_underflows_are_tx_underflow` and `ur_28_the_device_reports_a_late_burst`.*
- **UR-29** A `DeviceError` with `lost: true` from any streaming call (`rx_recv`, `tx_send`, `rx_start`, `rx_stop`) or from uhd-control's device time read every 500 ms (which finds a lost device in a transmit-only or idle Run too), or a receive stream that yields only `Timeout` for 1 s after T0 + 1 s while it should be streaming, makes the Provider emit `DEVICE_LOST` itself (MA-9a) once, with the error's message, and stop using the device; `stop` and `cleanup` then succeed without device calls that could block. `UhdDevice` sets `lost` for `UHD_ERROR_IO`, `UHD_ERROR_USB` and `UHD_ERROR_OS`, and for `UHD_ERROR_RUNTIME` on a streaming call only; a receive metadata error other than UR-18…UR-19's (`BROKEN_CHAIN` among them) is an error, not a lost device (INFERRED; `RUNTIME` is generic, and bench step B9 checks both the unplug and the absence of false reports). *Checked by `ur_29_a_lost_device_aborts_the_run`, `ur_29_a_silent_stream_is_a_lost_device` (`DEVICE_LOST` 1 to 2 s after the silence begins) and `ur_29_a_lost_device_is_found_while_idle`.*

### The test double and the bench

- **UR-33** `FakeDevice` is a wall-clock double of a USRP, compiled always and constructed only by Rust code (`FakeDevice::new(FakeConfig)`); `open` never returns one (GZ-9). It is faithful to the device in the ways the tests of §6 depend on, and each way is named here so that a test cannot pass on a looser fake (Review J, T4): **time** — it counts ticks of a configurable master clock (default 200 MHz) from `Instant`, running `FakeConfig::drift_ppm` (default 0) fast or slow against the host; `set_time_zero` resets the count (at the next whole second of its clock when `at_next_pps`); **channels** — one each way per entry of `FakeConfig::front_ends` (default `["UBX", "UBX"]`, at most two), whose front end `front_end` names as that entry followed by ` RX` or ` TX` (the tests' one-CBX fake is `["CBX-120", "Unknown (0xffff) - 0"]`, as a real X310 with slot B empty); **configuration** — `apply` coerces a rate to `mcr / round(mcr / rate)`, a gain to 0.5 dB steps and applies a frequency exactly, taking `FakeConfig::apply_delay` (default 0) of wall time; a timed `apply` joins an in-order command queue: a command takes effect at the later of its time and the previous command's, is late (applied on arrival) when that is past, and the queue refuses to accept more than `FakeConfig::command_queue` commands not yet in effect by blocking, as UHD back-pressures; **transmit** — a transmit queue in order: samples are accepted at most 50 ms ahead of its clock (blocking otherwise), a timed start-of-burst whose time is at or before the end of the samples already queued, or in its past, is reported `TimeError` and dropped (at the end: the X300's behaviour, design-notes §11 F3), reporting a tick at or after the late start, an open burst that runs out of samples before its end-of-burst is reported `Underflow`, a start-of-burst without a time spec inside a burst is recorded as a restart (the CORDIC reset UHD performs, RM-13's evidence), and `BurstAck` is reported at the end of a burst; **receive** — for each receive sample instant it returns the sample transmitted on transmit channel 0 at that instant (delayed by `FakeConfig::loopback_delay_samples`, default 0) **only when the transmit and receive frequencies are equal and the transmit channel's rate matches**, and otherwise a ramp `(k mod 65 536) / 65 536` on the real part; it paces `rx_recv` to its clock; it reports `Overflow` when the reader falls more than 100 ms behind (then skips to the next sample instant after its clock, as a restarted stream would), `LateCommand` for a receive start in its past; it stops the stream at once on any `rx_stop`, timed or not, as the X3x0 does (design-notes §11 F1), still delivering what it produced before the stop, ahead of the next stream's samples (the bench's one or two blocks); an `rx_recv` on a stopped stream waits its whole timeout, as UHD's does (§11 F2); with `FakeConfig::rx_latency` and `rx_packet` (defaults 0 and a whole request) it delivers a packet that long after its last sample and waits for each packet up to the timeout, returning what it has when one does not come and `Timeout` at once on the next call, as UHD's `recv` does (`rx_streamer_impl.hpp`; Review N, T1: the tests of B1 and B2 run on the bench's link, 1 996-sample packets 2–3.5 ms late); **transmit** — it counts a timed start-of-burst sent inside an un-ended burst (`unended_bursts`, Review L, P1-4). A test scripts faults on it (`FakeConfig`): a stall of the reader, an overflow or a sequence error at an instant, an alignment error, an underflow report, a device loss (every later call fails with `lost: true`), a failing time read, a slow one (5 ms, UR-7's bracket rule), an unlocked reference, and a rate it applies wrongly (at `prepare` or at a later switch). `describe()` says `fake: true`; `FakeDevice` records every call for the tests to read. *Checked by `ur_33_the_fake_device_loops_back_what_it_transmits`, `ur_33_the_fake_device_keeps_the_devices_queues`, `ur_33_a_timed_receive_stop_stops_the_stream_at_once`, `ur_33_a_stopped_stream_s_tail_comes_before_the_next_stream`, `ur_33_a_stopped_stream_s_recv_waits_its_whole_timeout`, `ur_33_a_recv_cut_short_by_a_packet_s_timeout_is_followed_by_a_timeout_at_once`, `ur_33_a_timed_start_at_the_previous_burst_s_end_is_late`, `ur_33_a_burst_that_runs_dry_underflows` (Review N, T2), `ur_33_scripted_faults_fire` and `ur_33_no_document_selects_the_fake_device`.*
- **UR-34** `tests/hardware.rs` (feature `uhd`; every test `#[ignore = "needs a USRP: see plan/phase7/bench.md"]`; the device from `EZSDR_UHD_ARGS`, the profile the one the device's receive channel 0 front end names — `x310-obx` for `OBX…`, `x310-cbx` for `CBX…`, else `x310-ubx` — and the steps' frequency that profile's default; GZ-8) runs the bench's steps: `hw_b1_probe`, `hw_b2_authority`, `hw_b3_receive_at_t0`, `hw_b4_capture_at_a_sample_index`, `hw_b5_overflow`, `hw_b6_txrx_and_repeat`, `hw_b7_session_loopback`, `hw_b8_leads`, `hw_b9_unplug` (manual) and `hw_b9_usrp2_probe`.
