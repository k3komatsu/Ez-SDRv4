## 1. Kernel amendments

Each Kernel spec these amendments change records it in its status row: the rows of specs 04 and 06 end "Amended in Phase 3 by KB-1.", that of spec 05 "Amended in Phase 3 by KB-1, KB-2."

### KB-1 — A Module reads the Run's inputs by hash

**Evidence.** The coordinator keeps the bytes of every input in `RunHandle.store: BTreeMap<ContentHash, Vec<u8>>` (`crates/ezsdr-kernel/src/coordinator/mod.rs:106`), which only the control path reads: KC-9 verifies a Spec's inputs against it and KC-28 adds a Session's waveforms to it. A `TxBurst` carries only the waveform's `ArtifactRef` (RS-44a), so a Provider has never been able to read what it is asked to transmit. Phase 2 did not need to: MockRadio took the length from `ArtifactRef.size_bytes` and built no transmit bytes (MR-15, MR-16, Phase 2's Y8, whose stated upgrade path is "Phase 3 reads the bytes when the channel needs them"). The SimulationChannel needs them (MR-32).

**Rejected.** Bytes inside the Action (an Action is a small document with a schema, RS-48; a waveform of megabytes does not belong in the action log). The runtime handing each Provider the input bytes at construction (a Session's waveforms arrive after construction, and RS-44a makes the Kernel the owner of the store). A `file://` read by the Provider (a Session waveform has only a `mem:` uri, and KC-9 keeps file input out of the Run).

**New text.**

Spec 05 §4, the `PrepareContext` row replaced and a row added after `ActionSubmitter`:

```text
PrepareContext    { run: RunId, class: ExecutionClass,
                    time: shared TimeAuthority handle, clocks: shared ClockRegistry handle,
                    events: shared EventSink, actions: shared ActionReceiver,
                    actions_out: shared ActionSubmitter,
                    environment: shared read-only Map<Namespace, Value>,
                    inputs: shared read-only InputStore,
                    links: [{ component: Ident, port: Ident, endpoint: Endpoint }],
                    components: Map<Ident, ComponentDescriptor>, host_budget: RelativeBudget }
ActionSubmitter   submits a proposed Action into admit() (RS-16), never to a Module directly
InputStore        get(ContentHash) -> shared bytes or none: the Run's inputs, read-only (RS-44a, KB-1)
```

**MA-5a amended** (sentence added before its *Checked* marker): "`inputs` is the Run's input store: the bytes of every input KC-9 verified and of every waveform KC-28 ingested, keyed by content hash and read-only. A Session's waveform is stored before the Action that names it is dispatched, so a Provider that transmits a `TxBurst`'s samples reads its waveform there (Phase 3, KB-1)."

**MA-6 amended** (the handle list): "a Kernel handle (`PrepareContext`, the container that carries the others, `EventSink`, `ActionReceiver`, `ActionSubmitter`, `InputStore` (Phase 3, KB-1), `Endpoint`, …".

**MA-46 amended** (the Plugin mapping): "…the `ClockRegistry` a request and response, the `InputStore` a request and response (Phase 3, KB-1), and the `environment` a document sent once at `prepare`."

**RS-44a amended** (sentence added): "The stored bytes are what a Module reads through `PrepareContext.inputs` (spec 05 MA-5a) (Phase 3, KB-1)."

**KC-11 amended** (spec 06): "…the coordinator's `ActionSubmitter`; the profile's `environment`; the Run's input store, shared with KC-9 and KC-28 (KB-1); KC-10's attached ends for this fragment; …".

### KB-2 — A Provider settles its fidelity in `prepare`

**Evidence.** MA-10 (KA-13's sentence): "A Provider's `instance()` returns the same `id`, `tree`, `fidelity`, `driving`, `arm_after` and `min_command_lead` for the whole Run". A MockRadio's `rf` fidelity is `impairment_model` exactly when the environment declares a SimulationChannel (Vision §14: "rf (SimulationChannel models, §16)"), and a Provider reads the environment only in `prepare` (MA-5a). **New text.** **MA-10 amended** (the last sentence before the marker replaced): "A Provider's `instance()` returns the same `id`, `tree`, `driving`, `arm_after` and `min_command_lead` for the whole Run; `fidelity` is final when `prepare` returns, because what a simulated Provider models can depend on the environment it reads there — a SimulationChannel makes MockRadio's `rf` aspect `impairment_model` (MR-31); after that only `sections` may change, as the Provider records what happened (Phase 3, KB-2)." ## 2. Vocabulary and Module amendments

### VB-1 — `radio` 1.1.0: path delays, the late comparison, the stop instant

**Evidence.**
- Spec 07 §8 deferred "A delay-calibration default per profile (Vision §26; Phase 3, when a loopback makes it observable)", and Vision §26 makes it "not optional, even for SISO". A loopback is observable now (spec 11).
- RM-14 compares a burst's target with the Provider's "current instant in the transmit SampleClock" without saying how that instant is rounded to a sample; MockRadio floors it (`crates/ezsdr-mock-radio/src/lib.rs:701`), so with a zero lead a target on the sample the current instant falls in — an instant already past — is `OnTime`, and would radiate before the round that admitted it (spec 11 CH-9).
- RM-16 closes the open burst at a stop without saying which samples were transmitted; MockRadio closes it at the end of the last whole block it emitted (`lib.rs:616-633`), so the samples between that block and the stop instant — in the past, and so transmitted by any real device that had received them — are neither recorded (SC-28: "what was transmitted is recorded") nor, with a channel, radiated.


### VB-4 — A block is published or emitted only after its last sample

**Evidence.** MR-14 publishes a block "when `until` is at or after the root tick of sample `s + L − 1`, rounded up" (`lib.rs:336-337`, and the wakeup at `lib.rs:513`). When that last sample's instant is an integer root tick — every sample at 1 Msps on a 1 GHz root — the block is published in the very round of its last sample. Its content from the SimulationChannel then depends on whether a transmitter stepped earlier in that round has already started a burst at that instant (spec 11 CH-9). On hardware a sample is delivered only after it has been taken. The transmit side had the same inclusive rule (MR-15: "when `until` has reached its last sample", `lib.rs:781` and its wakeup at `lib.rs:530`): the first pass of a round at the instant of a transmit block's last sample emitted and recorded that sample, and an Action handled in a later pass of the same round — a stop, whose cut is the first sample at or after the round, or a burst starting at that sample after the block had ended its burst — then cut the radiation below the record or let two records hold one sample (found by the fourth planning review, P0-1 and P0-2, through a Session as well).

**Rejected.** A strict rule in channel mode only (two publication rules in one Provider, and the pattern-mode rule is no more faithful); stepping transmitters first (spec 11 C8); for the transmit side, tracking the first sample not yet transmitted and raising a stop's cut and MR-16's refusal to it (a second notion of "now" beside the round's, and a stop would then transmit the sample at its own instant in one pass and not in another, against RM-16).

**New text** (spec 09): **MR-14 amended** — its first sentence replaced by "A receive block is published once its last sample is in the past: in `step(until)`, a block `[s, s + L)` is published when `until` is strictly after the instant of sample `s + L − 1`, that is at or after that instant's floor plus one root tick. A sample is never delivered at the instant it is taken, as on hardware, and a block computed from the SimulationChannel is then final whatever order the stepping loop steps the Mocks in (spec 11 CH-9) (Phase 3, VB-4)." — and its wakeup clause "the root tick, rounded up, of the next receive block's last sample, that of the next transmit block's last sample," replaced by "the first root tick strictly after the next receive block's last sample, the first root tick strictly after the next transmit block's last sample,". **MR-15 amended** — "A block is emitted when `until` has reached its last sample, as MR-14 says." becomes "A block is emitted once its last sample is in the past, as MR-14 says of a receive block: when `until` is strictly after the instant of its last sample. An Action handled at the instant of a transmit sample, in whichever pass of that round, therefore finds that sample not yet transmitted, and a stop's cut (MR-25), MR-16's refusals and the burst records agree with what is radiated (Phase 3, VB-4)." In §4's algorithm, "emit every receive block whose last sample is ≤ until" becomes "emit every receive block whose last sample is before until (MR-14)", and "emit every transmit block whose last sample is ≤ until" becomes "emit every transmit block whose last sample is before until (MR-15)". The **Tests** row of `mr_14_blocks_appear_when_their_last_sample_has_occurred` becomes "at 1 Msps with 1 GHz root, block 0 appears at `T0 + 1 999 001`, not at `T0 + 1 999 000`, the instant of its last sample; the next wakeup is at `T0 + 3 999 001`", MR-14's marker becomes "*Checked by `mr_14_blocks_appear_when_their_last_sample_has_occurred`, `mr_14_a_block_is_published_strictly_after_its_last_sample` and `ch_09_the_receive_output_does_not_depend_on_the_stepping_order` (Phase 3, VB-4).*", and `mr_19_backpressure_is_an_overrun`'s "step to the instant of block 0's last sample" becomes "step to one root tick after block 0's last sample" (and likewise for block 1 and the block beginning at 52 000).

**Code.** `patches/03-mock-radio.patch`: `src/time.rs` gains `v_after(o, q, k) = ⌊o + k · q⌋ + 1` with the unit test `mr_14_a_block_is_published_strictly_after_its_last_sample`; `emit_rx_until`, `emit_tx_until` and both wakeups of `schedule_wakeup` call it where they called `v_of`.

**Tests.** `mr_14_blocks_appear_when_their_last_sample_has_occurred` (amended), `mr_14_a_block_is_published_strictly_after_its_last_sample` (new unit test), and CH-9's `ch_09_the_receive_output_does_not_depend_on_the_stepping_order`, which fails with the inclusive rule. Eight Phase 2 MockRadio tests step one root tick later than before, because they stepped to exactly a last sample's instant and asserted the block: `mr_13_ramp_values`, `mr_14_…`, `mr_18_a_cold_rate_change_starts_a_new_sample_clock`, `mr_18_a_cold_receive_change_before_t0_applies_at_t0`, `mr_19_backpressure_is_an_overrun`, `mr_21_overrun_shape`, `mr_22_sequence_error_shape`, `mr_25_orderly_stop_delivers_the_tail_abort_does_not`. ### VB-8 — A burst cannot start at or before the open burst's next sample

## 3. Vision issues found

1. **§26** says "Ez-SDR carries a default per device profile in the Radio Model"; RM-23 carries it as two capabilities in samples, as srsRAN and OpenAirInterface do. §26 should name them.
2. **§23** says "MockRadio clips at the contract's full scale (Phase 2 Mock obligations)"; MR-36 does, in Phase 3. The parenthesis should read "(MR-36)".
3. **§25**'s "the Provider declares this behaviour and MockRadio emulates it" is MR-34; §26's closing sentence "emulation of phase changes on retune is Phase 3 work" should cite it.
4. **§13 rule 3** ("RF behaviour is not part of the envelope. It stays in SimulationChannel") and **§16**'s list, which names clipping among the channel's models, put all RF behaviour in the channel. Phase 3 puts the device's own RF behaviour — gain, LO phase, clipping, path delay — in the radio model and only propagation in the channel (M15), as §23 (MockRadio clips) and §25 (MockRadio emulates the retune phase) already imply. §13 rule 3 should say propagation stays in the SimulationChannel, and §16 should call clipping the radio's.
